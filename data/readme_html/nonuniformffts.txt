<p dir="auto">Yet another package for computing multidimensional <a href="https://en.wikipedia.org/wiki/NUFFT" rel="nofollow">non-uniform fast Fourier transforms (NUFFTs)</a> in Julia.</p>
<p dir="auto">Like other <a href="#differences-with-other-packages">existing packages</a>, computations
are parallelised using threads.
By default, all available Julia threads are used.</p>

<summary><b>Using the AbstractNFFTs.jl interface</b></summary>
<p dir="auto">This package also implements the <a href="https://juliamath.github.io/NFFT.jl/stable/abstract/" rel="nofollow">AbstractNFFTs.jl</a>
interface as an alternative API for constructing plans and evaluating transforms.
This can be useful for comparing with similar packages such as <a href="https://github.com/JuliaMath/NFFT.jl">NFFT.jl</a>.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using NonuniformFFTs
using AbstractNFFTs
using LinearAlgebra: mul!

Ns = (256, 256)  # number of Fourier modes in each direction
Np = 1000        # number of non-uniform points

# Generate some non-uniform random data
T = Float64                      # must be a real data type (Float32, Float64)
d = length(Ns)                   # number of dimensions (d = 2 here)
xp = rand(T, (d, Np)) .- T(0.5)  # non-uniform points in [-1/2, 1/2)ᵈ; must be given as a (d, Np) matrix
vp = randn(Complex{T}, Np)       # random values at points (must be complex)

# Create plan for data of type Complex{T}. Note that we pass the points `xp` as
# a first argument, which calls an AbstractNFFTs-compatible constructor.
p = PlanNUFFT(xp, Ns)

# Getting the expected dimensions of input and output data.
AbstractNFFTs.size_in(p)   # (256, 256)

<p dir="auto">This package roughly follows the same notation and conventions of the <a href="https://finufft.readthedocs.io/en/latest/" rel="nofollow">FINUFFT library</a>
and its <a href="https://github.com/ludvigak/FINUFFT.jl">Julia interface</a>, with a few differences detailed below.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Conventions used by this package</h3><a id="user-content-conventions-used-by-this-package" class="anchor" aria-label="Permalink: Conventions used by this package" href="#conventions-used-by-this-package"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">We try to preserve as much as possible the conventions used in FFTW3.
In particular, this means that:</p>
<ul dir="auto">
<li>
<p dir="auto">The FFT outputs are ordered starting from mode <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$k = 0$</math-renderer> to <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$k = N/2 - 1$</math-renderer> (for even <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$N$</math-renderer>) and then from <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$-N/2$</math-renderer> to <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$-1$</math-renderer>.
Wavenumbers can be obtained in this order by calling <code>AbstractFFTs.fftfreq(N, N)</code>.
Use <code>AbstractFFTs.fftshift</code> to get Fourier modes in increasing order <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b8fb9d3e2ff2c0ecdb8fdd594e205bb7">$-N/2, …, -1, 0, 1, …, N/2 - 1$</math-renderer>.
In FINUFFT, one should set <a href="https://finufft.readthedocs.io/en/latest/opts.html#data-handling-options" rel="nofollow"><code>modeord = 1</code></a> to get this order.</p>
</li>
<li>
<p dir="auto">The type-1 NUFFT (non-uniform to uniform) is defined with a minus sign in the exponential.
This is the same convention as the <a href="http://fftw.org/fftw3_doc/The-1d-Discrete-Fourier-Transform-_0028DFT_0029.html" rel="nofollow">forward DFT in FFTW3</a>.
In particular, this means that performing a type-1 NUFFT on uniform points gives the same output than performing a FFT using FFTW3.
In FINUFFT, this corresponds to setting <a href="https://ludvigak.github.io/FINUFFT.jl/latest/#FINUFFT.finufft_makeplan-Tuple%7BInteger,%20Union%7BInteger,%20Array%7BInt64%7D%7D,%20Integer,%20Integer,%20Real%7D" rel="nofollow"><code>iflag = -1</code></a> in type-1 transforms.
Conversely, type-2 NUFFTs (uniform to non-uniform) are defined with a plus sign, equivalently to the backward DFT in FFTW3.</p>
</li>
</ul>
<p dir="auto">For compatibility with other packages such as <a href="https://github.com/JuliaMath/NFFT.jl">NFFT.jl</a>, these conventions are <em>not</em>
applied when the AbstractNFFTs.jl interface is used (see example above).
In this specific case, modes are assumed to be ordered in increasing order, and
the opposite sign convention is used for Fourier transforms.</p>
