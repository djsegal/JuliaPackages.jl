<p dir="auto">The <code>ShortFFTs.jl</code> package provides a single function, <code>short_fft</code>,
that performs a Fast Fourier Transform (FFT) on its input. Different
from the <code>fft</code> functions provided via the <code>AbstractFFTs.jl</code> interface
(e.g. by <code>FFTW.jl</code>), <code>short_fft</code> is designed to be called for a single
transform at a time.</p>
<p dir="auto">One major advantage of <code>short_fft</code> is that it can be efficiently
called from within a loop kernel, or from device code (e.g. a CUDA
kernel). This allows combining several operations into a single loop,
e.g. pre-processing input data by applying a window function.</p>
<p dir="auto">The term "short" in the name refers to FFT lengths less than about
1000.</p>

<p dir="auto">The function <code>short_fft</code> expects its input as a tuple. One also needs
to specify the output element type. The output of the FFT is returned
as a tuple as well. This makes sense because the call to <code>short_fft</code>
is expected to be inlined, and using arrays would introduce an
overhead.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using ShortFFTs

<p dir="auto"><code>short_fft</code> can be called by device code, e.g. in a CUDA kernel.</p>
<p dir="auto"><code>short_fft</code> is a "generated function" that is auto-generated at run
time for each output type and tuple length. The first call to
<code>short_fft</code> for a particular combination of argument types is much
more expensive than the following because Julia needs to generate the
optimzed code.</p>
<p dir="auto">Since <code>short_fft</code> is implemented in pure Julia it can work with any
(complex) type. The implementation uses local variables as scratch
storage, and very large transforms are thus likely to be inefficient.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Algorithm</h2><a id="user-content-algorithm" class="anchor" aria-label="Permalink: Algorithm" href="#algorithm"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>ShortFFTs.jl</code> implements the <a href="https://en.wikipedia.org/wiki/Cooley%E2%80%93Tukey_FFT_algorithm" rel="nofollow">Cooley-Tukey FFT
algorithm</a>
as described on Wikipedia. It has been tested against <code>FFTW.jl</code>.</p>
<p dir="auto">Transforms of any lenghts are supported. Lengths without large prime
factors (especially powers of two) are significantly more efficient.
<code>256</code> is a very good length, <code>257</code> is a very bad one (since it is a
prime number).</p>
<p dir="auto"><code>short_fft</code> is not parallelized at all. It is expected that the
surrounding code is parallelized if that makes sense. For long
transforms <code>AbstractFFTs.jl</code> will provide a better performance.</p>

<p dir="auto">Since <code>short_fft</code> is implemented purely in Julia, expressions can also
be evaluate symbolically. Notice that the input points that are known
to be zero are optimized away in the output:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; using ShortFFTs

y[0] = x0 + x1 + x2 + x3
