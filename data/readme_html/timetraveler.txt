<p dir="auto"><strong>Welcome Time Traveler!</strong></p>
<p dir="auto">TimeTraveler.jl is a package designed to make your time adventures more easy and  convenient.</p>
<p dir="auto"><g-emoji class="g-emoji" alias="warning">⚠️</g-emoji> Please do not add this as a dependency of your package <g-emoji class="g-emoji" alias="warning">⚠️</g-emoji><br>
Time travel is too dangerous to put in the hands of automated systems.
Instead add it to your global environment, like Revise etc.</p>
<p dir="auto">You should also add <code>using TimeTraveler</code> to your start-up.jl.
e.g. by adding to <code>~/.julia/config/startup.jl</code></p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="try
    using TimeTraveler
catch e
    @warn &quot;Error initializing TimeTraveler&quot; exception=e
end"><pre><span class="pl-k">try</span>
    <span class="pl-k">using</span> TimeTraveler
<span class="pl-k">catch</span> e
    <span class="pl-c1">@warn</span> <span class="pl-s"><span class="pl-pds">"</span>Error initializing TimeTraveler<span class="pl-pds">"</span></span> exception<span class="pl-k">=</span>e
<span class="pl-k">end</span></pre></div>
<p dir="auto">You can not time-travel to before the machine was built.
Or more precisely, you can, but you need to know exactly when your destination is.
You can use <code>@back_in_the_day</code> to travel to world-age provided as a <code>UInt64</code>, but you can't use <code>@when_freshly_loaded Package</code> to travel to the time of loading <code>Package</code> if that package was loaded before TimeTraveler.jl as we won't have tracked when that was.</p>
<p dir="auto">Be aware you can not modify the past!
Which is to say you can not define new methods in old world-ages.
But you can observe it.</p>

<p dir="auto">In all seriousness the intended use case of this is is for writing tests.
The ideal Test Driven Development workflow is</p>
<ol dir="auto">
<li>Write a test.</li>
<li>Make sure it fails.</li>
<li>Write the code so it doesn't fail.</li>
<li>Confirm the test now passes.</li>
</ol>
<p dir="auto">In practice it is often annoying to write the test before you have written the code. Sometimes it is hard to know what you need to test.
So what this package lets you do is, write the test after you have written the code, but then time travel back to before you wrote the test</p>

<p dir="auto">Lets say we are fixing a bug in Foo.jl</p>
<p dir="auto">First do
<code>using TimeTraveler</code> (if it isn't in your startup.jk),
then you go about your day by loading <code>Foo</code> and doing what ever you need to do.
Then you run into a bug in Foo, while trying to do something else.</p>
<p dir="auto">Now go and fix that bug.
While using <a href="https://timholy.github.io/Revise.jl" rel="nofollow">Revise.jl</a> so your active julia session reflects the changes you have made.
(Or if you must by reexecuting defintions manually)</p>
<p dir="auto">Then write a test</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@test Foo.foo() = 100"><pre><span class="pl-c1">@test</span> Foo<span class="pl-k">.</span><span class="pl-en">foo</span>() <span class="pl-k">=</span> <span class="pl-c1">100</span></pre></div>
<p dir="auto">and you see that that passes</p>
<p dir="auto">Now to go back and confirm it used to fail:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@when_freshly_loaded Foo begin
    @test foo.foo() == 100
end"><pre><span class="pl-c1">@when_freshly_loaded</span> Foo <span class="pl-k">begin</span>
    <span class="pl-c1">@test</span> foo<span class="pl-k">.</span><span class="pl-c1">foo</span>() <span class="pl-k">==</span> <span class="pl-c1">100</span>
<span class="pl-k">end</span></pre></div>
<p dir="auto">Note: if you didn't load <code>Test</code> before loading the package then the test code may not be defined.
So you would do <code>@@when_freshly_loaded Test</code> instead to run at the time that was loaded -- if that is early enough.
If not you would have to move the <code>@test</code> outside the macro -- or inspect the result manually.
e.g.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@test 100 == @when_freshly_loaded Foo foo.foo()"><pre><span class="pl-c1">@test</span> <span class="pl-c1">100</span> <span class="pl-k">==</span> <span class="pl-c1">@when_freshly_loaded</span> Foo foo<span class="pl-k">.</span><span class="pl-c1">foo</span>()</pre></div>
<p dir="auto">There is also <a href="https://timholy.github.io/Revise.jl/stable/#Secrets-of-Revise-%22wizards%22-1" rel="nofollow">a section in the Revise.jl docs</a> about a similar work flow, which doing this with <code>git stash</code>.</p>

<p dir="auto">It's worth understanding how this time machine works.
Basically julia has a notion of a <em>world age</em>.
This is incremented every time package is loaded or a new method is defined etc.
And things always run in a particular world-age, which must be after the one where they were defined. -- Its why you can't <code>eval</code> a method then call it from within the same function (<code>invoke_latest</code> bypasses this rule.).
Method specialiations remember the first and last world age they are allowed to run in.
<code>Base.invoke_in_world</code> allows a function to be called in a particular world age.</p>
