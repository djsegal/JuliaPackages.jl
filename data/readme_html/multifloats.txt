<p dir="auto"><strong>MultiFloats.jl</strong> is a Julia package for extended-precision arithmetic using 100–400 bits (30–120 decimal digits). In this range, it is the fastest library that I am aware of. At 100-bit precision, <strong>MultiFloats.jl</strong> is roughly <strong>40× faster than <a href="https://docs.julialang.org/en/v1/manual/integers-and-floating-point-numbers/#Arbitrary-Precision-Arithmetic" rel="nofollow"><code>BigFloat</code></a></strong>, <strong>5× faster than <a href="https://github.com/JuliaMath/Quadmath.jl">Quadmath.jl</a></strong>, and <strong>1.5× faster than <a href="https://github.com/JuliaMath/DoubleFloats.jl">DoubleFloats.jl</a></strong>.</p>
<p dir="auto"><strong>MultiFloats.jl</strong> is fast because it uses native <code>Float64</code> operations on static data structures that do not dynamically allocate memory. In contrast, <a href="https://docs.julialang.org/en/v1/manual/integers-and-floating-point-numbers/#Arbitrary-Precision-Arithmetic" rel="nofollow"><code>BigFloat</code></a> allocates memory for every single arithmetic operation, requiring frequent pauses for garbage collection. In addition, <strong>MultiFloats.jl</strong> uses branch-free algorithms that can be vectorized for even faster execution on <a href="https://github.com/eschnett/SIMD.jl">SIMD</a> processors.</p>
<p dir="auto"><strong>MultiFloats.jl</strong> provides pure-Julia implementations of the basic arithmetic operations (<code>+</code>, <code>-</code>, <code>*</code>, <code>/</code>, <code>sqrt</code>), comparison operators (<code>==</code>, <code>!=</code>, <code>&lt;</code>, <code>&gt;</code>, <code>&lt;=</code>, <code>&gt;=</code>), and floating-point introspection methods (<code>isfinite</code>, <code>eps</code>, <code>minfloat</code>, etc.). Transcendental functions (<code>exp</code>, <code>log</code>, <code>sin</code>, <code>cos</code>, etc.) are supported through <a href="https://www.mpfr.org/" rel="nofollow">MPFR</a>.</p>
<p dir="auto"><strong>MultiFloats.jl</strong> stores extended-precision numbers in a <strong>multi-limb representation</strong> that generalizes the idea of <a href="https://en.wikipedia.org/wiki/Quadruple-precision_floating-point_format#Double-double_arithmetic" rel="nofollow">double-double arithmetic</a> to an arbitrary number of components. This idea takes inspiration from Jonathan Shewchuk's work on <a href="http://dx.doi.org/10.1007/pl00009321" rel="nofollow">adaptive-precision floating-point arithmetic</a> and Yozo Hida, Xiaoye Li, and David Bailey's <a href="https://doi.org/10.1109/ARITH.2001.930115" rel="nofollow">algorithms for quad-double arithmetic</a>, combined with Julia's metaprogramming capabilities.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">New Features in v2.0</h2><a id="user-content-new-features-in-v20" class="anchor" aria-label="Permalink: New Features in v2.0" href="#new-features-in-v20"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><strong>MultiFloats.jl v2.0</strong> now supports explicit SIMD vector programming using <a href="https://github.com/eschnett/SIMD.jl">SIMD.jl</a>. In addition to the basic scalar types <code>Float64x2</code>, <code>Float64x3</code>, ..., <code>Float64x8</code>, <strong>MultiFloats.jl v2.0</strong> also provides the vector types <code>v2Float64x2</code>, <code>v4Float64x2</code>, <code>v8Float64x2</code>, ..., <code>v2Float64x8</code>, <code>v4Float64x8</code>, <code>v8Float64x8</code>, allowing users to operate on two, four, or eight extended-precision values at a time. These are all instances of the generic type <code>MultiFloatVec{M,T,N}</code>, which represents a vector of <code>M</code> values, each consisting of <code>N</code> limbs of type <code>T</code>.</p>
<p dir="auto"><strong>MultiFloats.jl v2.0</strong> also provides the functions <code>mfvgather(array, indices)</code> and <code>mfvscatter(vector, array, indices)</code> to simultaneously load/store multiple values from/to a dense array of type <code>Array{MultiFloat{T,N},D}</code>.</p>
<p dir="auto"><strong>MultiFloats.jl v2.0</strong> uses Julia's <code>@generated function</code> mechanism to automatically generate code on-demand for arithmetic and comparison operations on <code>MultiFloat</code> and <code>MultiFloatVec</code> values. It is no longer necessary to call <code>MultiFloats.use_standard_multifloat_arithmetic(9)</code> in order to compute with <code>Float64x{9}</code>; thanks to the magic of metaprogramming, it will just work!</p>

<p dir="auto"><strong>MultiFloats.jl v2.0</strong> no longer exports the <code>renormalize</code> function by default. Internal renormalization is now performed more frequently, which should make it unnecessary for users to explicitly call <code>renormalize</code> in the vast majority of cases. It is still available for internal use as <code>MultiFloats.renormalize</code>.</p>
<p dir="auto"><strong>MultiFloats.jl v2.0</strong> no longer provides the user-selectable precision modes that were available in v1.0. Consequently, the following functions no longer exist:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="MultiFloats.use_clean_multifloat_arithmetic()
MultiFloats.use_standard_multifloat_arithmetic()

MultiFloats.use_standard_multifloat_arithmetic()
MultiFloats.use_sloppy_multifloat_arithmetic()
</code></pre></div>
<p dir="auto">My experience has shown that <code>sloppy</code> mode causes serious problems in every nontrivial program, while <code>clean</code> mode has poor performance tradeoffs. Instead of using, say, <code>Float64x3</code> in <code>clean</code> mode, it almost always makes more sense to use <code>Float64x4</code> in <code>standard</code> mode. Therefore, I made the decision to streamline development by focusing only on <code>standard</code> mode. If you have an application where <code>sloppy</code> or <code>clean</code> mode is demonstrably useful, please open an issue for discussion!</p>
<p dir="auto"><strong>MultiFloats.jl v2.0</strong> no longer provides a pure-MultiFloat implementation of <code>exp</code> and <code>log</code>. The implementation provided in v1.0 was flawed and performed only marginally better than MPFR. A new implementation, based on economized rational approximations to <code>exp2</code> and <code>log2</code>, is being developed for a future v2.x release.</p>

<p dir="auto"><strong>MultiFloats.jl</strong> provides the types <code>Float64x2</code>, <code>Float64x3</code>, ..., <code>Float64x8</code>, which represent extended-precision numbers with 2×, 3×, ..., 8× the precision of <code>Float64</code>. These are all subtypes of the parametric type <code>MultiFloat{T,N}</code>, where <code>T = Float64</code> and <code>N = 2, 3, ..., 8</code>.</p>
<p dir="auto">Instances of <code>Float64x2</code>, <code>Float64x3</code>, ..., <code>Float64x8</code> are convertible to and from <code>Float64</code> and <code>BigFloat</code>, as shown in the following example.</p>

<p dir="auto"><sup>Note: <strong>MultiFloats.jl</strong> also provides a <code>Float64x1</code> type that has the same precision as <code>Float64</code>, but behaves like <code>Float64x2</code>–<code>Float64x8</code> in terms of supported operations. This is occasionally useful for testing, since any code that works for <code>Float64x1</code> should also work for <code>Float64x2</code>–<code>Float64x8</code> and vice versa.</sup></p>

<p dir="auto"><strong>MultiFloats.jl</strong> requires an underlying implementation of <code>Float64</code> with IEEE round-to-nearest semantics. It works out-of-the-box on x86 and ARM but may fail on more exotic architectures.</p>
<p dir="auto"><strong>MultiFloats.jl</strong> does not attempt to propagate IEEE <code>Inf</code> and <code>NaN</code> values through arithmetic operations, as this <a href="https://github.com/dzhang314/MultiFloats.jl/issues/12#issuecomment-751151737" data-hovercard-type="issue" data-hovercard-url="/dzhang314/MultiFloats.jl/issues/12/hovercard">could cause significant performance losses</a>. You can pass these values through the <code>Float64x{N}</code> container types, and introspection functions (<code>isinf</code>, <code>isnan</code>, etc.) will work, but arithmetic operations will typically produce <code>NaN</code> on all non-finite inputs.</p>
