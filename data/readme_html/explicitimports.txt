<ul dir="auto">
<li><em>implicit import</em>: a name <code>x</code> available in a module due to <code>using XYZ</code> for some package or module <code>XYZ</code>. This name has not been explicitly imported; rather, it is simply available since it is exported by <code>XYZ</code>.</li>
<li><em>explicit import</em>: a name <code>x</code> available in a module due to <code>using XYZ: x</code> or <code>import XYZ: x</code> for some package or module <code>XYZ</code>.</li>
<li><em>qualified access</em>: a name <code>x</code> accessed via <code>XYZ.x</code></li>
</ul>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Why</h2><a id="user-content-why" class="anchor" aria-label="Permalink: Why" href="#why"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Relying on implicit imports can be problematic, as Base or another package can start exporting that name as well, resulting in a clash. This is a tricky situation because adding a new feature to Base (or a package) and exporting it is not considered a breaking change to its API, but it can cause working code to stop working due to these clashes.</p>
<p dir="auto">If you've even seen a warning like:</p>
<blockquote>
<p dir="auto">WARNING: both X and Y export "foo"; uses of it in module MyPackage must be qualified</p>
</blockquote>
<p dir="auto">Then this is the kind of clash at issue. When this occurs, the name <code>foo</code> won't point to either package's name, since it is ambiguous which one it should be. However, if the package code is relying on the name <code>foo</code> existing, then there's trouble.</p>
<p dir="auto">One fix, as the warning suggests, is to qualify the use <code>foo</code> by writing e.g. <code>X.foo</code> or <code>Y.foo</code>. Another option is to explicitly import it, by writing <code>using X: foo</code> instead of just <code>using X</code>.</p>
<p dir="auto">There are various takes on <em>how problematic</em> this issue is, to what extent this occurs in practice, and to what extent it is worth mitigating. See <a href="https://github.com/JuliaLang/julia/pull/42080" data-hovercard-type="pull_request" data-hovercard-url="/JuliaLang/julia/pull/42080/hovercard">julia#42080</a> for some discussion on this.</p>
<p dir="auto">Personally, I don't think this is always a huge issue, and that it's basically fine for packages to use implicit imports if that is their preferred style and they understand the risk. But I do think this issue is somewhat a "hole" in the semver system as it applies to Julia packages, and I wanted to create some tooling to make it easier to mitigate the issue for package authors who would prefer to not rely on implicit imports.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Some tricky scoping situations are not handled correctly</h3><a id="user-content-some-tricky-scoping-situations-are-not-handled-correctly" class="anchor" aria-label="Permalink: Some tricky scoping situations are not handled correctly" href="#some-tricky-scoping-situations-are-not-handled-correctly"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">These can likely all be fixed by improving the code in <code>src/get_names_used.jl</code>, so they aren't inherent limitations of this approach, but since we are re-implementing Julia's scoping rules on top of the parse tree, for fully accurate results we need to handle each situation correctly, which takes a lot of work.</p>
<p dir="auto">Known issues:</p>
<ul dir="auto">
<li><code>global</code> and <code>local</code> keywords are currently ignored</li>
<li><code>baremodule</code> is currently not handled</li>
<li>arguments in macro definitions are not handled (may be treated incorrectly as globals)</li>
<li>arguments to <code>let</code> blocks are not handled (may be treated incorrectly as globals)</li>
<li>multi-argument <code>include</code> calls are ignored</li>
<li>In Julia, <code>include</code> adds the included code at top-level in the module in which it is called. Here, when <code>include</code> is called within a local scope, all of the code being included is treated as being within that local scope.</li>
<li>quoted code (e.g. when building Julia expressions programmatically) may be analyzed incorrectly</li>
<li>default values in function definitions can be incorrectly treated as local variables (<a href="https://github.com/ericphanson/ExplicitImports.jl/issues/62" data-hovercard-type="issue" data-hovercard-url="/ericphanson/ExplicitImports.jl/issues/62/hovercard">#62</a>)</li>
</ul>
<p dir="auto">The consequence of these issues is that ExplicitImports may misunderstand whether or not a particular name refers to a local variable or a global one, and thus whether or not some particular implicitly-available name (exported by some module) is in fact being used. This could cause it to suggest an unnecessary explicit import, fail to suggest an explicit import, or to falsely claim that an explicit import is stale.</p>
<p dir="auto">Hopefully these situations are somewhat rare, because even if ExplicitExports misunderstands the scoping for one usage of a name, it may correctly parse the scoping of it in another usage in the same module, and could end up drawing the correct conclusion anyway.</p>
<p dir="auto">Additionally, the testing-oriented functions <code>check_no_implicit_imports</code> and <code>check_no_stale_explicit_imports</code> have the ability to filter out problematic names or modules, to allow manual intervention in cases in which ExplicitImports gets it wrong.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Cannot recurse through dynamic <code>include</code> statements</h3><a id="user-content-cannot-recurse-through-dynamic-include-statements" class="anchor" aria-label="Permalink: Cannot recurse through dynamic include statements" href="#cannot-recurse-through-dynamic-include-statements"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">These are <code>include</code> in which the argument is not a string literal. For example, the package MathOptInterface.jl currently includes the following code in it's <code>Test</code> module:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="for file in readdir(@__DIR__)

<p dir="auto">This is problematic for ExplicitImports.jl; unless we really use a full-blown interpreter (which I do think could be a viable strategy<sup><a href="#user-content-fn-1-6c53544488440c8a7dcf3b11114fc6bf" id="user-content-fnref-1-6c53544488440c8a7dcf3b11114fc6bf" data-footnote-ref="" aria-describedby="footnote-label">1</a></sup>), we can't really execute this code to know what files are being included. Thus being unable to traverse dynamic includes is essentially an inherent limitation of the approach used in this package.</p>
<p dir="auto">The consequence of missing files is that the any names used or imports made in those files are totally missed. Even if we did take a strategy like "scan the package <code>src</code> directory for Julia code, and analyze all those files", without understanding <code>includes</code>, we wouldn't understand which files belong to which modules, making this analysis useless.</p>
<p dir="auto">However, we do at least detect this situation, so we can know which modules are affected by the missing information, and (by default) refuse to make claims about them. For example, running <code>print_explicit_imports</code> on this module gives:</p>

<p dir="auto">If we do pass <code>strict=false</code>, in this case we get</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Need to load the package/module</h3><a id="user-content-need-to-load-the-packagemodule" class="anchor" aria-label="Permalink: Need to load the package/module" href="#need-to-load-the-packagemodule"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This implementation relies on <code>Base.which</code> to introspect which module any given name comes from, and therefore we need to load the module, not just inspect its source code. We can't solely use the source code because implicit imports are implicit -- which is part of the criticism of them in the first place, that the source file alone does not tell you where the names come from.</p>
<p dir="auto">In particular, this means it is hard to convert implicit imports to explicit as a formatting pass, for example.</p>
<p dir="auto">Given a running <a href="https://github.com/julia-vscode/LanguageServer.jl">language server</a>, however, I think it should be possible to query that for the information needed.</p>
