<p dir="auto">A <code>RecursiveDict</code> is a wrapped <code>Dict</code>, where values may always be a <code>Dict</code> (or
<code>RecursiveDict</code>) with the same type parameters.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Why Does the Type Signature Look Like That?</h2><a id="user-content-why-does-the-type-signature-look-like-that" class="anchor" aria-label="Permalink: Why Does the Type Signature Look Like That?" href="#why-does-the-type-signature-look-like-that"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Type parameters express the free variables in the type. In a <code>Dict{K,V}</code>, the keytype and
valtype are both free, so <code>K</code> and <code>V</code> are both the <code>keytype</code> and <code>valtype</code>, and the free parameters.</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="julia&gt; d = Dict{Int,String}(1 =&gt; &quot;one&quot;, 2 =&gt; &quot;two&quot;)

<p dir="auto">With a <code>RecursiveDict</code>, the free parameters are the <code>keytype</code>, and whatever value type
<em>other than that sort of RecursiveDict</em> is allowed, so the above identity doesn't hold.</p>

<p dir="auto">This fact is why <code>RecursiveDicts</code> exists, since it makes it impossible to specify
a recursive container without wrapping it in a struct.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">What's the Point?</h2><a id="user-content-whats-the-point" class="anchor" aria-label="Permalink: What's the Point?" href="#whats-the-point"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Types are good for a few things, one of those things is correctness: types can ensure
that certain invariants always hold.  A recursively-defined hashmap is a useful
primitive for building tree structures, for instance, one might make a prefix tree (Trie)
from <code>RecursiveDict{String,String}</code>.  It's also the natural structure to build syntax
trees, and many other common composite data types.</p>
<p dir="auto">The <code>RecursiveDict</code> struct is nothing more than an immutable container around a <code>Dict</code>.
The Julia compiler is very good at inferring through this kind of wrapper and inlining
methods which act on it, so there should be no performance impact from using it.</p>
<p dir="auto">It's possible that the compiler might be free to write more efficient code under some
circumstances, although I wouldn't count on it.  It does let <em>you</em> write more efficient
code.  Since, by construction, the type parameters of a <code>RecursiveDict</code> value will be the
ones you expect, there's no need to check this.</p>
<p dir="auto">The real reason this package exists is because, early in my Julia journey, I drove myself
insane trying to write a type signature for a recursively defined <code>Dict</code>.  I learned a lot
about type parameters from the exercise, but had to give up, because it is not, in fact,
possible.</p>
<p dir="auto">Recursively-defined structs, on the other hand, are legal. Hence this package.</p>

<p dir="auto">If you want a <code>Dict</code> where the <code>valtype</code> includes the same sort of Dict, absolutely!
<code>RecursiveDicts</code> has a version of every test on <code>Dict</code> from Julia core, modified where
necessary to reflect the semantic differences.  Other than the obvious ones involving
<code>valtype</code>, <code>RecursiveDicts</code> will not promote numeric types which differ to a common type
(with the exception of Pairs passed during the original creation of the dict).  That
might be a bit surprising, but it's consistent with the <code>valtype</code> being a Union, Julia
throws an error on code like <code>convert(Union{Int,Symbol}, 4.0)</code>.</p>
<p dir="auto"><code>RecursiveDicts</code> is a self-contained package, having no dependencies other than the
stdlib.</p>
<p dir="auto"><code>convert(Dict, d::RecursiveDict)</code> will return the wrapped <code>Dict</code>, which will continue to
share contents with the original, and <code>convert(RecursiveDict, d::Dict)</code> is also defined,
this makes it mostly painless to use a <code>RecursiveDict</code> wherever a <code>Dict</code> is
expected.  Many, probably most, methods with <code>::Dict</code> in the signature, should actually
have <code>::AbstractDict</code>, so if you have the option, it's better to relax the signature (or
submit a PR doing so) than to unwrap the <code>RecursiveDict</code>.</p>
