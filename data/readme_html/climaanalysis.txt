<p dir="auto"><code>ClimaAnalysis.jl</code> is a Julia library to post-process and visualize <code>ClimaAtmos</code>
simulations (and, more generally, NetCDF files).</p>
<p dir="auto">Check out the <a href="https://CliMA.github.io/ClimaAnalysis.jl" rel="nofollow">documentation</a> for more information and tutorials.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Features</h2><a id="user-content-features" class="anchor" aria-label="Permalink: Features" href="#features"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li>Read, organize, and process NetCDF files</li>
<li>Visualize heatmaps and 1D profiles with <code>Makie</code></li>
<li>Visualize heatmaps on a globe with <code>GeoMakie</code></li>
<li>Apply averages and other reductions to the output variables</li>
<li>Slice variables along a given value (e.g., take the slice with altitude of 500 meters)</li>
<li>Window variables within given ranges (e.g., select times between 10 and 100 days)</li>
<li>Perform mathematical operations between output variables</li>
<li>Extract dimensions from conventional names (e.g., <code>times</code>)</li>
<li>Interpolate output variables onto arbitrary points</li>
<li>Reinterpolate output variables onto pressure levels</li>
</ul>

<p dir="auto">We prioritize well-tested code to guarantee <code>ClimaAnalysis.jl</code> functions

<p dir="auto">This means that all the tests can be run with <code>Pkg.test()</code>.</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">There are no checked <code>Manifest.toml</code> files</h4><a id="user-content-there-are-no-checked-manifesttoml-files" class="anchor" aria-label="Permalink: There are no checked Manifest.toml files" href="#there-are-no-checked-manifesttoml-files"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">While checking in <code>Manifest.toml</code> files ensures reproducibility, it also
introduces some nuisance, including:</p>
<ul dir="auto">
<li>lot of git/repository noise just for "up deps";</li>
<li>multiple environments that have to be managed;</li>
<li>busywork to keep the manifests updated.</li>
</ul>
<p dir="auto">In this repository, we have two environments:</p>
<ul dir="auto">
<li>project,</li>
<li>documentation.</li>
</ul>
<p dir="auto">The project environment defines the test dependencies in its <code>extras</code> (to reduce
the number of environments and to avoid the "cannot merge projects" problem).</p>

<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Running tests</h4><a id="user-content-running-tests" class="anchor" aria-label="Permalink: Running tests" href="#running-tests"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>ClimaAnalysis.jl</code> defines the test dependencies directly in the main
<code>Project.toml</code>. This means that the package can be tested simply by running <code>] test</code> in a Julia REPL, as shown below:</p>
<p dir="auto">Start a Julia session in the <code>ClimaAnalysis</code> directory:</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia --project"><pre>julia --project</pre></div>
<p dir="auto">Enter <code>Pkg</code> mode by typing <code>]</code>. This will change the prompt. Run <code>test</code>.</p>
<p dir="auto">When doing so, <code>Julia</code> will start a new temporary environment where the tests
are run in isolation. Tests are running checking for in-bounds and for
deprecations, and this can result in code invalidation and new precompilation.</p>
<p dir="auto">Note, the project environment does not contain the test dependencies. Therefore,
you will find that some dependencies are missing if you try "manually" run the
test in a REPL. To solve this problem, use
<a href="https://github.com/JuliaTesting/TestEnv.jl">TestEnv</a>. Install <code>TestEnv</code> in your
base environment (<code>julia -e 'using Pkg; Pkg.add("TestEnv")'</code>). Then, when you
want to use the test dependencies, activate it from your REPL with <code>using TestEnv; TestEnv.activate()</code>. This will bump you to an environment where the
test dependencies are available.</p>
<blockquote>
<p dir="auto">:note: Please, open an issue if you find workflow problems/friction with this
system.</p>
</blockquote>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Code Formatting with <code>JuliaFormatter.jl</code></h4><a id="user-content-code-formatting-with-juliaformatterjl" class="anchor" aria-label="Permalink: Code Formatting with JuliaFormatter.jl" href="#code-formatting-with-juliaformatterjl"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">One of the tests consists in checking that the code is uniformly formatted. We
use <a href="https://github.com/domluna/JuliaFormatter.jl">JuliaFormatter.jl</a> to achieve
consistent formatting. Here's how to use it:</p>
<p dir="auto">You can either install in your base environment with</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia -e 'using Pkg; Pkg.add(&quot;JuliaFormatter&quot;)'"><pre>julia -e <span class="pl-s"><span class="pl-pds">'</span>using Pkg; Pkg.add("JuliaFormatter")<span class="pl-pds">'</span></span></pre></div>
<p dir="auto">or use it from within the <code>TestEnv</code> (or base) environments (see previous section).</p>
<p dir="auto">Then, you can format the package running:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using JuliaFormatter; format(&quot;.&quot;)"><pre><span class="pl-k">using</span> JuliaFormatter; <span class="pl-c1">format</span>(<span class="pl-s"><span class="pl-pds">"</span>.<span class="pl-pds">"</span></span>)</pre></div>
<p dir="auto">or just with <code>format(".")</code> if the package is already imported.</p>
<p dir="auto">The rules for formatting are defined in the <code>.JuliaFormatter.toml</code>.</p>
<p dir="auto">If you are used to formatting from the command line instead of the REPL, you can
install <code>JuliaFormatter</code> in your base environment and call</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia -e 'using JuliaFormatter; format(&quot;.&quot;)'"><pre>julia -e <span class="pl-s"><span class="pl-pds">'</span>using JuliaFormatter; format(".")<span class="pl-pds">'</span></span></pre></div>
<p dir="auto">You could also define a shell alias</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="alias julia_format_here=&quot;julia -e 'using JuliaFormatter; format(\&quot;.\&quot;)'&quot;"><pre><span class="pl-c1">alias</span> julia_format_here=<span class="pl-s"><span class="pl-pds">"</span>julia -e 'using JuliaFormatter; format(<span class="pl-cce">\"</span>.<span class="pl-cce">\"</span>)'<span class="pl-pds">"</span></span></pre></div>

<p dir="auto">Here's how to structure your contributions effectively:</p>
<ul dir="auto">
<li>Descriptive Title: Briefly summarize the changes your PR introduces. Commit
titles should preferably be under 50 characters, start with a capital latter,
and use imperative verbs (e.g., "Remove superfluous function call").</li>
<li>Detailed Description: Explain the purpose of your changes. Focus on the
intent.</li>
<li>Breaking Changes: If your PR introduces breaking changes, highlight them
clearly in the description.</li>
</ul>
<p dir="auto">Your pull request can contain one or multiple commits. In either cases, it is
important that each commit is atomic (meaning that each commit represents a
single logical change).</p>
<p dir="auto">Please, squash commits that represent a single logical change (e.g., do not have
two commits when the second just fixes the first).</p>
<p dir="auto">Pull requests are not merged, but <em>rebased</em>, ensuring a linear history (this is
handled automatically by GitHub).</p>
