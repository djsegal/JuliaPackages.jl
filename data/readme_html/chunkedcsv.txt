<p dir="auto">The main goal of this package is to offer a parser for CSV files that can be used for streaming purposes.
This means that it can work with data that is too large to fit into memory or in situations where we only need to process parts of the input data at a time.
The parser reads the data in chunks, and it can parse each chunk in parallel while simultaneously prefetching the next one to increase throughput.
Additionally, the parsed data is passed to a user-defined function that can consume it in any way required.</p>
<p dir="auto">Moreover, the package can automatically handle <a href="https://github.com/JuliaData/Parsers.jl"><code>Parsers.jl</code></a>-compatible types without dynamic dispatch overhead and with a low compilation overhead.
This is done without specializing on input schema, and the memory usage is upper bound by the user, who can control the chunk size.
All internally allocated buffers are reused, so if the number of values per MiB of input is roughly constant, allocations should be minimal.</p>

<p dir="auto">The package builds on <a href="https://github.com/JuliaData/ChunkedBase.jl"><code>ChunkedBase.jl</code></a>, which provides a framework for parser packages, enabling them to customize three main aspects of the parsing process: how the data is parsed into a result buffer, what is the layout of the result buffer, and how the result buffer is consumed. <code>ChunkedBase.jl</code> itself handles IO, splitting chunks by newlines and distributing them among multiple workers in parallel, where they are parsed by this package and consumed.</p>
<p dir="auto">For the parsing part, this package uses the <code>Parsers.jl</code> package, and special care is taken to avoid dynamic dispatch overhead when parsing user-provided schemas without specializing on them.
See the <code>src/populate_result_buffer.jl</code> file for more details about how this is done.</p>
<p dir="auto">We currently only expose one result buffer type, <code>TaskResultBuffer</code>, where parsed data are stored by column and missing values are encoded in a densely packed bit matrix.
We also store a <code>RowStatus</code> bitset for each row, so we know if a row had any parsing errors or missing values.
See the <code>src/result_buffer.jl</code> file for more details.</p>
<p dir="auto">How the result buffer is consumed is up to the user, who can provide custom callback function that will be called in parallel for each chunk of data that is parsed. More on this in the "How to use" section below.</p>

<p dir="auto">The main entry point is the <code>parse_file</code> function, which accepts a path or an <code>IO</code> as the input, a <code>schema</code> which describes the types of the columns in the CSV, and a user-defined "consume context" type.</p>
<p dir="auto">Once the user provides this context, a subtype of <code>AbstractConsumeContext</code>, it will be used internally to dispatch on a custom <code>consume!(::AbstractConsumeContext,::ParsedPayload)</code> method.
This method will be called in parallel for each chunk of data that is parsed, and it will receive a <code>ParsedPayload</code> object that contains the parsed result buffer in the <code>results</code> field and other relevant metadata for the corresponding chunk.</p>
<p dir="auto">When no schema is provided, all columns are assumed to be <code>String</code>s and when no consume context is given, the <code>DebugContext</code> will be used.
This context will print a short summary for each chunk and will also print the first couple of rows with errors in each chunk.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Notable differences to other CSV parsers</h2><a id="user-content-notable-differences-to-other-csv-parsers" class="anchor" aria-label="Permalink: Notable differences to other CSV parsers" href="#notable-differences-to-other-csv-parsers"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">When compared to established packages like <a href="https://github.com/JuliaData/CSV.jl"><code>CSV.jl</code></a>, our package has a few notable differences:</p>
<ul dir="auto">
<li>We don't do any type inference for column types, so the user has to provide a schema. Otherwise, all columns will be parsed as <code>String</code>s.</li>
<li>We don't give the user back any table-like object. Instead all, results are only temporarily available in the <code>consume!</code> method of the <code>AbstractConsumeContext</code> provided. One could use this package to build a table-like object inside of the context object, but this is not provided out out of the box.</li>
<li>We pre-lex the chunks of data so that parallel parsing can be safe. <code>CSV.jl</code> does the often faster and riskier thing, where parser tasks jump directly in the file at various offsets, without knowing the record boundaries, and try to recover.</li>
<li>At the time of writing, <code>CSV.jl</code> doesn't support multithreaded parsing of <em>chunks</em>, while we do.</li>
<li>The package plays nicely with <code>PrefetchedDownloadStream.jl</code> from <a href="https://github.com/JuliaServices/CloudStore.jl"><code>CloudStore.jl</code></a>, which is an IO stream that prefetches chunks of data from Amazon S3/Azure Blob Storage. This is useful for parsing large files from the cloud without having to download the whole file first, even if it is compressed.</li>
</ul>

<p dir="auto">Sometimes, one needs to know the schema that will used to parse the file before creating a consume context. For this reason we split the <code>parse_file</code> function into two parts.
First, we provide a <code>setup_parser</code> function which has similar interface as <code>parse_file</code> above, but doesn't require any consume context and doesn't do any parsing.
It will validate user input, ingest enough data chunks to reach the first valid row in the input, and then examine the first row to ensure we have a valid header and schema.
It will then return multiple objects:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="(should_close, parsing_ctx, chunking_ctx, lexer) = setup_parser(input, schema; kwargs...)"><pre>(should_close, parsing_ctx, chunking_ctx, lexer) <span class="pl-k">=</span> <span class="pl-c1">setup_parser</span>(input, schema; kwargs<span class="pl-k">...</span>)</pre></div>
<ul dir="auto">
<li><code>should_close</code> is a <code>Bool</code> which is <code>true</code> if we opened an <code>IO</code> object we need to close later</li>
<li><code>parsing_ctx</code> is a <code>ChunkedCSV.ParsingContext</code> which contains the header, schema, and settings needed for <code>Parsers.jl</code></li>
<li><code>chunking_ctx</code> is a <code>ChunkedBase.ChunkingContext</code> which holds the ingested data, newline positions and other things required by <code>ChunkedBase.jl</code> internally</li>
<li><code>lexer</code> is a <code>NewlineLexers.Lexer</code> which is used to find newlines in the ingested chunks and which is also needed by <code>ChunkedBase.jl</code></li>
</ul>
<p dir="auto">Since the parsing context contains both the schema and the header, you can use this information to create a custom consume context.
Once you have your <code>consume_ctx</code>, you can call <code>parse_file</code> with the state returned by <code>setup_parser</code>.</p>
