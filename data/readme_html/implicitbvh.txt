<p dir="auto"><em>High-Performance Parallel Bounding Volume Hierarchy for Collision Detection</em></p>
<p dir="auto">It uses an implicit bounding volume hierarchy constructed from an iterable of some geometric
primitives' (e.g. triangles in a mesh) bounding volumes forming the <code>ImplicitTree</code> leaves. The leaves
and merged nodes above them can have different types - e.g. <code>BSphere{Float64}</code> leaves merged into
larger <code>BBox{Float64}</code>.</p>
<p dir="auto">The initial geometric primitives are sorted according to their Morton-encoded coordinates; the
unsigned integer type used for the Morton encoding can be chosen between <code>UInt16</code>, <code>UInt32</code> and <code>UInt64</code>.</p>
<p dir="auto">Finally, the tree can be incompletely-built up to a given <code>built_level</code> and later start contact
detection downwards from this level.</p>

<p dir="auto">The main idea behind the ImplicitBVH is the use of an implicit perfect binary tree constructed from some
bounding volumes. If we had, say, 5 objects to construct the BVH from, it would form an incomplete
binary tree as below:</p>

<p dir="auto">We do not need to store the "virtual" nodes in memory; rather, we can compute the number of virtual
nodes we need to skip to get to a given node index, following the fantastic ideas from [1].</p>
<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Performance</h1><a id="user-content-performance" class="anchor" aria-label="Permalink: Performance" href="#performance"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">As contact detection is one of the most computationally-intensive parts of physical simulation and computer
vision applications, this implementation has been optimised for maximum performance and scalability:</p>
<ul dir="auto">
<li>Computing bounding volumes is optimised for triangles, e.g. constructing 249,882 <code>BSphere{Float64}</code> on a single thread takes 4.47 ms on my Mac M1. The construction itself has zero allocations; all computation can be done in parallel in user code.</li>
<li>Building a complete bounding volume hierarchy from the 249,882 triangles of <a href="https://github.com/alecjacobson/common-3d-test-models/blob/master/data/xyzrgb_dragon.obj"><code>xyzrgb_dragon.obj</code></a> takes 11.83 ms single-threaded. The sorting step is the bottleneck, so multi-threading the Morton encoding and BVH up-building does not significantly improve the runtime; waiting on a multi-threaded sorter.</li>
<li>Traversing the same 249,882 <code>BSphere{Float64}</code> for the triangles (aggregated into <code>BBox{Float64}</code> parents) takes 136.38 ms single-threaded and 43.16 ms with 4 threads, at 79% strong scaling.</li>
</ul>
<p dir="auto">Only fundamental Julia types are used - e.g. <code>struct</code>, <code>Tuple</code>, <code>UInt</code>, <code>Float64</code> - which can be straightforwardly inlined, unrolled and fused by the compiler. These types are also straightforward to transpile to accelerators via <a href="https://github.com/JuliaGPU/KernelAbstractions.jl"><code>KernelAbstractions.jl</code></a> such as <code>CUDA</code>, <code>AMDGPU</code>, <code>oneAPI</code>, <code>Apple Metal</code>.</p>
