<p dir="auto">Computational problems can often be represented as specific types of graphs known as <a href="https://en.wikipedia.org/wiki/Directed_acyclic_graph" rel="nofollow">directed acyclic graphs (DAGs)</a>. That allows an execution framework to execute parts in right order, schedule in parallel, and make optimal use of available resources.</p>
<p dir="auto">DagScheduler.jl is a package that can execute DAGs in parallel across multiple machines. <a href="https://github.com/JuliaParallel/Dagger.jl">Dagger</a> is another such executor for DAGs in Julia. DagScheduler uses the same underlying DAG representation of Dagger. And it is designed to be used in place of the the default scheduler of Dagger;  scheduler logic in Dagger can be replaced/plugged in.</p>
<p dir="auto">DagScheduler attempts to do better on the following goals:</p>
<ul dir="auto">
<li>scalability
<ul dir="auto">
<li>scheduling load is distributed</li>
<li>data locality (and locality of intermediate results) is taken into account</li>
<li>coarse grained (sub-tree level) scheduling at master</li>
<li>per node (task level) scheduling by brokers</li>
</ul>
</li>
<li>asynchronicity
<ul dir="auto">
<li>data transfer does not block computation</li>
<li>inter-node io is offloaded to brokers</li>
<li>inter-process (within a node) io is via memory mapped files / shared memory</li>
</ul>
</li>
<li>resilience against node / process failures
<ul dir="auto">
<li>external metadata stores provide resilient storage for state and results</li>
<li>master detects failures and re-schedules tasks assigned to failed nodes</li>
</ul>
</li>
</ul>

<p dir="auto">Sets up the execution environment. Parameters (optional):</p>
<ul dir="auto">
<li><code>rootpath</code>: A path used to identify (and isolate) execution environments. This path is used as prefix in metadata stores, and to create several OS level handles. It is good to pass a path with user id or process id suffixed.</li>
<li><code>masterid</code>: The master process. Always <code>myid()</code> as of now.</li>
<li><code>nodes</code>: A list of node environments. Each node identifies a group of processes local to one physical node. Auto-detected by default.</li>
<li><code>debug</code>: Pass <code>true</code> to switch on debugging and verbose logging.</li>
<li><code>profile</code>: Pass <code>true</code> to switch on profiling. Profile outputs are written to <code>/tmp/&lt;pid&gt;.log</code> after every invocation of <code>rundag</code>.</li>
<li><code>remotetrack</code>: Pass <code>true</code> to send remote tracking events to a <a href="https://github.com/tanmaykm/RemoteMonitor.jl">RemoteMonitor.jl</a> listener.</li>
</ul>

<p dir="auto">Reset the execution environment to take into account any worker processes added or removed.</p>
<p dir="auto">Nodes can be added or removed dynamically based on processing requirements.</p>
<p dir="auto">If case of any errors while executing a DAG through <code>rundag</code>, DagScheduler attempts to automatically recover by removing the erring process / node from the execution environment and re-scheduling failed computation to other nodes. The calling program can examine the state after <code>rundag</code> returns and can choose to add new processes to replenish lost capacity.</p>

<p dir="auto">There are a few configurable settings for DagScheduler, to configure the metadata store. The defaults are almost always fine, but some may need customization when running a large setup. The settings are kept in a dictionary <code>DagScheduler.META_IMPL</code> and must be set on all nodes before creating an instance of <code>RunEnv</code>. Settings must not be changed once set.</p>
<p dir="auto">E.g.:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="addprocs(20)

    DagScheduler.META_IMPL[:map_entry_sz] = 1512
end

using Dagger,DagScheduler

@everywhere begin
    DagScheduler.META_IMPL[:map_num_entries] = 1024*100
    DagScheduler.META_IMPL[:map_entry_sz] = 1512
end

runenv = DagScheduler.Plugin.setrunenv(RunEnv())
</code></pre></div>
<p dir="auto">Configurable items:</p>
<ul dir="auto">
<li><code>:map_num_entries</code>: Max number of dag node results that can be stored. A result needs to be stored when it is needed across processes. Default: <code>1024*5</code></li>
<li><code>:map_entry_sz</code>: Max size (bytes) of each result stored in shared dict. Results are typically chunks saved to memory mapped files. Default: <code>256</code></li>
<li><code>:done_tasks_sz</code>: Size of shared memory segment used to keep track of completed task ids on each node. Roughly: (total_dag_nodes / nphyiscal_nodes). Default: <code>1024*100</code></li>
<li><code>:shared_tasks_sz</code>: Size of shared memory segment used to keep track of tasks shared across processes on each node. Roughly: (total_dag_nodes / nphyiscal nodes). Default: <code>1024*100</code></li>
<li><code>:node</code>: The metadata store to use among processes within a node. Default: <code>"DagScheduler.ShmemMeta.ShmemExecutorMeta"</code></li>
<li><code>:cluster</code>: The metadata store to use among nodes (brokers). Default: <code>"DagScheduler.SimpleMeta.SimpleExecutorMeta"</code></li>
</ul>
