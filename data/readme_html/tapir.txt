<p dir="auto">The goal of the <code>Tapir.jl</code> project is to produce a reverse-mode AD package which is written entirely in Julia, which improves over both <code>ReverseDiff.jl</code> and <code>Zygote.jl</code> in several ways, and is competitive with <code>Enzyme.jl</code>.</p>

<p dir="auto">There are several ways to interact with Tapir.jl.
The one that we recommend people begin with is <a href="https://github.com/gdalle/DifferentiationInterface.jl/">DifferentiationInterface.jl</a>. For example, use it as follows to compute the gradient of a function mapping a <code>Vector{Float64}</code> to <code>Float64</code>.</p>

<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">How it works</h1><a id="user-content-how-it-works" class="anchor" aria-label="Permalink: How it works" href="#how-it-works"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>Tapir.jl</code> is based around a function <code>rrule!!</code> (which computes vector-Jacobian products (VJPs)) and a related function, <code>build_rrule</code> (which builds functions semantically identical to <code>rrule!!</code>).
These VJPs can, for example, be used to compute gradients.
<code>rrule!!</code> is similar to ChainRules' <code>rrule</code> and Zygote's <code>_pullback</code>, but supports functions which mutate (modify) their arguments, in addition to those that do not, and immediately increments (co)tangents.
It has, perhaps unsurprisingly, wound up looking quite similar to the rule system in Enzyme.</p>
<p dir="auto">For a given function and arguments, it is roughly speaking the case that either</p>
<ol dir="auto">
<li>a hand-written method of <code>rrule!!</code> is applicable, or</li>
<li>no hand-written method of <code>rrule!!</code> is applicable.</li>
</ol>
<p dir="auto">In the first case, we run the <code>rrule!!</code>.
In the second, we use <code>build_rrule</code> to create a function with the same semantics as <code>rrule!!</code> by "doing AD" -- we decompose the function into a composition of functions which <em>do</em> have hand-written <code>rrule!!</code>s.
In general, the goal is to write as few hand-written <code>rrule!!</code>s as is necessary, and to "do AD" for the vast majority of functions.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Coverage of more of the Language</h3><a id="user-content-coverage-of-more-of-the-language" class="anchor" aria-label="Permalink: Coverage of more of the Language" href="#coverage-of-more-of-the-language"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The need for first-class support for mutation has been well understood in the Julia AD community for a number of years now.
Its primary benefit is the ability to differentiate through the truly vast quantity of mutating code on which users depend in <code>Base</code> / <code>Core</code>, the standard libraries, and packages in the general registry -- empowering users to AD through code which <em>they</em> write in a mutating way is often of secondary importance.
Thus you should equate <code>rrule!!</code>'s support for mutation with good support for existing code.
Conversely, you should equate <code>Zygote.jl</code>'s / <code>ReverseDiff.jl</code>'s patchy support for mutation with patchy support for existing code.</p>
<p dir="auto"><code>rrule!!</code>s impose no constraints on the types which can be operated on, as with <code>ChainRules</code>'s <code>rrule</code> and <code>Zygote</code>'s <code>_pullback</code>.
Consequently, there is in principle nothing to prevent <code>Tapir.jl</code> from operating on any type, for example, structured arrays, GPU arrays, and complicated <code>struct</code>s / <code>mutable struct</code>s.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Correctness and Testing</h3><a id="user-content-correctness-and-testing" class="anchor" aria-label="Permalink: Correctness and Testing" href="#correctness-and-testing"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Mutation support enables writing <code>rrule!!</code>s at a low-level (<code>Core.InstrincFunction</code>s, <code>built-in function</code>s, <code>ccall</code>s to e.g. <code>BLAS</code> and <code>LAPACK</code> and the bits of Base Julia which are implemented in C).
The simplicity of this low-level functionality makes implementing correct <code>rrule!!</code>s for it a simple task.
In conjunction with being strict about the types used internally to represent (co)tangents, we have found this leads to <code>rrule!!</code>s composing very well, and AD being correct in practice as a consequence.</p>
<p dir="auto">Furthermore, the interfaces for <code>rrule!!</code> and the (co)tangent type system have been designed to make a reliable <code>test_rule</code> function possible to create.
All of our testing is implemented via this (or via another function which calls this) which makes adding test-cases trivial, and has meant that we have produced a lot of test cases.</p>
<p dir="auto">This contrasts with <code>Zygote.jl</code> / <code>ChainRules.jl</code>, where the permissive (co)tangent type system complicates both composition of <code>rrule</code>s and testing.</p>
<p dir="auto">Additionally, our approach to AD naturally handles control flow which differs between multiple calls to the same function.
This contrasts with e.g. <code>ReverseDiff.jl</code>'s compiled tape, which can give silent numerical errors if control flow ought to differ between gradient evaluations at different arguments.
<del>Additionally, we augment the tape that we construct with additional instructions which throw an error if control flow differs from when the tape was constructed.</del>
<del>This contrasts with <code>ReverseDiff.jl</code>, which silently fails in this scenario.</del></p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Performance</h3><a id="user-content-performance" class="anchor" aria-label="Permalink: Performance" href="#performance"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Hand-written <code>rrule!!</code>s have excellent performance, provided that they have been written well (most of the hand-written rules in <code>Tapir.jl</code> have excellent performance, but some require optimisation. Doing this just requires investing some time).
Consequently, whether or not the overall AD system has good performance is largely a question of how much overhead is associated to the mechanism by which hand-written <code>rrules!!</code>s are algorithmically composed.</p>
<p dir="auto"><del>At present (11/2023), we do <em>not</em> do this in a performant way, but this will change.</del>
<del>At present (01/2024), we do this in a <em>moderately</em> performant way.</del>
At present (03/2024), we do this in a <em>moderately</em> performant way (but better than the previous way!)
See <a href="#project-status">Project Status</a> below for more info.</p>
<p dir="auto">Additionally, the strategy of immediately incrementing (co)tangents resolves long-standing performance issues associated with indexing arrays.</p>

<p dir="auto"><code>Tapir.jl</code> is written entirely in Julia.
This sits in contrast to <code>Enzyme.jl</code>, which targets LLVM and is primarily written in C++.
These two approaches entail different tradeoffs.</p>

<p dir="auto">Before an initial release, this package was called <code>Taped.jl</code>, but that name ceased to be helpful when we stopped using a classic "Wengert list"-style type to implement AD.
For about 48 hours is was called <code>Phi.jl</code>, but the community guidelines state that the name of packages in the general registry should generally be at least 5 characters in length.</p>
<p dir="auto">Disambiguation: when choosing the name <code>Tapir.jl</code> we were only vaguely aware of other work <a href="https://github.com/wsmoses/Tapir-LLVM">of the same name</a>, and didn't feel that it presented a serious name clash as it isn't AD-specific or a Julia project.
As it turns out, there has been significant work attempting to integrate the ideas from this work into the <a href="https://github.com/JuliaLang/julia/pull/39773" data-hovercard-type="pull_request" data-hovercard-url="/JuliaLang/julia/pull/39773/hovercard">Julia compiler</a>, so it is possible that this package name <em>may</em> change again at <em>some</em> point in the future.</p>

<p dir="auto">The plan is to proceed in three phases:</p>
<ol dir="auto">
<li>design, correctness and testing</li>
<li>performance optimisation</li>
<li>maintenance</li>
</ol>
<p dir="auto">You should take this with a pinch of salt, as it seems highly likely that we will have to revisit some design choices when optimising performance -- we do not, however, anticipate requiring major re-writes to the design as part of performance optimisation.
We aim to reach the maintenance phase of the project before 01/06/2024.</p>
<p dir="auto"><em>Update: (30/04/2024)</em>
Phase 2 continues!
We are now finding that <code>Tapir.jl</code> comfortably outperforms compiled <code>ReverseDiff.jl</code> on type-stable code in all of the situations we have tested.
Optimising to get similar performance to <code>Enzyme.jl</code> is an on-going process.</p>
<p dir="auto"><em>Update: (22/03/2024)</em>
<del>Phase 2 is now further along.</del>
<del><code>Tapir.jl</code> now uses something which could reasonably be described as a source-to-source system to perform AD.</del>
<del>At present the performance of this system is not as good as that of Enzyme, but often beats compiled ReverseDiff, and comfortably beats Zygote in any situations involving dynamic control flow.</del>
<del>The present focus is on dealing with some remaining performance limitations that should make <code>Tapir.jl</code>'s performance much closer to that of Enzyme, and consistently beat ReverseDiff on a range of benchmarks.</del>
<del>Fortunately, dealing with these performance limitations necessitates simplifying the internals substantially.</del></p>
<p dir="auto"><em>Update: (16/01/2024)</em>
<del>Phase 2 is now well underway. We now make use of a much faster approach to interpreting / executing Julia code, which yields performance that is comparable with ReverseDiff (when things go well). The current focus is on ironing out performance issues, and simplifying the implementation.</del></p>
<p dir="auto"><em>Update: (06/11/2023)</em>
<del>We are mostly through the first phase.</del>
<del>Correctness testing is proceeding well, and we are ironing out known issues.</del>
<del>Notably, our broad experience at present is that as we continue to increase the amount of Julia code on which the package is tested, things fail for known, predictable, straightforwardly-fixable reasons (largely missing rrules for <code>ccall</code>s), rather than unanticipated problems.</del></p>
<p dir="auto"><del>Please note that, since we have yet to enter phase 2 of the project, we have spent <em>no</em> time whatsoever optimising for performance.</del>
<del>We strongly believe that there is nothing in principle preventing us from achieving excellent performance.</del>
<del>However, currently, you should expect to experience <em>amazingly</em> poor performance.</del></p>

<p dir="auto">Noteworthy things which should work and be performant include:</p>
<ol dir="auto">
<li>code containing control flow</li>
<li>value-dependent control flow</li>
<li>mutation of arrays and mutable structs</li>
</ol>
<p dir="auto">These are noteworthy in the sense that they are different from ReverseDiff / Zygote.
Enzyme is also able to do these things.</p>
<p dir="auto">Please be aware that by "performant" we mean similar or better performance than ReverseDiff with a compiled tape, but not as good performance as Enzyme.</p>

<p dir="auto">While <code>Tapir.jl</code> should now work on a very large subset of the language, there remain things that you should expect not to work. A non-exhaustive list of things to bear in mind includes:</p>
<ol dir="auto">
<li>It is always necessary to produce hand-written rules for <code>ccall</code>s (and, more generally, foreigncall nodes). We have rules for many <code>ccall</code>s, but not all. If you encounter a foreigncall without a hand-written rule, you should get an informative error message which tells you what is going on and how to deal with it.</li>
<li>Builtins which require rules. The vast majority of them have rules now, but some don't. <del>Notably, <code>apply_iterate</code> does not have a rule, so <code>Tapir.jl</code> cannot currently AD through type-unstable splatting -- someone should resolve this.</del> <code>Core._apply_iterate</code> should now work correctly.</li>
<li>Anything involving tasks / threading -- we have no thread safety guarantees and, at the time of writing, I'm not entirely sure what error you will find if you attempt to AD through code which uses Julia's task / thread system. The same applies to distributed computing. These limitations ought to be possible to resolve.</li>
</ol>
