<p dir="auto">This package implements <code>MemoryView</code>, a simple, low-level view into a chunk of <code>Memory</code>, as well as the <code>MemoryKind</code> trait to guide dispatch of generic methods to memory views.
It is intended to be used as a foundational base for other packages.</p>
<p dir="auto">To learn how to use the package, <a href="https://biojulia.github.io/MemoryViews.jl/dev/" rel="nofollow">read the documentation</a></p>

<ul dir="auto">
<li>
<p dir="auto">Many optimised fast methods for more established types like <code>Vector</code> are missing for <code>MemoryView</code>.
These are added over time. Please make an issue or a PR as you encounter missing methods.</p>
</li>
<li>
<p dir="auto">Currently, <code>MemoryView</code> does not make use of <code>Core.GenericMemory</code>'s additional parameters, such as atomicity or address space.
This may easily be added with a <code>GenericMemoryView</code> type, similar to <code>Memory</code> / <code>GenericMemory</code>.</p>
</li>
<li>
<p dir="auto">I can't figure out how to support reinterpreted arrays.
Any way I can think of doing so will sigificantly complicate <code>MemoryView</code>, which takes away some of
the appeal of this type's simplicity.
It's possible that reinterpreted arrays are so outside Julia's ordinary memory management
that this simply can't be done.</p>
</li>
<li>
<p dir="auto">Currently, <code>String</code>s are not backed by <code>Memory</code> in Julia. Therefore, creating a <code>MemoryView</code> of a string
requires heap-allocating a new <code>Memory</code> pointing to the existing memory of the string.
This can be fixed if <code>String</code> is re-implemented to be backed by <code>Memory</code>, but I don't know
enough details about the implementation of <code>String</code> to know if this is practical.</p>
</li>
</ul>
