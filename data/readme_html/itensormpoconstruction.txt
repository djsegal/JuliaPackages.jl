<p dir="auto">A fast algorithm for constructing a Matrix Product Operator (MPO) from a sum of local operators. This is a replacement for <code>MPO(os::OpSum, sites::Vector{&lt;:Index})</code>. In all cases examined so far this algorithm constructs an MPO with a smaller (or equal) bond dimension faster than the competition. All runtimes below are taken from a single sample on a 2021 MacBook Pro with the M1 Max CPU and 32GB of memory.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Constraints</h2><a id="user-content-constraints" class="anchor" aria-label="Permalink: Constraints" href="#constraints"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This algorithm shares the same constraints as ITensors' default algorithm.</p>
<ol dir="auto">
<li>The operator must be expressed as a sum of products of single site operators. For example a CNOT could not appear in the sum since it is a two site operator.</li>
<li>When dealing with Fermionic systems the parity of each term in the sum must be even. That is the combined number of creation and annihilation operators in each term in the sum must be even.</li>
</ol>
<p dir="auto">There are also two additional constraints:</p>
<ol start="3" dir="auto">
<li>Each term in the sum of products representation can only have a single operator acting on a site. For example a term such as <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$\mathbf{X}^{(1)} \mathbf{X}^{(1)}$</math-renderer> is not allowed. However, there is a pre-processing utility that can automatically replace <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$\mathbf{X}^{(1)} \mathbf{X}^{(1)}$</math-renderer> with <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$\mathbf{I}^{(1)}$</math-renderer>. This is not a hard requirement for the algorithm but a simplification to improve performance.</li>
<li>When constructing a quantum number conserving operator the total flux of the operator must be zero. It would be trivial to remove this constraint.</li>
</ol>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto"><code>MPO_new</code></h2><a id="user-content-mpo_new" class="anchor" aria-label="Permalink: MPO_new" href="#mpo_new"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The main exported function is <code>MPO_new</code> which takes an <code>OpSum</code> and transforms it into a MPO.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="function MPO_new(os::OpSum, sites::Vector{&lt;:Index}; kwargs...)::MPO"><pre><span class="pl-k">function</span> <span class="pl-en">MPO_new</span>(os<span class="pl-k">::</span><span class="pl-c1">OpSum</span>, sites<span class="pl-k">::</span><span class="pl-c1">Vector{&lt;:Index}</span>; kwargs<span class="pl-k">...</span>)<span class="pl-k">::</span><span class="pl-c1">MPO</span></pre></div>
<p dir="auto">The optional keyword arguments are</p>
<ul dir="auto">
<li><code>basis_op_cache_vec</code>: A list of operators to use as a basis for each site. The operators on each site are expressed as one of these basis operators.</li>
<li><code>tol::Real</code>: The tolerance used in the sparse QR decomposition (which is done by SPQR). The default value is the SPQR default which is calculated separately for each QR decomposition. If you want a MPO that is accurate up to floating point errors the default tolerance should work well. If instead you  want to compress the MPO the value <code>tol</code> will differ from the <code>cutoff</code> passed to <code>ITensor.MPO</code> since the truncation method is completely different. If you want to replicate the same truncation behavior first construct the MPO with a suitably small (or default) <code>tol</code> and then use <code>ITensors.truncate!</code>.</li>
</ul>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Examples: Fermi-Hubbard Hamiltonian in Real Space</h2><a id="user-content-examples-fermi-hubbard-hamiltonian-in-real-space" class="anchor" aria-label="Permalink: Examples: Fermi-Hubbard Hamiltonian in Real Space" href="#examples-fermi-hubbard-hamiltonian-in-real-space"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The one dimensional Fermi-Hubbard Hamiltonian with periodic boundary conditions on <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$N$</math-renderer> sites can be expressed in real space as</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$$
\mathcal{H} = -t \sum_{i = 1}^N \sum_{\sigma \in (\uparrow, \downarrow)} \left( c^\dagger_{i, \sigma} c_{i + 1, \sigma} + c^\dagger_{i, \sigma} c_{i - 1, \sigma} \right) + U \sum_{i = 1}^N n_{i, \uparrow} n_{i, \downarrow} \ ,
$$</math-renderer></p>
<p dir="auto">where the periodic boundary conditions enforce that <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$c_k = c_{k + N}$</math-renderer>. For this Hamiltonian all that needs to be done to switch over to using ITensorMPOConstruction is switch <code>MPO(os, sites)</code> to <code>MPO_New(os, sites)</code>.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Examples: Fermi-Hubbard Hamiltonian in Momentum Space</h2><a id="user-content-examples-fermi-hubbard-hamiltonian-in-momentum-space" class="anchor" aria-label="Permalink: Examples: Fermi-Hubbard Hamiltonian in Momentum Space" href="#examples-fermi-hubbard-hamiltonian-in-momentum-space"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The one dimensional Fermi-Hubbard Hamiltonian with periodic boundary conditions on <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$N$</math-renderer> sites can be expressed in momentum space as</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$$
\mathcal{H} = \sum_{k = 1}^N \epsilon(k) \left( n_{k, \downarrow} + n_{k, \uparrow} \right) + \frac{U}{N} \sum_{p, q, k = 1}^N c^\dagger_{p - k, \uparrow} c^\dagger_{q + k, \downarrow} c_{q, \downarrow} c_{p, \uparrow}
$$</math-renderer></p>
<p dir="auto">where <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$\epsilon(k) = -2 t \cos(\frac{2 \pi k}{N})$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$c_k = c_{k + N}$</math-renderer>. The code to construct the <code>OpSum</code> is shown below.</p>

<p dir="auto">Unlike the previous example, some more involved changes will be required to use ITensorMPOConstruction. This is because the <code>OpSum</code> has multiple operators acting on the same site, violating constraint #3. For example when <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$k = 0$</math-renderer> in the second loop we have terms of the form <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$c^\dagger_{p, \uparrow} c^\dagger_{q, \downarrow} c_{q, \downarrow} c_{p, \uparrow}$</math-renderer>. You could always create a special case for <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$k = 0$</math-renderer> and rewrite it as <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$n_{p, \uparrow} n_{q, \downarrow}$</math-renderer>. However if using "Electron" sites then you would also need to consider other cases such as when <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$p = q$</math-renderer>, this would introduce a lot of extraneous complication. Luckily ITensorMPOConstruction provides a method to automatically perform these transformations. If you provide a set of operators for each site to <code>MPO_new</code> it will attempt to express the operators acting on each site as a single one of these "basis" operators. The code to do this is shown below.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>OpIDSum</code></h3><a id="user-content-opidsum" class="anchor" aria-label="Permalink: OpIDSum" href="#opidsum"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">For <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$N = 200$</math-renderer> constructing the <code>OpSum</code> takes 42s and constructing the MPO from the <code>OpSum</code> with ITensorMPOConstruction takes another 306s. For some systems constructing the <code>OpSum</code> can actually be the bottleneck. In these cases you can construct an <code>OpIDSum</code> instead.</p>
<p dir="auto"><code>OpIDSum</code> plays the same roll as <code>OpSum</code> but in a much more efficient manner. To specify an operator in a term of an <code>OpSum</code> you specify a string (the operator's name) and a site index, whereas to specify an operator in a term of an <code>OpIDSum</code> you specify an <code>OpID</code> which contains an operator index and a site. The operator index is the index of the operator in the provided basis for the site.</p>
<p dir="auto">For <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="979d79eafd6d86dfd94ee101c7f4aee1">$N = 200$</math-renderer> constructing an <code>OpIDSum</code> takes only 0.4s. Shown below is code to construct the Hamiltonian using an <code>OpIDSum</code>.</p>
