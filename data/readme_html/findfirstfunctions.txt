over more generic implementations.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>bracketstrictlymontonic</code></h3><a id="user-content-bracketstrictlymontonic" class="anchor" aria-label="Permalink: bracketstrictlymontonic" href="#bracketstrictlymontonic"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="bracketstrictlymontonic(v, x, guess; lt=&lt;comparison&gt;, by=&lt;transform&gt;, rev=false)"><pre><span class="pl-c1">bracketstrictlymontonic</span>(v, x, guess; lt<span class="pl-k">=</span><span class="pl-k">&lt;</span>comparison<span class="pl-k">&gt;</span>, by<span class="pl-k">=</span><span class="pl-k">&lt;</span>transform<span class="pl-k">&gt;</span>, rev<span class="pl-k">=</span><span class="pl-c1">false</span>)</pre></div>
<p dir="auto">Starting from an initial <code>guess</code> index, find indices <code>(lo, hi)</code> such that <code>v[lo] ≤ x ≤ v[hi]</code> according to the specified order, assuming that <code>x</code> is actually within the range of
values found in <code>v</code>.  If <code>x</code> is outside that range, either <code>lo</code> will be <code>firstindex(v)</code> or
<code>hi</code> will be <code>lastindex(v)</code>.</p>
<p dir="auto">Note that the results will not typically satisfy <code>lo ≤ guess ≤ hi</code>.  If <code>x</code> is precisely
equal to a value that is not unique in the input <code>v</code>, there is no guarantee that <code>(lo, hi)</code>
will encompass <em>all</em> indices corresponding to that value.</p>
<p dir="auto">This algorithm is essentially an expanding binary search, which can be used as a precursor
to <code>searchsorted</code> and related functions, which can take <code>lo</code> and <code>hi</code> as arguments.  The
purpose of using this function first would be to accelerate convergence in those functions
by using correlated <code>guess</code>es for repeated calls.  The best <code>guess</code> for the next call of
this function would be the index returned by the previous call to <code>searchsorted</code>.</p>
<p dir="auto">See <code>sort!</code> for an explanation of the keyword arguments <code>by</code>, <code>lt</code> and <code>rev</code>.</p>

<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="searchsortedfirstcorrelated(v::AbstractVector, x, guess)"><pre><span class="pl-c1">searchsortedfirstcorrelated</span>(v<span class="pl-k">::</span><span class="pl-c1">AbstractVector</span>, x, guess)</pre></div>
<p dir="auto">An accelerated <code>findfirst</code> on sorted vectors using a bracketed search. Requires a <code>guess</code>
to start the search from, which is either an integer or an instance of <code>Guesser</code>.</p>
<p dir="auto">An analogous function <code>searchsortedlastcorrelated</code> exists.</p>

<p dir="auto">The branches in a binary search are unpredictable, thus disabling the conversion of <code>cmov</code> into branches results in a substantial performance increase.
Additionally, enablig <code>cmov</code> (i.e., disabling <code>cmov</code> conversion) greatly reduces the optimal base case size for <code>FindFirstFunctions.findfirstsortedequal</code>. Without <code>cmov</code>, we need a very large base case to avoid too many branches, scanning large swaths contiguously.
With <code>cmov</code>, we can reduce the base case size to <code>8</code>, taking several additional binary search steps without incurring heavy branch prediction penalties.</p>
<p dir="auto">However, we default to a large base case size, under the assumptions users are not setting this <code>ENV</code> variable; we assume that an expert user concerned about binary search performance who sets this variable will also be able to choose their own basecase size.</p>
<p dir="auto">Take care when benchmarking <code>JULIA_LLVM_ARGS="-x86-cmov-converter=false"</code>: your CPU's branch predictor can probably memorize a sequence of hundreds of perfectly random branches. Branch predcitors are great at defeating microbenchmarks.
Thus, you need a very long unpredictable sequence (which I tried to do in the above benchmark) to prevent the branch predictor from memorizing it.
In "real world" workloads, your branch predictor isn't going to be able to memorize a sequence of left vs right bisections in your binary search, as you won't be performing the same searches over and over again!
Without making your benchmark realistic, the default setting of converting <code>cmov</code> into branches will look unrealistically good.</p>
<p dir="auto">If you actually are, memoize. If you're looking for close answers, look for something like <code>bracketstrictlymontonic</code>'s <code>guess</code> API.</p>
