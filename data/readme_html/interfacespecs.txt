<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Background</h2><a id="user-content-background" class="anchor" aria-label="Permalink: Background" href="#background"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Recently there's been a lot of interest in attempting to add more static guarantees
or checking to julia as a language. I think this interest is coming from a number
of different angles, but I've heard at least the following:</p>
<ol dir="auto">
<li>
<p dir="auto">Some people would like a more formalized way to document the expectations of
various interfaces that provide extension points. E.g. what exactly does it
mean to be iterable, to be an array, a random number generator, etc.</p>
</li>
<li>
<p dir="auto">Some people would like like better tooling to automatically determine whether
an interface has been implemented correctly or not. E.g. if somebody implements
a custom lattice for the compiler, it would be nice to make sure that it satisfies
the basic interface.</p>
</li>
<li>
<p dir="auto">Some people would like more static guarantees on abstract signatures for optimization
reasons (e.g. to prevent invalidations)</p>
</li>
</ol>
<p dir="auto">I think the solutions to these kinds of things fall in roughly two general categories:</p>
<ol dir="auto">
<li>
<p dir="auto"><em>Semantic</em> Solutions: These are changes to the language semantics, for example
by being able to restrict and check the return types of abstract signatures
and enforce the implementation.</p>
</li>
<li>
<p dir="auto"><em>Non-Semantic</em> Solutions: In this model, interface specifications never <strong>change</strong> the semantics of a program, but interfaces are useful for the developer as documentation and can potentially be checked at test time (or a separate check stage).</p>
</li>
</ol>

<p dir="auto">This package is a playground for my thinking around this topic. I hesitate to even
call it a proposal, because I'm not sure it's going anywhere, but I think there's
some neat ideas that I'd like to explore.</p>
<p dir="auto">The core idea of this package is that I'd like to provide the ability for users
to write down specifications for the interfaces in a natural, but machine-readable
way and then use these specifications to provide a smooth path from property-based
testing of these specifications to a more formal-methods/type-checking based
approach to software verification.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">The intrinsics</h3><a id="user-content-the-intrinsics" class="anchor" aria-label="Permalink: The intrinsics" href="#the-intrinsics"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The rest of this document discussed a number of different interfaces, APIs and tools
that could be built. However, it has come to my attention that it wasn't clear that
these are all intended to be built on the same primitive (just with various variations
of syntax sugar). Therefore, before we go any further, let's talk about the core intrinsics
in this proposal and their semantics. Readers interested primarily in the high-level interface
may skip ahead.</p>
<p dir="auto">The core of this package's design is the addition of two intrinsics, <code>forall</code> and <code>exists</code>.
Both intrinsics are similar in that they operate (semantically) on the abstract space of all
possible julia objects. Of course, there is infinitely many such objects, so these semantics
are not implementable computationally directly, but as discussed below, that does not mean
that an implementation cannot be provided by computing the same semantics in a smarter way.</p>
<p dir="auto">To understand the semantics of these intrinsics, let us supposed we had an interator <code>all_julia_objects()</code>
that (in no particular order) returned all (newly instantiated - see below for notes on mutation)
julia objects (of all possible types currently defined).
Of course this iterator is countably infinite and not implementable (and not part of the proposal),
but it has useful explanatory power.</p>
<p dir="auto">With this assumption, the semantics of <code>forall</code> and <code>exists</code> are roughly:</p>

<p dir="auto">These semantics are very similar, so it's possible we may want to unify them as
one intrinsic in the future, but they serve different purposes, so let's treat
them separately for now.</p>
<p dir="auto">Informally, <code>forall</code> executes some test function <code>f</code> for all julia objects that
match some criteria specified by the projection function <code>π</code>. Similarly, <code>exists</code>
produces some julia object that satiesfies the projection function.</p>
<p dir="auto">Since both the predicate (f) and projection (π) functions are effect-checked, the
primary question is whether a particular predicate or projection will throw an
error for a particular input. This is the basis of the theorem proving capabilities
of these intrinsics.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">A first proof</h3><a id="user-content-a-first-proof" class="anchor" aria-label="Permalink: A first proof" href="#a-first-proof"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">For example, consider</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="forall(Int) do x
    x + x == 2x
end"><pre><span class="pl-c1">forall</span>(Int) <span class="pl-k">do</span> x
    x <span class="pl-k">+</span> x <span class="pl-k">==</span> <span class="pl-c1">2</span>x
<span class="pl-k">end</span></pre></div>
<p dir="auto">If this call (semantically) does not error, we have proven the property true
for all values of type <code>Int</code>. Even though this example looks simple, there are
a number of subtle points that need addressing.</p>
<ol dir="auto">
<li>First, why does <code>Int</code> work as a projection function here? The trivial answer
is that we have a method <code>Int(x::Int) = x</code>. The semantic <code>all_julia_objects</code>,
includes integers, and since that method does not throw, all integers are selected
as the predicate set. Of course, there's more than this method that produces integers,
e.g. we also have <code>Int(x::Float64) = convert(Int, x)</code>, but the only semantically
determinable question is whether an object is in the predicate set, not how many
times it was selected.</li>
</ol>
<p dir="auto">** Pedantic footnoe: (one might object that since we did not check <code>consistent</code>,
running the same predicate function twice might error in one instance and return
in the other - however, consistent-cy is defined with respect to a particular
environment state and the absence of mutation guaranteed by <code>:effect_free</code>,
combined with the non-definedness of the execution order allows us to assume
egal heap states for egal objects). **</p>
<ol start="2" dir="auto">
<li>
<p dir="auto">At this point one might object that this is a very roundabout way of specifying
that the prdicate set is all values of type <code>Int</code>. And indeed, implementations can and should just
look at the type of the projection function and make the appropriate conclusion.
We will see more interesting cases where <code>π</code> is not just a type constructor shortly.
However, in the meantime, this does bring us to one important additional semantic wrinkle: At present,
constructors do not in fact fully constrain the possible julia values of a given type
as values can be constructed indirectly using <code>unsafe_load</code>, <code>reinterpret</code> or <code>eval(Expr(:new))</code>.
To address this, we add a <em>type constructor exception</em> to our semantics, where if the
predicate is a literal type constructor, we extend the predicate set to all values of
that type, independent of whether they are constructable by their constructors or not.
In the future, core julia might gain a concept of sealed types where bypassing the
constructor is disallowed, in which case this exception would of course only apply to
non-sealed types.</p>
</li>
<li>
<p dir="auto">Even though the predicate looks trivial (and it basically is), there is actually a fair
bit going on here. In parcticular, dynamic dispatch needs to be performed as usual,
so this is an assertion not just about the behavior of <code>Int</code> arithmetic, but also about
the dispatches of <code>+</code>, <code>==</code> and implicit multiplication.</p>
</li>
</ol>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Proof checking as compiler optimization</h3><a id="user-content-proof-checking-as-compiler-optimization" class="anchor" aria-label="Permalink: Proof checking as compiler optimization" href="#proof-checking-as-compiler-optimization"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">For the particular example we just look at, implementing a correct version of <code>forall</code>
turns out to be relatively simple. In particular, the regular julia compilation
pipeline is strong enough to fully resolve this question and turn <code>x + x == 2x</code>
into <code>return true</code>. Thus, to implement <code>forall</code>, we can simply run the regular
compilation pipeline, see if the predicate function is <code>return true</code> (or similar)
and then compile <code>forall</code> to a no-op.</p>
<p dir="auto">In fact, this is a general sketch for implementing proof-checkers in this scheme.
The standard julia pipeline is run to ensure the required effects and strip
away julia-specific semantics around multiple-dispatch, etc, providing a
monomorphised version of the code that may then be compiled to any target that
may be capable of performing the proof. In the present example, this was LLVM,
but the pacakge contains experimental bindings to Z3 as well and the intention
is to be as agnostic as possible to the proof backend.</p>
<p dir="auto">The primary benefit of this setup is that it re-uses the entire compiler stack
built for static compilation of Julia. As in the static compilation case, not
all julia code will be suitable for use as predicate and projection functions.
As such, it is important to have tooling that explains to the user what
limitations they need to impose on their functions in order to be able to use
them with this scheme. By sharing this implementation work across use cases,
the burden on tool development can hopefully be minimized.</p>

<li>For all <code>a</code> of type <code>T</code> such that <code>iszero(a)</code> (is true), we require that
a. for all <code>b</code> of type <code>T</code> such that <code>a == b</code>, we have <code>iszero(b)</code> (is true) and
b. for all <code>b</code> of type <code>T</code> such that <code>iszero(b)</code>, we have <code>a == b</code> (is true)</li>
</ol>
<p dir="auto">Or, said equivalently</p>
<ol dir="auto">
<li>For all  <code>a</code>, <code>b</code> of type <code>T</code>, <code>iszero(a)</code> implies (<code>iszero(b)</code> if and only if <code>a == b</code>)</li>
</ol>
<p dir="auto">In particular, this implies that we have no separate representation of implication in this system,
just a particularly general way of typing the inputs to <code>forall</code>. This is of course no ground-breaking
discovery - dependently typed proof systems are built around this kind of observation.
However, as our flavor of the intrinsics is somewhat different, I thought it deserved a specific mention.</p>

<p dir="auto">As described above, the <code>forall</code> function requires <code>:effect_free_if_inaccessiblemem</code> effects,
i.e. the compiler needs to prove that the predicate does not perform any unbounded heap
mutation. However, heap mutation that is bounded to heap objects whose lifetime does not
exceed the duration of the <code>forall</code> body is permitted. This is intended to be a practical
tradeoff that allows predicates that make use of mutation, while still requiring that the
(non)-execution of the <code>forall</code> predicate is not externally observable.</p>

range of the <code>all_julia_objects</code> pseudo-intrinsics discussed above. As mentioned in the side-node,
we consider newly allocated object hierarchies here, not existing julia objects. In particular,
<code>exists</code> will never return a mutable object that aliases an existing mutable object:</p>

<p dir="auto">A long-standing feature request in the julia community has been the addition
of some notion of higher-level specification of interfaces such as abstract
arrays. There's two primary purposes for this kind of systems:</p>
<ol dir="auto">
<li>
<p dir="auto">Implementers of new array types want to know that they have correctly implemented
the array type.</p>
</li>
<li>
<p dir="auto">Users want to know that they are not accidentally relying on implementation details
of a particular <code>AbstractArray</code>, but rather that their code is generic over all <code>AbstractArray</code>s</p>
</li>
</ol>
<p dir="auto">One primary issue that is often brought up with this is that in julia, types are used for dispatch,
not correctness, so the mere existence of a particular method does not guarantee that the method
actually conforms to the interface. For <code>AbstractArray</code>, one such invariant may be that:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="A[i] = x
@assert x == A[i]"><pre>A[i] <span class="pl-k">=</span> x
<span class="pl-c1">@assert</span> x <span class="pl-k">==</span> A[i]</pre></div>
<p dir="auto">The mere existence of <code>getindex</code> and <code>setindex</code> do not assure that the array actually does something
with it, only that no immediate method error will be thrown.</p>
<p dir="auto">Of course, the system we have just presented is perfectly capable of encoding behavioral invariants
in addition to type-based one. However, there are potential robustness challenges. The system just
presented is completely general and it is not completely clear what particular subset of julia
code will be proveable on any particular backend. As a result, the full system may be hard to use
correctly.</p>
<p dir="auto">One natural way out of this connundrum is to create a more restrictive view into the full system
that is sufficiently powerful to specify interfaces of moderate complexity, but yet restricted
enough to have some chance of being checked automatically. By <em>view</em> here, I mean some higher-level
abstraction that provides a restricted version of the capability, but is nevertheless semantically
representable by the same intrinsics and that uses the same top-level entry points as the
full system.</p>
<p dir="auto">This package includes such an abstraction as the <code>Interface</code> spec in the <code>sugar</code> directory.
Let us walk through it as both an example of the usage of the lower level interface and a
description of the high-level interface.</p>
<p dir="auto">First, we must consider what it is that we actually want to prove. There's a few options,
but a reasonable choice is to try to prove that in the cases we're interested in, a method
of the desired signature exists (no MethodErrors get thrown), returns a value of the correct type.
So, let's write such a spec (for a single singature for the time being):</p>

    <span class="pl-c1">forall</span>(ic<span class="pl-k">.</span>iface) <span class="pl-k">do</span> _
        <span class="pl-c1">DoesNotThrow</span>(<span class="pl-c1">CheckSignature</span>(ic<span class="pl-k">.</span>checksig), MethodError)()
    <span class="pl-k">end</span>
<span class="pl-k">end</span></pre></div>
<p dir="auto">To understand why this works, remember from above the correspondence between
projection and implication. In particular, to prove <code>InterfaceCheck</code>, it is
not necessary to prove that the relevant interface holds, only that the
predicate holds if the interface does.</p>
