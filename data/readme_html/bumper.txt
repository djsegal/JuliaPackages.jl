<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Bumper.jl</h1><a id="user-content-bumperjl" class="anchor" aria-label="Permalink: Bumper.jl" href="#bumperjl"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Bumper.jl is a package that aims to make working with bump allocators (also known as arena allocators)
easier and safer. You can dynamically allocate memory to these bump allocators, and reset
them at the end of a code block, just like Julia's stack. Allocating to a bump allocator with Bumper.jl
can be just as efficient as stack allocation. Bumper.jl is still a young package, and may have bugs.
Let me know if you find any.</p>
<p dir="auto">If you use Bumper.jl, please consider submitting a sample of your use-case so I can include it in the test suite.</p>

<p dir="auto">Bumper.jl has a task-local default allocator, using a <em>slab allocation strategy</em> which can dynamically
grow to arbitary sizes.</p>
<p dir="auto">The simplest way to use Bumper is to rely on its default buffer implicitly like so:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using Bumper

function f(x)
    # Set up a scope where memory may be allocated, and does not escape:
    @no_escape begin
        # Allocate a `UnsafeVector{eltype(x)}` (see UnsafeArrays.jl) using memory from the default buffer.
        y = @alloc(eltype(x), length(x))
        # Now do some stuff with that vector:
        y .= x .+ 1
        sum(y) # It's okay for the sum of y to escape the block, but references to y itself must not do so!
    end
end

<p dir="auto">When you use <code>@no_escape</code>, you are promising that the code enclosed in the macro will not leak <strong>any</strong> memory
created by <code>@alloc</code>. That is, you are <em>only</em> allowed to do intermediate <code>@alloc</code> allocations inside a <code>@no_escape</code> block,
and the lifetime of those allocations is the block. <strong>This is important.</strong> Once a <code>@no_escape</code> block finishes running, it
will reset its internal state to the position it had before the block started, potentially overwriting or freeing any
arrays which were created in the block.</p>
<p dir="auto">In addition to <code>@alloc</code> for creating arrays, you can use <code>@alloc_ptr(n)</code> to get an <code>n</code>-byte pointer (of type
<code>Ptr{Nothing}</code>) directly.</p>

<p dir="auto">So, using Bumper.jl in this benchmark gives a slight speedup relative to regular julia <code>Vector</code>s,
and a major increase in performance <em>consistency</em> due to the lack of heap allocations.</p>
<p dir="auto">However, we can actually go a little faster better if we're okay with manually passing around a buffer.
The way I invoked <code>@no_escape</code> and <code>@alloc</code> implicitly used the task's default buffer, and fetching that
default buffer is not as fast as using a <code>const</code> global variable, because Bumper.jl is trying to protect
you against concurrency bugs (more on that later).</p>
<p dir="auto">If we provide the allocator to <code>f</code> explicitly, we go even faster:</p>

<p dir="auto">If you manually specify a buffer like this, it is your responsibility to ensure that you don't have
multiple concurrent tasks using that buffer at the same time.</p>
<p dir="auto">Running <code>default_buffer()</code> will give you the current task's default buffer. You can explicitly construct
your own <code>N</code> byte buffer by calling <code>AllocBuffer(N)</code>, or you can create a buffer which can dynamically
grow by calling <code>SlabBuffer()</code>. <code>AllocBuffer</code>s are <em>slightly</em> faster than <code>SlabBuffer</code>s, but will throw
an error if you overfill them.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Important notes</h2><a id="user-content-important-notes" class="anchor" aria-label="Permalink: Important notes" href="#important-notes"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li><code>@no_escape</code> blocks can be nested as much as you want, just don't let references outlive the specific block they were created in.</li>
<li>At the end of a <code>@no_escape</code> block, all memory allocations from inside that block are erased and the buffer is reset to its previous state</li>
<li>The <code>@alloc</code> marker can only be used directly inside of a <code>@no_escape</code> block, and it will always use the buffer that the
corresponding <code>@no_escape</code> block uses.</li>
<li>You cannot use <code>@alloc</code> from a different concurrent task than its parent <code>@no_escape</code> block as this can cause concurrency bugs.</li>
<li>If for some reason you need to be able to use <code>@alloc</code> outside of the scope of the <code>@no_escape</code> block, there is a
function  =<code>Bumper.alloc!(bug, T, n...)</code>= which takes in an explicit buffer <code>buf</code> and uses it to allocate an array of
element type <code>T</code>, and dimensions <code>n...</code>. Using this is not as safe as <code>@alloc</code> and not recommended.</li>
<li>Bumper.jl only supports <code>isbits</code> types. You cannot use it for allocating vectors containing mutable, abstract, or
other pointer-backed objects.</li>
<li>As mentioned previously, <em>Do not allow any array which was initialized inside a</em> <code>@no_escape</code>
<em>block to escape the block.</em> Doing so will cause incorrect results.</li>
<li>If you accidentally overfill a buffer, via e.g. a memory leak and need to reset the buffer, use
<code>Bumper.reset_buffer!</code> to do this.</li>
<li>You are not allowed to use <code>return</code> or <code>@goto</code> inside a <code>@no_escape</code> block, since this could compromise the cleanup it performs after the block finishes.</li>
</ul>

</p><div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">SlabBuffer</h3><a id="user-content-slabbuffer" class="anchor" aria-label="Permalink: SlabBuffer" href="#slabbuffer"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>SlabBuffer</code> is a slab-based bump allocator which can dynamically grow to hold an arbitrary amount of memory.
Small allocations from a <code>SlabBuffer</code> will live within a specific slab of memory, and if that slab fills up,
a new slab is allocated and future allocations will then happen on that slab. Small allocations are stored
in slabs of size <code>SlabSize</code> bytes (default 1 megabyte), and the list of live slabs are tracked in a field called
<code>slabs</code>. Allocations which are too large to fit into one slab are stored and tracked in a field called
<code>custom_slabs</code>.</p>
<p dir="auto"><code>SlabBuffer</code>s are nearly as fast as stack allocation (typically up to within a couple of nanoseconds) for typical
use. One potential performance pitfall is if that <code>SlabBuffer</code>'s current position is at the end of a slab, then
the next allocation will be slow because it requires a new slab to be created. This means that if you do something
like</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="buf = SlabBuffer{N}()

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Creating your own allocator types</h2><a id="user-content-creating-your-own-allocator-types" class="anchor" aria-label="Permalink: Creating your own allocator types" href="#creating-your-own-allocator-types"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>

<p dir="auto">
</p><p dir="auto">Bumper.jl's <code>SlabBuffer</code> type is very flexible and fast, and so should almost always be preferred, but you
may have specific use-cases where you want to use a different design or make different tradeoffs, but want
to be able to interoperate with Bumper.jl's other features. Hence, Bumper.jl provides an API for you to hook
custom allocator types into it.</p>
<p dir="auto">When someone writes</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@no_escape buf begin

<p dir="auto"><code>checkpoint_save</code> should save the state of <code>buf</code>, <code>alloc!</code> should create an array using memory from <code>buf</code>, and <code>checkpoint_restor!</code> needs to reset <code>buf</code> to the state it was in when the checkpoint was created.</p>
<p dir="auto">Hence, in order to use your custom allocator with Bumper.jl, all you need to write is the following methods:</p>
<ul dir="auto">
<li><code>Bumper.alloc_ptr!(::YourAllocator, n::Int)::Ptr{Nothing}</code> which returns a pointer that can hold up to <code>n</code> bytes, and should be created from memory supplied with your allocator type however you see fit.
<ul dir="auto">
<li>Alternatively, you could implement <code>Bumper.alloc!(::YourAllocator, ::Type{T}, s::Vararg{Integer})</code> which should return a multidimensional array whose sizes are determined by <code>s...</code>, created from memory supplied by your custom allocator. The default implementation of this method calls <code>Bumper.alloc_ptr!</code>.</li>
</ul>
</li>
<li><code>Bumper.checkpoint_save(::YourAllocator)::YourAllocatorCheckpoint</code> which saves whatever information your allocator needs to save in order to later on deallocate all objects which were created after <code>checkpoint_save</code> was called.</li>
<li><code>checkpoint_restore!(::YourAllocatorCheckpoint)</code> which resets the allocator back to the state it was in when the checkpoint was created.</li>
</ul>
