<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Caching Clebsch-Gordan coefficients</h2><a id="user-content-caching-clebsch-gordan-coefficients" class="anchor" aria-label="Permalink: Caching Clebsch-Gordan coefficients" href="#caching-clebsch-gordan-coefficients"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">As computing the Clebsch-Gordan coefficients is a relatively expensive operation, this packages automatically caches the results of the computations. To obtain information about the current status of the cache, one can call <code>SUNRepresentations.cache_info()</code>.</p>
<p dir="auto">Often, it may be useful to precompute a large set of coefficients (in parallel). These can
then be stored on disk and loaded when needed, or even transferred to other machines. This
can be done using the <code>SUNRepresentations.precompute_disk_cache(N, a_max)</code> function, which
will compute all Clebsch-Gordan coefficients for <code>s1 ⊗ s2 -&gt; s3</code>, where <code>s1</code> and <code>s2</code> will
have Dynkin labels smaller than <code>a_max</code>, and <code>s3</code> runs over all outputs of the fusion
product.</p>

<p dir="auto">The values are stored at <code>SUNRepresentations.CGC_CACHE_PATH</code>, which is a package-wide
scratchspace. Each file <code>CGC/N/T/s1/s2.jld2</code> contains coefficients with datatype <code>T</code> for
the fusion of the <code>SU(N)</code> irreps <code>s1 ⊗ s2 → s3</code>, where <code>s3</code> runs over all possible fusion
channels. The folder structure is as follows:</p>

<p dir="auto">By default, irreps are denoted by their <code>N</code> weights, which are equivalent to the number of
boxes in each row of the Young tableau, and this is also how they are stored. For example,
the fundamental representation of SU(3) is denoted by <code>SUNIrrep(1, 0, 0)</code>, and the adjoint
representation by <code>SUNIrrep(2, 1, 0)</code>. Nevertheless, we also support using <code>N - 1</code> Dynkin
labels, which are denoted using <code>Vector{Int}</code>. For example, the fundamental representation
of SU(3) is denoted by <code>SUNIrrep([1, 0])</code>, and the adjoint representation by
<code>SUNIrrep([1, 1])</code>. Finally, it is also possible to use the dimensional name which is often
used in physics, e.g. <code>SUNIrrep{3}("3")</code> and <code>SUNIrrep{3}("8")</code>.</p>
<p dir="auto">The display of irreps can be changed in a persistent way by setting the <code>display_mode</code>
preference:</p>
<div class="highlight highlight-source-julia-console notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; using SUNRepresentations
