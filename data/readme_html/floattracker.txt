<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Description</h1><a id="user-content-description" class="anchor" aria-label="Permalink: Description" href="#description"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>TrackedFloats.jl</code> is a library that provides three new types: <code>TrackedFloat16</code>, <code>TrackedFloat32</code>, and <code>TrackedFloat64</code>.
These behave just like their <code>FloatN</code> counterparts except that they detect and log instances of exceptional floating point values. (E.g. <code>NaN</code> or <code>Inf</code>)</p>
<p dir="auto">There are three kinds of events that can happen during the lifetime of an exceptional floating point value:</p>
<p dir="auto"><a target="_blank" rel="noopener noreferrer" href="./exception_lifecycle.png"><img src="./exception_lifecycle.png" alt="Life cycle of an exceptional value" title="The birth, death, and times of a NaN" style="max-width: 100%;"></a></p>
<ul dir="auto">
<li><strong>GEN</strong>: the operation generated an exceptional value as a result (e.g. <code>0.0 / 0.0 → NaN</code>)</li>
<li><strong>PROP</strong>: the operation propagated an exceptional value from arguments to result (e.g. <code>NaN + 2.0 → NaN</code>, <code>2.0 / 0.0 → Inf</code>)</li>
<li><strong>KILL</strong>: the operation had an exceptional value in its arguments but not in its result (e.g. <code>NaN &gt; 1.0 → false</code>)</li>
</ul>
<p dir="auto">These events are then stored in a buffered log and can be written out to a file during or after the execution of a program.</p>

<p dir="auto">This code shows two different implementations of a max-element function.
One uses the builtin <code>&lt;</code> operator and the other uses Julia's <code>max</code> function. When encountering a <code>NaN</code> the <code>&lt;</code> will "kill" it (always returning <code>false</code>) and the <code>max</code> function will "prop" it (always returning back the <code>NaN</code>).</p>
<p dir="auto">Note that the result of this program is <em>wrong</em>: instead of the true maximum value of the list (<code>5.0</code>) getting returned, the bad version returns <code>4.0</code>!</p>
<p dir="auto">We can see this in the log that produced by TrackedFloats when running this file.</p>

<ol dir="auto">
<li>Call <code>using TrackedFloats</code>; you may want to include functions like <code>enable_nan_injection</code> or <code>config_logger</code> or the like. (See below for more details.)</li>

<p dir="auto">TrackedFloats should take care of the rest!</p>
<p dir="auto">Digging into step 2, there are two things that you can customize after initialization:</p>
<ul dir="auto">
<li>
<p dir="auto"><strong>The logger</strong></p>
<p dir="auto">Determines what and how events are captured and logged.</p>
</li>
<li>
<p dir="auto"><strong>The injector</strong></p>
<p dir="auto">Optional—default is to not inject. If you want to try injecting NaNs to fuzz your code, this is where you control when that happens.</p>
</li>
</ul>

<p dir="auto">Keyword arguments for <code>config_logger</code>:</p>
<ul dir="auto">
<li>
<p dir="auto"><code>filename::String</code> Basename of the file to write logs to.</p>
<p dir="auto">Constructors automatically prefix the timestamp to the beginning of this
basename so the logs are grouped together chronologically.</p>
</li>
<li>
<p dir="auto"><code>buffersize::Int</code> Number of logs to buffer in memory before writing to file.</p>
<p dir="auto">Defaults to 1000. Decrease if you are crashing without getting the logs that you need.</p>
</li>
<li>
<p dir="auto"><code>printToStdOut::Bool</code> Whether or not to write logs to STDOUT; defaults  to <code>false</code>.</p>
</li>
<li>
<p dir="auto"><code>cstg::Bool</code> Write logs in CSTG format.</p>
</li>
<li>
<p dir="auto"><code>cstgLineNum::Bool</code> Include the line number in CSTG output.</p>
</li>
<li>
<p dir="auto"><code>cstgArgs::Bool</code> Include arguments to functions in CSTG output.</p>
</li>
<li>
<p dir="auto"><code>maxFrames::Union{Int,Unbounded}</code> Maximum number of frames to print per even in the logs; defaults to <code>Unbounded</code>.</p>
</li>
<li>
<p dir="auto"><code>maxLogs::Union{Int,Unbounded}</code> Maximum number of events to log; defaults to <code>Unbounded</code>.</p>
</li>
<li>
<p dir="auto"><code>exclusions::Array{Symbol}</code> Events to not log; defaults to <code>[:prop]</code>.</p>
</li>
</ul>

<p dir="auto">TrackedFloats can <em>inject</em> <code>NaN</code>s at random points in your program to help you find places where you might not be handling exceptional values properly: this technique can help you find <code>NaN</code> kills before they happen in a production environment.</p>

<p dir="auto">Keyword arguments for <code>config_injector</code>:</p>
<ul dir="auto">
<li>
<p dir="auto"><code>active::Boolean</code> inject only if true</p>
</li>
<li>
<p dir="auto"><code>n_inject::Int</code> maximum number of NaNs to inject; gets decremented every time
a NaN gets injected</p>
</li>
<li>
<p dir="auto"><code>odds::Int</code> inject a NaN with 1:odds probability—higher value → rarer to
inject</p>
</li>
<li>
<p dir="auto"><code>functions::Array{FunctionRef}</code> if given, only inject NaNs when within these
functions; default is to not discriminate on functions</p>
</li>
<li>
<p dir="auto"><code>libraries::Array{String}</code> if given, only inject NaNs when within this library.</p>
</li>
<li>
<p dir="auto"><code>record::String</code> if given, record injection invents in a way that can be
replayed later with the <code>replay</code> argument.</p>
</li>
<li>
<p dir="auto"><code>replay::String</code> if given, ignore all previous directives and use this file
for injection replay.</p>
</li>
</ul>
<p dir="auto"><code>functions</code> and <code>libraries</code> work together as a union: i.e. the set of possible NaN
injection points is a union of the places matched by <code>functions</code> and <code>libraries</code>.</p>

<p dir="auto">TrackedFloats allows you to fuzz code and inject NaNs or Infs wherever a <code>TrackedFloat</code> type is used. Moreover, you can record these injections to rerun injections.</p>
<p dir="auto"><strong>WARNING:</strong> it is critical that inputs to the program be exactly the same for recording and replaying to be consistent. The recordings are sensitive to the number of times a floating point operation is hit.</p>

<p dir="auto">During recording and replaying, we increment a counter each time a floating point operation happens. This doesn't add much overhead [<em>citation needed</em>] since we're already intercepting each of the floating point calls anyway—but it explains why we need to make sure our programs are deterministic before recording and replaying.</p>

<p dir="auto">The first field <code>42</code> is the injection point, or the nth time a floating point operation was intercepted by TrackedFloats. The second field <code>solve.jl</code> acts as a little sanity check: this is the first non-TrackedFloats file off of the stack trace. After that comes a list of module names paired with the function on the call stack.</p>

<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Julia and GPU programming</h1><a id="user-content-julia-and-gpu-programming" class="anchor" aria-label="Permalink: Julia and GPU programming" href="#julia-and-gpu-programming"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">TrackedFloats works on the CPU. If a Julia function calls a GPU kernel, then you can track exceptions inside the GPU execution using our companion tool <a href="https://github.com/LLNL/GPU-FPX">GPU-FPX</a> developed by Xinyi Li for her PhD. This will allow you to (1) see the exception flows inside the kernel, (2) whether the exceptions got killed inside the kernel, and if the exceptions were present in the return result of the Julia GPU call, then (3) TrackedFloats will show how that exception further flows through the Julia code. You get this full effect by running your Julia Command under <code>LD_PRELOAD</code>.</p>
<p dir="auto">For details of <code>LD_PRELOAD</code> and to obtain and install GPU-FPX, please visit the <a href="https://github.com/LLNL/GPU-FPX">GPU-FPX repository</a> and ask its authors for assistance if needed. For help on using TrackedFloats in conjunction with this tool, talk to us.</p>
