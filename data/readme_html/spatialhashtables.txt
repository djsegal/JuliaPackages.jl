<p dir="auto">Creates spatial hash tables on bounded and unbounded domains for fast
computations of pairwise interaction terms. Updating the hash table is
done in <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="e148443665d04ee344009c651d1141c4">$\mathcal{O}(n)$</math-renderer> time and allocation free. Iteration over neigbour lists
is also allocation free and supports CPU and GPU parallelization.</p>
<p dir="auto">The interface is minimalistic. For a more full-featured and established package, see <a href="https://github.com/m3g/CellListMap.jl">CellListMap.jl</a>.</p>
<p dir="auto">See the <a href="https://github.com/SteffenPL/SpatialHashTables.jl/tree/main/benchmarks">benchmarks</a> folder for some timings and performance comparisons.</p>

@kernel function compute_something!(F, @Const(X), grid, cutoff)
    i = @index(Global) 

    Xi = X[i]
    Fi = zero(Xi)

    FL = eltype(Xi) # make sure we only use Float32!!!

    cutoff² = cutoff^2

    for j in neighbours(grid, Xi, cutoff)
        Xij = Xi - X[j]
        d² = dist²(Xij)

        if d² &lt; cutoff²
            Fi += FL(1)/sqrt(d²) * (Xij)
        end
    end

    F[i] = Fi

<p dir="auto">All constructors follow the principle that one first defines the <code>cutoff</code>, then the data needed to determine the number of partitions used to create grid and finally the points <code>X</code> which are expected to be a <code>Vector</code> (or <code>CuVector</code> etc) of <code>SVector</code>s.</p>
<p dir="auto">The fourth argument might be a backend specific type suitable for storing indices, e.g. <code>CuVector{Int32}</code>, per default, <code>Vector{Int64}</code> is used.</p>
<p dir="auto">In addition, one might define <code>nthreads</code> and <code>backend</code> as keywoard arguments.</p>
<p dir="auto">The following constructors give a unbounded <code>HashGrid</code>:</p>

<p dir="auto">For <code>BoundedGrid</code>s it is not sufficient to determine how a number, but instead one needs to provide the <code>gridsize</code> which determines
how many unique cells are created in each direction (and then periodically continued).</p>
<p dir="auto">Note, that one can also provide a <code>SVector{Dim, Float}</code> to alternatively define the physical size of the <code>grid</code> (e.g. <code>domainsize = cutoff .* gridsize</code>). Dispatch is used to differentiated <code>gridsize::NTuple{Dim,Int}</code> and <code>domainsize::SVector{Dim,Float64}</code>.</p>
<p dir="auto">Optionally, one might shift the grid by the <code>origin</code> keyword.</p>
<p dir="auto">Other than that, the <code>BoundedGrid</code> has the same optional 4th arguemnt to determine the index type and the same keyword arguments for <code>nthreads</code> and <code>backend</code>.</p>

<p dir="auto">These are the current performance benchmarks (see <code>benchmarks/report</code> folder for the implementation of the benchmark).</p>
<p dir="auto">Notably, the package is approaching the performance of NVIDIA Warp's HashGrid. For benchmarks with only a few particles per box (<code>uniform</code>) the performance is already good, for benchmarks with many particles per box (<code>xatomic</code>) <a href="https://github.com/m3g/CellListMap.jl">CellListMap.jl</a> is faster.</p>
