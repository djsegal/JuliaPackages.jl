<p dir="auto">Stochastic rounding for floating-point arithmetic.</p>
<p dir="auto">This package exports <code>Float64sr</code>, <code>Float32sr</code>,<code>Float16sr</code>, and <code>BFloat16sr</code>, four number formats that behave
like their deterministic counterparts but with stochastic rounding that is proportional to the
distance of the next representable numbers and therefore
<a href="https://en.wikipedia.org/wiki/Rounding#Stochastic_rounding" rel="nofollow">exact in expectation</a>
(see also example below in <a href="https://github.com/milankl/StochasticRounding.jl#usage">Usage</a>.
The only known hardware implementation available is
<a href="https://www.graphcore.ai/products/ipu" rel="nofollow">Graphcore's IPU with stochastic rounding</a>,
but other vendors are likely working on stochastic rounding for their next-generation
GPUs (and maybe CPUs too).</p>
<p dir="auto">The software emulation in StochasticRounding.jl makes the number format
slower, but e.g. Float32 with stochastic rounding is only about 2x slower than the
default deterministically rounded Float64.
<a href="https://sunoru.github.io/RandomNumbers.jl/stable/man/xorshifts/#Xorshift-Family-1" rel="nofollow">Xoroshiro128Plus</a>,
a random number generator from the <a href="https://en.wikipedia.org/wiki/Xorshift" rel="nofollow">Xorshift family</a>, is used from the
<a href="https://github.com/sunoru/RandomNumbers.jl">RandomNumbers.jl</a> package, due to its speed and statistical properties.</p>
<p dir="auto">Every format of <code>Float64sr</code>, <code>Float32sr</code>,<code>Float16sr</code>, and <code>BFloat16sr</code> uses a higher precision format
to obtain the "exact" arithmetic result which is then stochastically rounded to the respective
lower precision format. <code>Float16sr</code> and <code>BFloat16sr</code> use <code>Float32</code> for this,
<code>Float32sr</code> uses <code>Float64</code>, and <code>Float64sr</code> uses <code>Double64</code> from
<a href="https://github.com/JuliaMath/DoubleFloats.jl">DoubleFloats.jl</a></p>
<p dir="auto">You are welcome to raise <a href="https://github.com/milankl/StochasticRounding.jl/issues">issues</a>,
ask questions or suggest any changes or new features.</p>
<p dir="auto"><code>BFloat16sr</code> is based on <a href="https://github.com/JuliaMath/BFloat16s.jl">BFloat16s.jl</a><br>
<code>Float16sr</code> is slow in Julia &lt;1.6, but much faster in Julia &gt;=1.6 due to LLVM's <code>half</code> support.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Usage</h2><a id="user-content-usage" class="anchor" aria-label="Permalink: Usage" href="#usage"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">StochasticRounding.jl defines <code>stochastic_round</code> as a general interface to round stochastically to
a floating-point number, e.g.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; stochastic_round(Float32,π)
3.1415927f0

julia&gt; stochastic_round(Float32,π)
3.1415925f0"><pre>julia<span class="pl-k">&gt;</span> <span class="pl-c1">stochastic_round</span>(Float32,π)
<span class="pl-c1">3.1415927f0</span>

julia<span class="pl-k">&gt;</span> <span class="pl-c1">stochastic_round</span>(Float32,π)
<span class="pl-c1">3.1415925f0</span></pre></div>
<p dir="auto">Here we round π (which is first converted to Float64) to Float32 where it is not exactly representable,
hence we have results that differ in the last bit. The chance here is</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; chance_roundup(Float32,π)
0.6333222836256027"><pre>julia<span class="pl-k">&gt;</span> <span class="pl-c1">chance_roundup</span>(Float32,π)
<span class="pl-c1">0.6333222836256027</span></pre></div>
<p dir="auto">about 63% to obtain the first (which therefore would be round to nearest, the default rounding mode),
and hence 37% to obtain the latter (round away from nearest). The <code>stochastic_round</code> function is wrapped
into the floating-point formats <code>Float64sr</code>, <code>Float32sr</code>, <code>Float16sr</code> and <code>BFloat16sr</code> are supposed to be drop-in
replacements for their deterministically rounded counterparts. You can create data of those types as expected
(which is bitwise identical to the deterministic formats respectively) and the type
will trigger stochastic rounding on every arithmetic operation.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; a = BFloat16sr(1.0)
BFloat16sr(1.0)
julia&gt; a/3
BFloat16sr(0.33398438)
julia&gt; a/3
BFloat16sr(0.33203125)"><pre>julia<span class="pl-k">&gt;</span> a <span class="pl-k">=</span> <span class="pl-c1">BFloat16sr</span>(<span class="pl-c1">1.0</span>)
<span class="pl-c1">BFloat16sr</span>(<span class="pl-c1">1.0</span>)
julia<span class="pl-k">&gt;</span> a<span class="pl-k">/</span><span class="pl-c1">3</span>
<span class="pl-c1">BFloat16sr</span>(<span class="pl-c1">0.33398438</span>)
julia<span class="pl-k">&gt;</span> a<span class="pl-k">/</span><span class="pl-c1">3</span>
<span class="pl-c1">BFloat16sr</span>(<span class="pl-c1">0.33203125</span>)</pre></div>
<p dir="auto">As <code>1/3</code> is not exactly representable the rounding will be at 66.6% chance towards 0.33398438
and at 33.3% towards 0.33203125 such that in expectation the result is 0.33333... and therefore exact.</p>

<p dir="auto">The random number generator is randomly seeded on every <code>import</code> or <code>using</code> such that running
the same calculations twice, will not yield bit-reproducible results. However, you can seed
the random number generator at any time with any integer larger than zero as follows</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; StochasticRounding.seed(2156712)"><pre>julia<span class="pl-k">&gt;</span> StochasticRounding<span class="pl-k">.</span><span class="pl-c1">seed</span>(<span class="pl-c1">2156712</span>)</pre></div>
<p dir="auto">the state of the random number generator for StochasticRounding.jl is independent from Julia's default,
which is used for <code>rand()</code>, <code>randn()</code> etc.</p>

<p dir="auto">Round-to-nearest (tie to even) is the standard rounding mode for IEEE floats.
Stochastic rounding is explained in the following schematic</p>
<p dir="auto"><a target="_blank" rel="noopener noreferrer" href="figs/schematic.png"><img src="figs/schematic.png" style="max-width: 100%;"></a></p>
<p dir="auto">The exact result x of an arithmetic operation (located at one fifth between x₂ and x₃ in this example)
is always rounded down to x₂ for round-to-nearest.
For stochastic rounding, only at 80% chance x is round down.
At 20% chance it is round up to x₃, proportional to the distance of x between x₂ and x₃.</p>

<p dir="auto">Stochastic rounding imposes an about x5 performance decrease for Float32 and BFloat16, but only x2 for Float16,
however, 10x for Float64 due to the use of Double64.
For more complicated benchmarks the performance decrease is usually within x10.
About 50% of the time is spend on the random number generation with Xoroshiro128+.</p>
