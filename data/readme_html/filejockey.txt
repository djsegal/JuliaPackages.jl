<p dir="auto">FileJockey is a light-weight wrapper around file system entries and paths. It provides primitives to facilitate batch operations on large numbers of them.</p>
<p dir="auto">Essentially, it uses dedicated types for the various kinds of entries:</p>

<br>
<p dir="auto">Some problem areas FileJockey tries to help you with:</p>
<ul dir="auto">
<li>
<p dir="auto">Unix natively provides support for batch file system ops, e.g., via <code>find . | xargs ...</code>. One has to be careful, though, and cope with errors during processing, properly handle spaces in filenames, account for or skip symlinks, etc. FileJockey wraps the path strings into dedicated file entry types to make this smoother.</p>
</li>
<li>
<p dir="auto">Traversing large directories that contain symlinks (especially symlinks to directories inside the very same hierarchy) can easily lead to duplicate file paths in our pipeline. On the other hand, skipping symlinks could "lose" files if the symlinks refer to dirs outside the original hierarchy. FileJockey explicitly tracks symlinks and can check for those pitfalls.</p>
</li>
<li>
<p dir="auto">Using raw strings as paths can be error-prone. Say, for example, you want to remove duplicate files (i.e., different file entries whose file contents are identical). Yet the paths "A.txt" and "../mydir/A.txt" could easily actually be the same file entry--deleting one of them could delete <em>that one</em> file. While it would be tempting to just <code>realpath</code> everything, this would also destroy valuable symlink information. FileJockey treats paths in a canonical way so you don't have to worry about <code>normpath</code>-/<code>abspath</code>-/<code>realpath</code>-ing anything. (For example, a <code>Symlink</code>'s file entry path consists of its "real" (symlink-free) dirname combined with the symlink's own basename.) Paths are thus identical <em>if and only if</em> the underlying entries are.</p>
</li>
<li>
<p dir="auto">We often don't thing about liberally using functions like <code>isfile</code> or <code>isdir</code>--but those can be surprisingly costly operations, especially when working with many files on slow network drives. FileJockey caches a file system entry's <code>StatStruct</code>; those operation become basically free (or unnecessary, as we can dispatch on the FileJockey types).</p>
</li>
</ul>
<br>
<br>
<p dir="auto">This should help us tackle higher-level issues in a more hassle-free way:</p>
<ul dir="auto">
<li>
<p dir="auto">Safely detect and remove duplicate files.</p>
</li>
<li>
<p dir="auto">Easily traverse dir hierarchies and filter the results by type, extension, etc.</p>
</li>
<li>
<p dir="auto">Apply arbitrary operations to such file batches, e.g., create hardlinks to each input file for a new, zero-diskspace view on your photo library.</p>
</li>
<li>
<p dir="auto">Process EXIF data from files, by calling outside EXIF tools in sub-batches (i.e., partitions of 100 files at a time) to largely sidestep costly startup time.</p>
</li>
<li>
<p dir="auto">Aaaand.. backups, dir-diffs, customizable recursive grepping,...</p>
</li>
</ul>
<br>

<ul dir="auto">
<li>
<p dir="auto"><code>ls(path)</code> -- list files; returns vector of file system entries (<code>AbstractEntry</code>s).</p>
</li>
<li>
<p dir="auto"><code>find(path)</code> -- akin to Unix <code>find</code>, returns all file system entries of a dir hierarchy.</p>
</li>
<li>
<p dir="auto"><code>eachentry(path)</code> -- same as <code>find()</code>, but returns iterator. Compose with <code>eachentry(.) |&gt; filter(hasext("jpg")) |&gt; first</code></p>
</li>
<li>
<p dir="auto"><code>getfiles(X)</code> -- called on file system entries, returns only regular files and targets of symlinks-to-files (resulting in a <code>Vector{FileEntry}</code>).</p>
</li>
</ul>
