<p dir="auto"><code>FITSHeaders</code> is a pure <a href="https://julialang.org/" rel="nofollow">Julia</a> package for managing basic
FITS structures such as FITS headers. <a href="https://fits.gsfc.nasa.gov/fits_standard.html" rel="nofollow">FITS (for <em>Flexible Image Transport
System</em>)</a> is a data file format
widely used in astronomy. A FITS file is a concatenation of <em>Header Data Units</em>
(HDUs) that consist in a header part and a data part. The header of a HDU is a
collection of so-called <em>FITS cards</em>. Each such card is stored in textual form
and associates a keyword with a value and/or a comment.</p>
<p dir="auto">The <code>FITSHeaders</code> package is intended to provide:</p>
<ul dir="auto">
<li>
<p dir="auto">Methods for fast parsing of a FITS header or of a piece of a FITS header
(that is a single FITS header card).</p>
</li>
<li>
<p dir="auto">An expressive API for creating FITS cards and accessing their components
(keyword, value, and comment), possibly, in a <em>type-stable</em> way.</p>
</li>
<li>
<p dir="auto">Methods for easy and efficient access to the records of a FITS header.</p>
</li>
</ul>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Building FITS cards</h2><a id="user-content-building-fits-cards" class="anchor" aria-label="Permalink: Building FITS cards" href="#building-fits-cards"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">A FITS header card associates a keyword (or a name) with a value and a comment
(both optional). A FITS header card can be efficiently stored as an instance of
<code>FitsCard</code> built by:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card = FitsCard(key =&gt; (val, com))"><pre>card <span class="pl-k">=</span> <span class="pl-c1">FitsCard</span>(key <span class="pl-k">=&gt;</span> (val, com))</pre></div>
<p dir="auto">with <code>key</code> the card name, <code>val</code> its value, and <code>com</code> its comment. The value
<code>val</code> may be:</p>
<ul dir="auto">
<li>a boolean to yield a card of type <code>FITS_LOGICAL</code>;</li>
<li>an integer to yield a card of type <code>FITS_INTEGER</code>;</li>
<li>a non-integer real to yield a card of type <code>FITS_FLOAT</code>;</li>
<li>a complex to yield a card of type <code>FITS_COMPLEX</code>;</li>
<li>a string to yield a card of type <code>FITS_STRING</code>;</li>
<li><code>nothing</code> to yield a card of type <code>FITS_COMMENT</code>;</li>
<li><code>undef</code> or <code>missing</code> to yield a card of type <code>FITS_UNDEFINED</code>.</li>
</ul>
<p dir="auto">The comment may be omitted for a normal FITS card and the value may be omitted
for a commentary FITS card:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card = FitsCard(key =&gt; val::Number)
card = FitsCard(key =&gt; str::AbstractString)"><pre>card <span class="pl-k">=</span> <span class="pl-c1">FitsCard</span>(key <span class="pl-k">=&gt;</span> val<span class="pl-k">::</span><span class="pl-c1">Number</span>)
card <span class="pl-k">=</span> <span class="pl-c1">FitsCard</span>(key <span class="pl-k">=&gt;</span> str<span class="pl-k">::</span><span class="pl-c1">AbstractString</span>)</pre></div>
<p dir="auto">In the 1st case, the comment is assumed to be empty. In the 2nd case, the
string <code>str</code> is assumed to be the card comment if <code>key</code> is <code>"COMMENT"</code> or
<code>"HISTORY"</code> and the card value otherwise.</p>
<p dir="auto">Conversely, <code>Pair(card)</code> yields the pair <code>key =&gt; (val, com)</code>. The <code>convert</code> method
is extended by the <code>FITSHeaders</code> package to perform these conversions.</p>
<p dir="auto">If the string value of a FITS card is too long, it shall be split across
several consecutive <code>CONTINUE</code> cards when writing a FITS file. Likewise, if the
comment of a commentary keyword (<code>"COMMENT"</code> or <code>"HISTORY"</code>) is too long, it
shall be split across several consecutive cards with the same keyword when
writing a FITS file.</p>

<p dir="auto">As the values of FITS keywords have different types, <code>card.value</code> does not
yield a Julia value but a callable object. Called without any argument, this
object yields the actual card value:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card.value() -&gt; val::Union{Bool,Int64,Float64,ComplexF64,String,Nothing,UndefInitializer}"><pre>card<span class="pl-k">.</span><span class="pl-c1">value</span>() <span class="pl-k">-&gt;</span> val<span class="pl-k">::</span><span class="pl-c1">Union{Bool,Int64,Float64,ComplexF64,String,Nothing,UndefInitializer}</span></pre></div>
<p dir="auto">but such a call is not <em>type-stable</em> as indicated by the union <code>Union{...}</code> in
the above type assertion. For a type-stable result, the card value can be
converted to a given data type <code>T</code>:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card.value(T)

<p dir="auto">both yield the value of <code>card</code> converted to type <code>T</code>. For readability, <code>T</code> may
be an abstract type: <code>card.value(Integer)</code> yields the same result as
<code>card.value(Int64)</code>, <code>card.value(Real)</code> or <code>card.value(AbstractFloat)</code> yield
the same result as <code>card.value(Float64)</code>, <code>card.value(Complex)</code> yields the same

error is thrown if the conversion is not possible or inexact.</p>

<code>isassigned(card)</code> yields whether <code>card</code> has a value (that is whether it is

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">FITS keywords</h2><a id="user-content-fits-keywords" class="anchor" aria-label="Permalink: FITS keywords" href="#fits-keywords"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">There are two kinds of FITS keywords:</p>
<ul dir="auto">
<li>
<p dir="auto">Short FITS keywords are words with at most 8 ASCII characters from the
restricted set of upper case letters (bytes 0x41 to 0x5A), decimal digits
(hexadecimal codes 0x30 to 0x39), hyphen (hexadecimal code 0x2D), or
underscore (hexadecimal code 0x5F). In a FITS file, keywords shorter than 8
characters are right-padded with ordinary spaces (hexadecimal code 0x20).</p>
</li>
<li>
<p dir="auto"><code>HIERARCH</code> FITS keywords start with the string <code>"HIERARCH "</code> (with a single
trailing space) followed by one or more words composed from the same
restricted set of ASCII characters as short keywords and separated by a
single space.</p>
</li>
</ul>
<p dir="auto">Keywords longer than 8 characters or composed of several words can only be
represented as <code>HIERARCH</code> FITS keywords. To simplify the representation of FITS
cards as pairs, the <code>FitsCard</code> constructor automatically converts long keywords
or multi-word keywords into a <code>HIERARCH</code> FITS keyword by prefixing the keyword
with the string <code>"HIERARCH "</code> for example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; card = FitsCard(&quot;VERY-LONG-NAME&quot; =&gt; (2, &quot;keyword is longer than 8 characters&quot;))

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Quick FITS keys</h2><a id="user-content-quick-fits-keys" class="anchor" aria-label="Permalink: Quick FITS keys" href="#quick-fits-keys"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">In <code>FITSHeaders</code>, a key of type <code>FitsKey</code> is a 64-bit value computed from a FITS
keyword. The key of a short FITS keyword is unique and exactly matches the
first 8 bytes of the keyword as it is stored in a FITS file. Thus quick keys
provide fast means to compare and search FITS keywords. The constructor
<code>FitsKey(name)</code> yields the quick key of the string <code>name</code>. A quick key may be
literally expressed by using the <code>@Fits_str</code> macro in Julia code. For example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card.key == Fits&quot;NAXIS&quot;"><pre>card<span class="pl-k">.</span>key <span class="pl-k">==</span> <span class="pl-s"><span class="pl-pds"><span class="pl-c1">Fits</span>"</span>NAXIS<span class="pl-pds">"</span></span></pre></div>
<p dir="auto">is faster than, say <code>card.name == "NAXIS"</code>, to check whether the name of the
FITS header card <code>card</code> is <code>"NAXIS"</code>. This is because, the comparison is
performed on a single integer (not on several characters) and expression
<code>Fits"...."</code> is a constant computed at compile time with no run-time penalty.
Compared to <code>FitsKey(name)</code>, <code>Fits"...."</code> checks the validity of the characters
composing the literal short keyword (again this is done at compile time so
without run-time penalty) and, for readability, does not allow for trailing
spaces.</p>
<p dir="auto">For a <code>HIERARCH</code> keyword, the quick key is equal to the constant
<code>Fits"HIERARCH"</code> whatever the other part of the keyword.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Parsing of FITS header cards</h2><a id="user-content-parsing-of-fits-header-cards" class="anchor" aria-label="Permalink: Parsing of FITS header cards" href="#parsing-of-fits-header-cards"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Each FITS header card is stored in a FITS file as 80 consecutive bytes from the
restricted set of ASCII characters from <code>' '</code> to <code>'~'</code> (hexadecimal codes 0x20
to 0x7E). Hence Julia strings (whether they are encoded in ASCII or in UTF8)
can be treated as vectors of bytes. The parsing methods provided by the
<code>FITSHeaders</code> package exploit this to deal with FITS headers and cards stored as
either vectors of bytes (of type <code>AbstractVector{UInt8}</code>) or as Julia strings
(of type <code>String</code> or <code>SubString{String}</code>).</p>
<p dir="auto">A <code>FitsCard</code> object can be built by parsing a FITS header card as it is stored
in a FITS file:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="card = FitsCard(buf; offset=0)"><pre>card <span class="pl-k">=</span> <span class="pl-c1">FitsCard</span>(buf; offset<span class="pl-k">=</span><span class="pl-c1">0</span>)</pre></div>
<p dir="auto">where <code>buf</code> is either a string or a vector of bytes. Keyword <code>offset</code> can be
used to specify the number of bytes to skip at the beginning of <code>buf</code>, so that
it is possible to extract a specific FITS header card, not just the first one.
At most, the 80 first bytes after the offset are scanned to build the
<code>FitsCard</code> object. The next FITS card to parse is then at <code>offset + 80</code> and so
on.</p>
<p dir="auto">The considered card may be shorter than 80 bytes, the result being exactly the
same as if the missing bytes were spaces. If there are no bytes left, a
<code>FitsCard</code> object equivalent to the final <code>END</code> card of a FITS header is
returned.</p>

<p dir="auto">A record <code>rec</code> may be pushed to a FITS header <code>hdr</code> to modify the header:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="push!(hdr, rec)"><pre><span class="pl-c1">push!</span>(hdr, rec)</pre></div>
<p dir="auto">where <code>rec</code> may have any form allowed by the <code>FitsCard</code> constructor. If the
keyword is <code>"COMMENT"</code>, <code>"HISTORY"</code>, <code>""</code>, or <code>"CONTINUE"</code>, <code>rec</code> is appended
to the end of the list of records stored by <code>hdr</code>. For other keywords which
must be unique, if a record of the same name exists in <code>hdr</code>, it is replaced by
<code>rec</code>; otherwise, it is appended to the end of the list of records stored by
<code>hdr</code>.</p>
<p dir="auto">The <code>setindex!</code> method may be used with a keyword (string) index. For example,
the two following statements are equivalent:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="hdr[key] = (val, com)
push!(hdr, key =&gt; (val, com))"><pre>hdr[key] <span class="pl-k">=</span> (val, com)
<span class="pl-c1">push!</span>(hdr, key <span class="pl-k">=&gt;</span> (val, com))</pre></div>
<p dir="auto">The <code>setindex!</code> method may also be used with a linear (integer) index.. For
example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="hdr[i] = rec"><pre>hdr[i] <span class="pl-k">=</span> rec</pre></div>
<p dir="auto">replaces the <code>i</code>-th record in <code>hdr</code> by <code>rec</code>. With an integer index, the rule

following example illustrates how this can be used to modify the comment of the

<p dir="auto"><code>FITSHeaders</code> is ought to be fast. Below are times and memory allocations for
parsing 80-byte FITS cards measured with Julia 1.8.5 on a Linux laptop with an
Intel Core i7-5500U CPU:</p>
<ul dir="auto">
<li>parsing logical FITS card:  114.588 ns (2 allocations:  64 bytes)</li>
<li>parsing integer FITS card:  118.519 ns (2 allocations:  72 bytes)</li>
<li>parsing HIERARCH FITS card: 142.462 ns (2 allocations:  88 bytes)</li>
<li>parsing float FITS card:    274.119 ns (4 allocations: 152 bytes)</li>
<li>parsing complex FITS card:  424.060 ns (6 allocations: 248 bytes)</li>
<li>parsing string FITS card:   155.694 ns (4 allocations: 144 bytes)</li>
<li>parsing string with quotes: 169.223 ns (4 allocations: 168 bytes)</li>
<li>parsing COMMENT FITS card:   90.615 ns (2 allocations: 112 bytes)</li>
<li>parsing HISTORY FITS card:  100.591 ns (2 allocations:  72 bytes)</li>
<li>parsing blank FITS card:     78.261 ns (0 allocations:   0 bytes)</li>
<li>parsing END FITS card:       82.286 ns (0 allocations:   0 bytes)</li>
</ul>
<p dir="auto">The benchmark code is in file <a href="test/benchmarks.jl"><code>test/benchmarks.jl</code></a>. The
HIERARCH card has an integer value. The float and complex valued cards take
more time to parse because parsing a floating-point value is more complex than
parsing, say, an integer and because the string storing the floating-point
value must be copied to replace letters <code>d</code> and <code>D</code>, allowed in FITS standard
to indicate the exponent, by an <code>e</code>.</p>
<p dir="auto">For comparison, just extracting the keyword, value, and comment parts from a
80-characters FITS card by calling the functions <code>fits_get_keyname</code> and
<code>fits_parse_value</code> of CFITSIO library takes about 150 ns on the same machine.
This does not includes the allocation of the buffers to store these 3 parts
(about 120 ns for this) and the parsing of the value which are all included in
the timings of the <code>FISCard</code> constructor above.</p>
