<p dir="auto">When creating a test suite, it is often the case that many tests share the same setup (and teardown) code. In
particular, it is often the case that the tests form a tree, where some setup is common to many tests, and additional
setup is common to a subset of the tests, and so on until reaching the leaf test cases of this tree.</p>
<p dir="auto">This package is built around this concept. It runs all the leaf test cases, and for each one, it runs all the setup code
needed for it, from scratch. That is, all the tests cases are isolated from each other and can freely modify the
prepared test data.</p>
<p dir="auto">The main function of this package is <a href="@ref"><code>nested_test</code></a>, which introduces a new sub-test to run. In addition, you can
always get the full path name of the current test environment using <a href="@ref"><code>test_name</code></a>. For example, consider the
following:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="nested_test(&quot;top&quot;) do

<p dir="auto">The framework will run both the simple operations tests and the complex operations tests. Nested test cases have full
access to the variables introduced in their parent, following Julia's nested variable scopes; this allows both leaf test
cases to access the <code>db</code> variable from the top level test case. However, the framework will re-run things so that each
of the leaf tests will get a fresh database, isolating the leaf tests from each other. If a parent test case fails for
any reason (including failed <code>@test</code> assertions), then its child tests are skipped.</p>
<p dir="auto">If you call <code>abort_on_first_failure(true)</code>, then the first failed test will abort execution. You can also restrict
the set of test cases that will be executed by specifying a list of prefixes, e.g. <code>test_prefixes(["top"])</code> will
restrict the executed tests to only cases nested under <code>top</code>.</p>
<p dir="auto">NOTE: Don't try to wrap <code>nested_test</code> inside a <code>@testset</code> - it won't work since <code>@testset</code> takes over the failed <code>@test</code>
assertions making it difficult for the <code>nested_test</code> to tell when a test case failed. It would have been nice to
integrate both systems so that each nested test case would be a <code>@testset</code>, or at least the top-level nested test case
would be, but this requires deep integration with the implementation of <code>@testset</code>. If someone wants to take a stab at
this, pull requests are welcome :-) For now we print the total number of passed/failed test cases (not <code>@test</code>
assertions) at the end, together with the elapsed time.</p>
