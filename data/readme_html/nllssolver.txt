<p dir="auto">A package for optimizing robustified Non-Linear Least Squares (NLLS) problems, with the following features:</p>
<ul dir="auto">
<li><strong>Simple interface</strong>: Large scale problems can be defined with relatively little code. Derivatives are computed automatically (though can be user-provided if desired).</li>
<li><strong>Robust</strong>: Residual blocks can be robustified easily.</li>
<li><strong>Non-Euclidean variables</strong>: Variables do not need to exist in a Euclidean space. For example, 3D rotations can be represented as a 9 parameter SO(3) matrix, yet retain a minimal 3DoF update parameterization.</li>
</ul>
<p dir="auto">The package is heavily inspired by, and very similar to, the <a href="http://ceres-solver.org/" rel="nofollow">Ceres-Solver C++ library</a>, in terms of interface and functionality. Ceres is used to optimize a large number of academic and commercial <a href="http://ceres-solver.org/users.html" rel="nofollow">problems</a>, mostly in the field of multi-view geometry.</p>
<p dir="auto">Features not currently supported:</p>
<ul dir="auto">
<li><strong>Constraints</strong>: Bounds on variables are not explicitly supported. However, bounded variables can be implemented using special, non-Euclidean parameterizations.</li>
</ul>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Problem definition</h3><a id="user-content-problem-definition" class="anchor" aria-label="Permalink: Problem definition" href="#problem-definition"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Each NLLS problem is defined using two types of data structure:</p>
<ul dir="auto">
<li><strong>Variable blocks</strong>, which contain the parameters to be optimized.</li>
<li><strong>Cost blocks</strong>, which contain the data that defines the NLLS cost function to be minimized w.r.t. the variables. A single cost block generates a scalar cost as a function of a fixed (at compile-time) number of variable blocks, currently up to 10.</li>
</ul>
<p dir="auto">Each instance of these two types must implement a standard API, as follows.</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Variable blocks</h4><a id="user-content-variable-blocks" class="anchor" aria-label="Permalink: Variable blocks" href="#variable-blocks"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li><strong><code>N::Union{Int, StaticInt} = nvars(::MyVar)</code></strong> returns the intrinsic dimensionality, N, of the variable block. This must be fixed for the duration of the optimization. Returning a <code>::StaticInt{N}</code> will improve performance, so do so where possible.</li>
<li><strong><code>newvar::MyVar = update(oldvar::MyVar, updatevec::AbstractVector, start::Int=1)</code></strong> updates a variable, using the values in update vector <code>updatevec</code>, starting at index <code>start</code>.</li>
</ul>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Cost blocks</h4><a id="user-content-cost-blocks" class="anchor" aria-label="Permalink: Cost blocks" href="#cost-blocks"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li><strong><code>::StaticInt{N} = ndeps(::MyCost)</code></strong> returns the number of variable blocks the cost block depends on. This must be a compile-time constant of type <code>StaticInt</code>.</li>
<li><strong><code>varind::SVector{N, Int} = varindices(costblock::MyCost)</code></strong> returns the indices of the variable blocks (stored in problem) that this cost block depends on. These values are assumed to remain fixed for the duration of an optimization.</li>
<li><strong><code>blockvars::Tuple = getvars(costblock::MyCost, allvars::Vector)</code></strong> returns a tuple containing the variables the cost block depends on.</li>
</ul>
<p dir="auto">Cost blocks can either be robustified least-squares blocks (an instance of an <code>AbstractResidual</code>), or a standard scalar cost block (an instance of an <code>AbstractCost</code>).</p>
<p dir="auto"><code>AbstractResidual</code> blocks should implement the following functions:</p>
<ul dir="auto">
<li><strong><code>M::Union{Int, StaticInt} = nres(::MyCost)</code></strong> (required for least squares costs only) returns the number of scalar residuals in the block. This must be fixed for the duration of the optimization. Returning a <code>::StaticInt{M}</code> will improve performance, so do so where possible.</li>
<li><strong><code>res::SVector{M, Float} = computeresidual(costblock::MyCost, blockvars...)</code></strong> returns the computed residual block.</li>
<li><strong><code>res::SVector{M, Float}, jac::SMatrix{M, P, Float} = computeresjac(::StaticInt{varflags}, res::MyCost, blockvars...)</code></strong> (<em>optional</em>) returns the computed residual block and its Jacobian, for all the variables whose corresponding bit in <code>varflags</code> is set. If this function isn't provided, the Jacobian is computed using ForwardDiff auto-differentiation. <code>P</code> is the total dimensionality of the unfixed variable blocks.</li>
<li><strong><code>robker::AbstractRobustifier = robustkernel(res::MyCost)</code></strong> (<em>optional</em>) returns the robust kernel data structure for the residual block. If this function isn't provided, the cost is the squared norm of the residual block.</li>
</ul>
<p dir="auto">A subtype of <code>AbstractResidual</code>, <code>AdaptiveAbstractResidual</code>, also exists. Instances of this abstract type should return a <code>robker::AbstractAdaptiveRobustifier</code> as the first value returned by the <code>getvars()</code> method, rather implementing the <code>robustkernel()</code> method. Otherwise, the API is similar to above. See examples/adaptivekernel.jl for an example.</p>
<p dir="auto"><code>AbstractCost</code> blocks should implement the following functions:</p>
<ul dir="auto">
<li><strong><code>cost::Float = computecost(costblock::MyCost, blockvars...)</code></strong> returns the computed residual block.</li>
<li><strong><code>cost::Float, grad::SVector{P, Float}, hess::SMatrix{P, P, Float} = computecostgradhess(::StaticInt{varflags}, costblock::MyCost, blockvars...)</code></strong> (<em>optional</em>) returns the computed cost and its gradient and Hessian, for all the variables whose corresponding bit in <code>varflags</code> is set. If this function isn't provided, the derivatives are computed using ForwardDiff auto-differentiation. <code>P</code> is the total dimensionality of the unfixed variable blocks.</li>
</ul>
<p dir="auto">A problem is then defined by creating an <code>NLLSProblem</code> object, and adding variable blocks and cost blocks to it using the <code>addvariable!</code> and <code>addcost!</code> methods respectively.</p>

<p dir="auto">Optimization is done as follows:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="    result::NLLSResult = optimize!(problem::NLLSProblem, options::NLLSOptions)"><pre class="notranslate"><code>    result::NLLSResult = optimize!(problem::NLLSProblem, options::NLLSOptions)
</code></pre></div>
<p dir="auto">Various optimizer <code>options</code> can be defined. During optimization, the optimizer updates variable blocks (stored in <code>problem</code>) in-place. Information about the optimization is retruned in <code>result</code>.</p>
