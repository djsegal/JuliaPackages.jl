<p dir="auto">A macro to add <code>isequal</code>, <code>==</code>, and <code>hash()</code> to struct types: <code>@auto_hash_equals</code>.</p>

<p dir="auto">The macro <code>@auto_hash_equals</code> produces an implementation of <code>Base.hash(x)</code> that computes the hash code when invoked.</p>
<p dir="auto">You use it like so:</p>

<span class="pl-k">end</span></pre></div>
<p dir="auto">which is translated to</p>

<p dir="auto">We do not take the type arguments of a generic type into account for <code>isequal</code>, <code>hash</code>, or <code>==</code> unless <code>typearg=true</code> is specified (see below).  So by default, a <code>Box{Int}(1)</code> will test equal to a <code>Box{Any}(1)</code>.</p>

<p dir="auto">You can have the hash value precomputed and stored in a hidden field, by adding the keyword argument <code>cache=true</code>. This useful for non-mutable struct types that define recursive or deep data structures (and therefore are likely to be stored on the heap).  It computes the hash code during construction and caches it in a field of the struct.  If you are working with data structures of any significant depth, computing the hash once can speed things up at the expense of one additional field per struct.</p>

<p dir="auto">The definition of <code>_show_default(io,x)</code> prevents display of the <code>_cached_hash</code> field while preserving the behavior of <code>Base.show(...)</code> that handles self-recursive data structures without a stack overflow.</p>
<p dir="auto">We provide an external constructor for generic types so that you get the same type inference behavior you would get in the absence of this macro.  Specifically, you can write <code>Box(1)</code> to get an object of type <code>Box{Int}</code>.</p>

By default they are not significant.  You can specify the default (they are not significant) with <code>typearg=false</code>:</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Specifying the "type seed"</h2><a id="user-content-specifying-the-type-seed" class="anchor" aria-label="Permalink: Specifying the &quot;type seed&quot;" href="#specifying-the-type-seed"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">When we compute the hash function, we start with a "seed" specific to the type being hashed.
By default, the seed is computed as <code>Base.hash(:TypeName)</code> if <code>typearg=false</code> (which is the default).
If <code>typearg=true</code> was specified, then the seed is computed as <code>type_seed(Type)</code>,
where <code>Type</code> is the type of the instance, including any type arguments.  <code>type_seed</code> is a
stable hash function defined (but not exported) in this package.</p>
<p dir="auto">You can select the seed to be used by specifying <code>typeseed=e</code>.</p>
<p dir="auto">The seed provided (<code>e</code>) is used in one of two ways, depending on the setting for <code>typearg</code>.
If <code>typearg=false</code> (the default), then the value <code>e</code> will be used as the type seed.
If <code>typearg=true</code>, then <code>e(t)</code> is used as the type seed, where <code>t</code> is the type of the object being hashed.</p>
<p dir="auto">Note that the value of <code>typeseed</code> is expected to be a <code>UInt</code> value when <code>typearg=false</code> (or <code>typearg</code> is not specified),
but a function that takes a type as its argument when <code>typearg=true</code>.</p>

<p dir="auto">In versions <code>v"1.0"</code> and earlier of <code>AutoHashEquals</code>, we produced a specialization of <code>Base.==</code>, implemented using <code>Base.isequal</code>.
This was not correct.
See <a href="https://docs.julialang.org/en/v1/base/base/#Base.isequal" rel="nofollow">https://docs.julialang.org/en/v1/base/base/#Base.isequal</a> and <a href="https://docs.julialang.org/en/v1/base/math/#Base.:==" rel="nofollow">https://docs.julialang.org/en/v1/base/math/#Base.:==</a>.
More correct would be to define <code>==</code> by using <code>==</code> on the members, and to define <code>isequal</code> by using <code>isequal</code> on the members.
In version <code>v"2.0"</code> we provide a correct implementation, thanks to @ericphanson.</p>
<p dir="auto">To get the same behavior as <code>v"1.0"</code> of this package, in which <code>==</code> is implemented based on <code>isequal</code>,
you can specify <code>compat1=true</code>.</p>
