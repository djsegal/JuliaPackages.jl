<p dir="auto">The <code>Distributed</code> package provides functionality for creating and controlling multiple Julia processes remotely, and for performing distributed and parallel computing. It uses network sockets or other supported interfaces to communicate between Julia processes, and relies on Julia's <code>Serialization</code> stdlib package to transform Julia objects into a format that can be transferred between processes efficiently. It provides a full set of utilities to create and destroy new Julia processes and add them to a "cluster" (a collection of Julia processes connected together), as well as functions to perform Remote Procedure Calls (RPC) between the processes within a cluster. See the <code>API</code> section for details.</p>
<p dir="auto">This package ships as part of the Julia stdlib.</p>

<p dir="auto">To use a newer version of this package, you need to build Julia from scratch. The build process is the same as any other build except that you need to change the commit used in <code>stdlib/Distributed.version</code>.</p>
<p dir="auto">It's also possible to load a development version of the package using <a href="https://github.com/JuliaLang/Pkg.jl#using-the-development-version-of-pkgjl">the trick used in the Section named "Using the development version of Pkg.jl" in the <code>Pkg.jl</code> repo</a>, but the capabilities are limited as all other packages will depend on the stdlib version of the package and will not work with the modified package.</p>

<p dir="auto">The public API of <code>Distributed</code> consists of a variety of functions for various tasks; for creating and destroying processes within a cluster:</p>
<ul dir="auto">
<li><code>addprocs</code> - create one or more Julia processes and connect them to the cluster</li>
<li><code>rmprocs</code> - shutdown and remove one or more Julia processes from the cluster</li>
</ul>
<p dir="auto">For controlling other processes via RPC:</p>
<ul dir="auto">
<li><code>remotecall</code> - call a function on another process and return a <code>Future</code> referencing the result of that call</li>
<li><code>Future</code> - an object that references the result of a <code>remotecall</code> that hasn't yet completed - use <code>fetch</code> to return the call's result, or <code>wait</code> to just wait for the remote call to finish</li>
<li><code>remotecall_fetch</code> - the same as <code>fetch(remotecall(...))</code></li>
<li><code>remotecall_wait</code> - the same as <code>wait(remotecall(...))</code></li>
<li><code>remote_do</code> - like <code>remotecall</code>, but does not provide a way to access the result of the call</li>
<li><code>@spawnat</code> - like <code>remotecall</code>, but in macro form</li>
<li><code>@spawn</code> - like <code>@spawn</code>, but the target process is picked automatically</li>
<li><code>@fetch</code> - macro equivalent of <code>fetch(@spawn expr)</code></li>
<li><code>@fetchfrom</code> - macro equivalent of <code>fetch(@spawnat p expr)</code></li>
<li><code>myid</code> - returns the <code>Int</code> identifier of the process calling it</li>
<li><code>nprocs</code> - returns the number of processes in the cluster</li>
<li><code>nworkers</code> - returns the number of worker processes in the cluster</li>
<li><code>procs</code> - returns the set of IDs for processes in the cluster</li>
<li><code>workers</code> - returns the set of IDs for worker processes in the cluster</li>
<li><code>interrupt</code> - interrupts the specified process</li>
</ul>
<p dir="auto">For communicating between processes in the style of a channel or stream:</p>
<ul dir="auto">
<li><code>RemoteChannel</code> - a <code>Channel</code>-like object that can be <code>put!</code> to or <code>take!</code> from any process</li>
</ul>
<p dir="auto">For controlling multiple processes at once:</p>
<ul dir="auto">
<li><code>WorkerPool</code> - a collection of processes than can be passed instead a process ID to certain APIs</li>
<li><code>CachingPool</code> - like <code>WorkerPool</code>, but caches functions (including closures which capture large data) on each process</li>
<li><code>@everywhere</code> - runs a block of code on all (or a subset of all) processes and waits for them all to complete</li>
<li><code>pmap</code> - performs a <code>map</code> operation where each element may be computed on another process</li>
<li><code>@distributed</code> - implements a <code>for</code>-loop where each iteration may be computed on another process</li>
</ul>

<p dir="auto">Julia processes connected with <code>Distributed</code> are all assigned a cluster-unique <code>Int</code> identifier, starting from <code>1</code>. The first Julia process within a cluster is given ID <code>1</code>, while other processes added via <code>addprocs</code> get incrementing IDs (<code>2</code>, <code>3</code>, etc.). Functions and macros which communicate from one process to another usually take one or more identifiers to determine which process they target - for example, <code>remotecall_fetch(myid, 2)</code> calls <code>myid()</code> on process 2.</p>
<p dir="auto"><strong>Note:</strong> Only process 1 (often called the "head", "primary", or "master") may add or remove processes, and manages the rest of the cluster. Other processes (called "workers" or "worker processes") may still call functions on each other and send and receive data, but <code>addprocs</code>/<code>rmprocs</code> on worker processes will fail with an error.</p>
