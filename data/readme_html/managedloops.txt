<p dir="auto"><code>ManagedLoops</code> defines an API to separate the task of writing loops from the task of defining how to
execute the loops (e.g. using SIMD, multiple threads, or on a GPU). In addition it provides convenience macros
<code>@unroll</code> to unroll loops whose length is known at <em>parse</em> time and <code>@vec</code> to mark loops as suitable for SIMD vectorization.</p>
<p dir="auto">The API is based on the abstract type <code>LoopManager</code> and its descendents, and on the function <code>offload</code>.
Manager types deriving from <code>LoopManager</code> offer different iteration strategies, see package <a href="https://github.com/ClimFlows/LoopManagers.jl"><code>LoopManagers</code></a>.
Function <code>offload</code> may be called directly (lower-level API), or may hide behind the <code>@loops</code> macro (higher-level API).</p>
<p dir="auto"><code>ManagedLoops</code> is very lightweight and depends only on <code>MacroTools</code>. Thus, making it a dependency of your "provider" modules, where number-crunching routines are defined, is very cheap. <a href="https://github.com/ClimFlows/LoopManagers.jl"><code>LoopManagers</code></a> is a more heavyweight package, but only "consumer" modules, those which create loop managers and pass them to functions, need to depend on it.</p>
<p dir="auto">Furthermore the high-level API is designed to have a small entry cost (loops must be placed in loop-only functions) and a zero exit cost:</p>
<ul dir="auto">
<li>If do not want to depend on <code>LoopManagers</code>,  pass <code>nothing</code> as the first argument of <code>@loops</code> functions and they will work "normally", as if <code>@loops</code> and <code>@vec</code> were not there.</li>
<li>If you decide to drop <code>ManagedLoops</code> altogether, simply remove <code>@loops</code> and <code>@vec</code> and your code just works.</li>
</ul>

<p dir="auto">Broadcast expressions such as <code>@. x = sin(y)</code> are semantically equivalent to loops. To manage the implied loop with <code>mgr::LoopManager</code>, use:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@. mgr[x] = sin(y)"><pre><span class="pl-c1">@.</span> mgr[x] <span class="pl-k">=</span> <span class="pl-c1">sin</span>(y)</pre></div>
<p dir="auto">or, if <code>x</code> is a function argument, pass <code>mgr[x]</code> instead of <code>x</code>. Since this works by specializing functions in Base Julia,
this can be used with function defined in modules that are not using <code>LoopManagers</code> at all.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="# function definition, possibly in a module that knows nothing about LoopManagers
f!(x,y) = @. x = sin(y)

# elsewhere call f(x,y) as usual
f!(x,y)
# we can also let `mgr::LoopManager` control the loops
f!(mgr[x], y)"><pre><span class="pl-c"><span class="pl-c">#</span> function definition, possibly in a module that knows nothing about LoopManagers</span>
<span class="pl-en">f!</span>(x,y) <span class="pl-k">=</span> <span class="pl-c1">@.</span> x <span class="pl-k">=</span> <span class="pl-c1">sin</span>(y)

<span class="pl-c"><span class="pl-c">#</span> elsewhere call f(x,y) as usual</span>
<span class="pl-c1">f!</span>(x,y)
<span class="pl-c"><span class="pl-c">#</span> we can also let `mgr::LoopManager` control the loops</span>
<span class="pl-c1">f!</span>(mgr[x], y)</pre></div>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">@unroll macro</h3><a id="user-content-unroll-macro" class="anchor" aria-label="Permalink: @unroll macro" href="#unroll-macro"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>@unroll (x^2 for x in (1,2,3))</code> expands to <code>(1^2, 2^2, 3^2)</code>.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="    @unroll for x in 1:3

    end"><pre>    <span class="pl-c1">@unroll</span> <span class="pl-k">for</span> x <span class="pl-k">in</span> <span class="pl-c1">1</span><span class="pl-k">:</span><span class="pl-c1">3</span>

<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="    myfun(1)

<p dir="auto"><code>ManagedLoops</code> also defines <code>parallel</code>, <code>barrier</code>, <code>master</code>, <code>share</code> to support
OpenMP-like execution with long-lived threads. This is currently experimental and not more performant than short-lived threads launched at each outer loop.</p>
