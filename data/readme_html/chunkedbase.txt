<p dir="auto">The package handles the ingestion of data chunks and the distribution &amp; synchronization of work that happens on these chunks in parallel. It came into existence while refactoring the <a href="https://github.com/RelationalAI/ChunkedCSV.jl"><code>ChunkedCSV.jl</code></a> and <a href="https://github.com/RelationalAI/ChunkedJSONL.jl"><code>ChunkedJSONL.jl</code></a> packages and was designed to be extended by packages like these. It is a package used to write parser packages.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Overview</h2><a id="user-content-overview" class="anchor" aria-label="Permalink: Overview" href="#overview"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The purpose of the package is to provide a framework for creating parsers for textual formats, where each record is separated by a newline character. Examples of such formats include CSV and JSONLines. The package is designed to operate on data chunks and to reuse preallocated buffers for each of these chunks. It simplifies the process of ingesting data, locating newlines, distributing work among multiple tasks, and synchronizing them. To implement a parsing package, one only needs to define how to <em>parse</em> the records and how to <em>consume</em> the parsed results.</p>
<p dir="auto">Parsing refers to taking the raw input bytes and the position of newlines that will be available to the user, and using a package like <code>Parsers.jl</code> or <code>JSON3.jl</code>, or some custom parsing code to produce records of Julia types that could be stored in user-defined result buffers, which can be customized e.g for row-oriented or column-oriented storage.</p>
<p dir="auto">Consuming refers to taking the parsed results and doing something with them, such as inserting them into a database, appending them to a <code>DataFrame</code>, or writing them to a file.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">How it works</h2><a id="user-content-how-it-works" class="anchor" aria-label="Permalink: How it works" href="#how-it-works"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Internally, <code>ChunkedBase.jl</code> uses a coordinator task and a set number of worker tasks to process data. The coordinator task is responsible for handling IO operations and acts as a coordinator for the worker tasks. It reads bytes from an input buffer and uses the <a href="https://github.com/JuliaData/NewlineLexers.jl"><code>NewlineLexers.jl</code></a> package to identify newlines in the data. Since the data is delimited by newlines, these newlines are used to split up the work among the worker tasks.</p>
<p dir="auto">The coordinator task alternates between two buffers, processing one while the workers process the other. This ensures that there is always data available for the workers to consume, which maximizes throughput across all tasks. We call this technique double-buffering.</p>

<td align="center"><em>The coordinator uses a counter behind a mutex to synchronize with the workers. After distributing the work, the coordinator starts to process the second chunk of data while the first buffer is still being worked on. A handoff occurs between the two buffers, where the bytes after the last newline from the first buffer are copied to the second. <p dir="auto">Packages like <code>ChunkedCSV.jl</code> and <code>ChunkedJSONL.jl</code> hook into this structure by defining their own <code>populate_result_buffer!</code> methods that parse the records they were assigned into their custom <code>Result</code> buffers which are then handed to the <code>consume!</code> method (e.g. to be inserted into a database).</p>
<p dir="auto">The main entry point of this package is the <code>parse_file_parallel</code> function, which accepts several "context" arguments, each controlling a different aspect of the process:</p>

<p dir="auto">Let's break it down:</p>
<ul dir="auto">
<li><code>lexer</code> controls how we find newlines in the ingested chunks of data. Newlines serve as record delimiters and knowing their positions allows us to split work safely among multiple workers, which are spawned internally. <code>Lexer</code>s are defined in the <code>NewlineLexers.jl</code> package.</li>
<li><code>parsing_ctx</code> controls how we parse the data. It allows the user to dispatch on custom <code>populate_result_buffer!</code> overload and to forward configurations to it. <code>populate_result_buffer!</code> is where we take the records identified by the <code>lexer</code> and parse them into <code>result_buffers</code>.</li>
<li><code>consume_ctx</code> controls how the parsed results are consumed (e.g. inserted into a database, appended to a <code>DataFrame</code>...). <code>consume_ctx</code> allows the user to dispatch on their <code>consume!</code> method and hold any state necessary for consumption. This happens immediately after <code>populate_result_buffer!</code>.</li>
<li><code>chunking_ctx</code> controls how the work on individual chunks of data is scheduled. It contains buffers for input bytes and found newlines. Through this struct the user controls the size of the chunks and the number of spawned tasks that carry out the parsing and consuming. If there is enough data in the input, a secondary <code>chunking_ctx</code> is created internally to facilitate the double-buffering described above.</li>
<li><code>result_buffers</code> controls in which format the results are stored. These result buffers hold results from <code>populate_result_buffer!</code> and are passed to <code>consume!</code>. This allows the user to have multiple result formats for the same <code>parsing_ctx</code> e.g. row-oriented vs column-oriented buffers.</li>
</ul>
<p dir="auto">There is also <code>parse_file_serial</code> which doesn't spawn any tasks and just calls <code>populate_result_buffer!</code> and <code>consume!</code> sequentially without double-buffering. This can be useful for debugging or for small files.</p>
<p dir="auto">See the docstring of <code>populate_result_buffer!</code> and <code>consume!</code> for more information about how to integrate with them.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Customizing work coordination</h3><a id="user-content-customizing-work-coordination" class="anchor" aria-label="Permalink: Customizing work coordination" href="#customizing-work-coordination"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Internally, the coordination of work happens through <code>setup_tasks!</code>, <code>task_done!</code> and <code>sync_tasks</code> functions which are defined in the <code>ConsumeContexts.jl</code> file. <code>setup_tasks!</code> sets the counter for the number of units of work that are expected to happen on the current chunk. <code>task_done!</code> is called by the worker tasks when they are done with their work, which will decrement the counter. <code>sync_tasks</code> is called by the coordinator task to wait for all workers to finish their work, i.e. for the counter to be 0. These functions are exposed to the user through the <code>AbstractConsumeContext</code> interface, so they can be overloaded to implement custom synchronization strategies. For example, if the user wants to send the parsed result buffers to external tasks from their <code>consume!</code> method and wait for <em>them</em> to be done with their work, they can overload <code>setup_tasks!</code> to increase the expected number of units of work and then call <code>task_done!</code> from the external tasks when they are done. This way, the coordinator task will wait for the external tasks to finish their work before refilling the buffer with new data. See the docstrings of these functions for more information.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Sniffing the beginning of the file</h3><a id="user-content-sniffing-the-beginning-of-the-file" class="anchor" aria-label="Permalink: Sniffing the beginning of the file" href="#sniffing-the-beginning-of-the-file"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Sometimes we want to skip over the first couple of lines of a file, e.g. when they contain comments or metadata, or we might want to set up our <code>AbstractParsingContext</code> with some information that is available at the beginning of the file (like the header names of a CSV).</p>
<p dir="auto">To do this, we can use fill our <code>ChunkingContext</code> with <code>read_and_lex!</code> which will read the first <code>buffersize</code> bytes from the input and lex them so that we can inspect the newlines and decide what to do with the file. We can use <code>skip_rows_init!</code> to skip over rows that we don't want to parse, and then use <code>parse_file_parallel</code> to parse the rest of the file, so our <code>populate_result_buffers!</code> method can focus on the "cleaner" part of the file.</p>
<p dir="auto">Instead of <code>read_and_lex!</code>, one could also call <code>initial_read!</code> and <code>initial_lex!</code> separately. This gives you the opportunity to detect which newline type is used in the file and set up your lexer accordingly.</p>
