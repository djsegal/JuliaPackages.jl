<p dir="auto">Cryptography is often looked at as a tool to secure and make communications confidential. It only requires to have a digital signature algorithm (DSA), Diffie Hellman key exchange (computation) and a good block cypher to satisfy the security requirements of 99% (metaphorically) of current online marketplaces and internet banking. However, security with those tools comes with a price of privacy and the necessity to trust the other end to keep your transactions private.</p>
<p dir="auto">A much more difficult case is present for systems that do require a high order of privacy and transparency, such as voting and auctions where an authority can not be blindly trusted, either with security or privacy. Complex multiparty protocols can be structured so that security and privacy do not lie in the hands of few. However, eliminating the effects of dishonest participants does require synchronous interactions between participants and thus is not scalable.</p>
<p dir="auto">Cryptography does offer an alternative known as zero-knowledge proofs (ZKP), which can often eliminate the need for synchronous interactions between participants to obtain an honest result. An excellent example is the zero-knowledge proof of shuffle, which we shall illustrate with a simple voting system.</p>
<p dir="auto">(Actually, arguments, but a common reference string can be constructed in a verifiably random way)</p>
<p dir="auto">It's best to illustrate it with the ElGamal cryptosystem. Let's say that officials have set up keypair <code>sk</code>, <code>pk = g^sk</code> and let everyone know <code>g, pk</code>.</p>
<ol dir="auto">
<li>A voter selects an option corresponding to a message <code>m</code>,  encrypts it with a freely secretly chosen randomisation factor <code>r</code> and obtains a tuple <code>c &lt;- (g^r, m*pk^r)</code>, which they submit to a bulletin board.</li>
<li>The votes are re-encrypted and shuffled
<ul dir="auto">
<li>each received ciphertext is re-encrypted as <code>c′ &lt;- (c[1]*g^p, c[2] * pk^p)</code></li>
<li>all re-encrypted ciphertexts are sorted, constituting a shuffle, and published to a bulletin board</li>
</ul>
</li>
<li>The authority who knows the secret key <code>sk</code> (<code>pk = g^sk</code>) decrypts each ciphertext <code>c′</code> as <code>m &lt;- c′[2] * c′[1]^(-sk)</code> and publishes that to a bulletin board.</li>
</ol>
<p dir="auto">This scheme, however, does pose serious drawbacks to election integrity. If the election authority is malicious, it can deviate from the re-encryption procedure in step 2. omit and substitute its own desired ciphertexts. Similarly, in the third step, nothing prevents the adversary from publishing their own desired decryption at step 3.</p>
<p dir="auto">Fortunately, zero-knowledge proofs are here to make such a system verifiable. Even if the adversary controlled, all election authorities would not be able to add, remove or modify votes.</p>

<p dir="auto">where ellection outcome is afterwards obtainned by tallying like <code>count(x-&gt; x == options[1], bbord.votes)</code>. Alternatively, homomorphic tallying could also be used, making it easier to airgap the system with a secret key.</p>
<p dir="auto">(A confused reader may assert that authority knowing the secret key, knows how every participant had voted. However, this is not so bad in practice. The last step of decryption can be done between multiple parties so no single party knows the full secret key. Alternatively, the decryption can happen in a gapless computer put in a Faraday cage only for ciphertexts which come out of reencryption step 2. A curious reader may delve into details Helios voting system, after which the example is modelled)</p>
<p dir="auto">Although all information is accessible to a bulletin board, we can not convince the voters that their votes have been properly counted and that adversary as corrupt authority or malware have not deviated from honest shuffling or decryption (steps 2 or 3) where it can add, modify or remove the votes.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Proving a correct shuffle</h2><a id="user-content-proving-a-correct-shuffle" class="anchor" aria-label="Permalink: Proving a correct shuffle" href="#proving-a-correct-shuffle"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">When we did a shuffle at step 2, the <code>shuffle</code> function returned two arguments: <code>proposition</code> and <code>secret</code>. The <code>proposition</code> contains all information about the statement whose truth should be asserted by a piece of evidence. The <code>secret</code> contains re-encryption factors and permutations. This can be used as evidence to validate the truth of the statement:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="verify(proposition, secret)"><pre class="notranslate"><code>verify(proposition, secret)
</code></pre></div>
<p dir="auto">However, if <code>secret</code> is used as evidence, it can't be made public; otherwise, it would violate the anonymity of the voters. Instead, we really want to prove that we know a <code>secret</code> such that <code>verify(proposition, secret) == true</code>, which in the literature is known as zero-knowledge proofs and, in particular, proofs of shuffle.</p>
<p dir="auto">Currently, WikstromTerelius proof of shuffle is the most widely used protocol implemented in Verificatum, CHVote and has been used to add verifiability for remote electronic voting systems in Estonia, Norway, Switzerland and others<sup><a href="#user-content-fn-5-a1acba9240604f6e0d0952ac065a89d0" id="user-content-fnref-5-a1acba9240604f6e0d0952ac065a89d0" data-footnote-ref="" aria-describedby="footnote-label">1</a></sup>. Verification, in particular, has a diligently written specification encouraging anyone willing to implement an independent verifier<sup><a href="#user-content-fn-1-a1acba9240604f6e0d0952ac065a89d0" id="user-content-fnref-1-a1acba9240604f6e0d0952ac065a89d0" data-footnote-ref="" aria-describedby="footnote-label">2</a></sup> so that proofs would not need to be trusted at face value. On the other hand, Haines<sup><a href="#user-content-fn-4-a1acba9240604f6e0d0952ac065a89d0" id="user-content-fnref-4-a1acba9240604f6e0d0952ac065a89d0" data-footnote-ref="" aria-describedby="footnote-label">3</a></sup> provides the most concise pseudocode for anyone willing to implement the prover but does deviate with verifier implementation from the Verifiactum protocol. The <code>ShuffleProofs.jl</code> implements a Verificatum verifier and compatible prover (so that the original Java code for Verificatum, in principle, could validate the integrity of a proof generated with <code>ShuffleProofs.jl</code>).</p>
<p dir="auto">To prove a statement for a corresponding proposition, it is necessary to instantiate a verifier which challenges the prover. A non-interactive zero-knowledge verifier compatible with Verifiactum can be initiated as:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="verifier = ProtocolSpec(; g) "><pre class="notranslate"><code>verifier = ProtocolSpec(; g) 
</code></pre></div>
<p dir="auto">It contains details on how independent basis vectors are chosen in a verifiable way, how challenges are computed from provers outputs like hash function to be used for random oracles and pseudo-random number generators, and how many bits are needed for pseudorandom numbers.</p>
<p dir="auto">With such a verifier, a proof can then be constructed easily as:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="proof = prove(proposition, secret, verifier)"><pre class="notranslate"><code>proof = prove(proposition, secret, verifier)
</code></pre></div>
<p dir="auto">Now finally, the proposition that no votes have been added, modified (spoiled) or removed at step 2. can be verified as:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="verify(proposition, proof, verifier)"><pre class="notranslate"><code>verify(proposition, proof, verifier)
</code></pre></div>
<p dir="auto">where <code>proof</code> and <code>verifier</code> can be published on the bulletin board along with the <code>proposition</code> so that everyone can verify the integrity of elections.</p>
<p dir="auto">Lastly, the <code>SuffleProofs.jl</code> implements a <code>shuffle(e::ElGamal, g, pk, verifier::Verifier)::Simulator</code>, which does the proof generation at the time of shuffling for convenience. The returned type then is <code>Simulator</code> which contains three fields <code>simulator.proposition</code> (discussed earlier), <code>simulator.verifier</code> and lastly, the proof as <code>simulator.proof</code>. The simulator contains all necessary information and can be published on the bulletin board (The exact way duplication of data is avoided up to the user of the library to decide).</p>

<p dir="auto">Initially, I implemented described prover and verifier, directly resembling the pseudocode Haines<sup><a href="#user-content-fn-4-a1acba9240604f6e0d0952ac065a89d0" id="user-content-fnref-4-2-a1acba9240604f6e0d0952ac065a89d0" data-footnote-ref="" aria-describedby="footnote-label">3</a></sup> paper and then later implemented the Verificatum verifier<sup><a href="#user-content-fn-1-a1acba9240604f6e0d0952ac065a89d0" id="user-content-fnref-1-2-a1acba9240604f6e0d0952ac065a89d0" data-footnote-ref="" aria-describedby="footnote-label">2</a></sup>. Unfortunately, implementing the Verificatum prover from the research papers was not within my capabilities, so I focused on merging both implementations. It became clear quickly that specifying challenges as multiple-function arguments would be highly cumbersome. To alleviate that, I made a verifier as an entry point of the finite state machine (FSM).</p>
<p dir="auto">Every verifier state does have two methods <code>step(verifier::Verifier, msg)::Verifier</code> where <code>msg</code> is new commitments from prover at a particular stage of execution. The other method is <code>challenge(verifier::Verifier)</code>, which returns a challenge to the prover upon which the protocol's security lies.</p>
<p dir="auto">For example, let's consider a verifier, <code>HonestVerifier</code>, which has chosen all challenges in advance. Although it is insecure, it will help to illustrate the point. We shall use the <code>PoSChallenge</code> type, which runs the last verification step, after which challenges from proof have been computed. The resulting implementation can be represented as:</p>

<p dir="auto"><code>HonestVerifier</code> here is a parametrised struct with enums, but in practice, each state does have its own relevant variables, and it makes sense to represent them with their own types. For example, see Verificatum verifier implementation in the <code>src/vverifier.jl</code>.</p>
<p dir="auto">The generality of the verifier can easily be extended to satisfy all kinds of variations available of WikstromTerelius proof of shuffle. For instance, an interactive protocol can be implemented in each challenge method to read from IO. Or verifier for <code>CHVote</code>, which computes the generator basis differently, can be supported by a subtyping verifier.</p>

<li>The current Julia implementation for the proof of shuffle is likely around 10...100 slower than the Verificatum Java library, as little care has been taken to make code type stable and minimise the number of allocations.</li>
</ul>
<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Braiding</h1><a id="user-content-braiding" class="anchor" aria-label="Permalink: Braiding" href="#braiding"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">An alternative use of proof of shuffle is to form knot-like structures or braids where inputs are related to outputs only through privately known exponents. As an example, consider private exponents <code>y = [2, 3, 4]</code> and some generator <code>g</code>. A list of public keys is <code>Y = [g^2, g^3, g^4]</code>.</p>
<p dir="auto">We can consider a mix which raises every public key in <code>Y</code> by a secret factor <code>x</code> and shuffles the list producing <code>Y' = [Y_3^x, Y_1^x, Y_2^x]</code> and publishes that together with a new relative generator <code>h = g^x</code>.</p>
<p dir="auto">In such a situation, owners of the private exponents can compute public keys with a relative generator <code>h</code> as <code>[h^2, h^3, h^4]</code>, which happens to be also available in <code>Y'</code>. This is useful as the owners of private exponents can issue anonymous signatures on messages with respect to relative generator <code>h</code> while asserting their membership to the group. This is useful in the context of voting system design or the protection of whistleblowers.</p>
<p dir="auto">The mix, however, in the above systems has the freedom to deviate from intended behaviour and replace undesirable public keys with his own. To avoid that, a zero-knowledge proof of shuffle can be used together with zero-knowledge proof of decryption to form a proof of correct braiding.</p>
<p dir="auto">To do such braiding, which produces proof of correctness <code>ShuffleProofs.jl</code> provides a <code>braid(generator::G, members::Vector{G}, verifier::Verifier)::Simulator</code>. A self-explanatory example is provided below:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="import CryptoGroups: curve, ECGroup, generator, specialize
