<p dir="auto">This library provides the basic tools for iterative pruning for Flux models. In particular, it provides prunable versions of all layers provided by Flux as well implementations of pruning strategies. The library also allows for easily producing a sparse representation of a model, after training and pruning has been completed.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Background</h2><a id="user-content-background" class="anchor" aria-label="Permalink: Background" href="#background"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The <em>Lottery Ticket Hypothesis</em> roughly states that deep, dense neural networks contain sparse subnetworks that account for most of the performance of the fully-parameterized model. For example, in some common architectures/tasks, subnetworks with fewer than 10% of the original number of parameters can be found that outperform the original model. Such subnetworks are called <em>winning tickets</em>.</p>
<p dir="auto">Finding winning tickets is challenging, but one common technique is to iteratively train a model, prune the bottom X% of parameters (by magnitude), reset the remaining weights to their original initialization, and train the model again. This process is repeated until the desired parameter count is reached or the model performance begins to degrade.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">General Implementation Notes</h2><a id="user-content-general-implementation-notes" class="anchor" aria-label="Permalink: General Implementation Notes" href="#general-implementation-notes"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This library revolves around wrapping Flux layers in a layer that captures and masks gradients. These layers contain the underlying layer, a set of masks, and a set copies of the original underlying weights. The prunable weights (usually dense matrices in the wrapped layer) have a corresponding mask (a boolean matrix of the same shape). If an index in the mask is <code>false</code>, it signals that the corresponding weight has been pruned. The underlying matrix weight will be set to zero, but this is not enough to ensure that the weight is pruned --- the gradients for that weight must also be set to zero during the backwards pass. The wrapped layers also include a copy of the original weight matrix (usually the initialization weights), so that the weights can be reset between training and pruning rounds.</p>
<p dir="auto">We use the the word <em>rewind</em> and <em>reset</em> interchangeably to mean resetting the weights of the underlying layer to their original initialization. In the API, this is always called <code>rewind</code>.</p>

<p dir="auto">All (trainable) Flux layers are supported by LotteryTickets.jl, with identical construction and calling signatures. For example, the <code>Dense</code> layer has an analogous <code>PrunableDense</code> type defined by LotteryTickets.jl. This type implements all of the constructors that <code>Dense</code> implements, as well as a way to construct a <code>PruneableDense</code> layer from a preexisting <code>Dense</code> specification. It also implements all of the calling conventions that <code>Dense</code> implements (that is, it accepts any input type that <code>Dense</code> would accept, and acts on it in the same way).</p>

<p dir="auto">When wrapping a new layer type, there is a not-so-small interface to implement (reducing the interface surface is a top priority for this project), but implementing each part is usually straightforward. It is best to follow the examples in <code>layers.jl</code> if you are stuck. The most basic one is <code>PrunableDense</code>, but you may also be interested in <code>PrunableRNNCell</code> for layers that have multiple outputs or <code>PrunableBilinear</code> for layers that have multiple inputs.</p>

<p dir="auto">where <code>c</code> is an instance of your <code>CustomLayer</code> and <code>orig_w1, ..., orig_wn</code> are the same type as the weights in your layer (these will store copies of the original weights) while <code>mask1, ..., maskn</code> are boolean matrices of the same shape as the corresponding weight.</p>
<p dir="auto">You should make this a functor by including the line:</p>
<p dir="auto"><code>Flux.@functor PrubableCustomLayer</code></p>
<p dir="auto">Then, you should mark the wrapped type as the only trainable parameter:</p>
<p dir="auto"><code>Flux.trainable(c::PrunableCustomLayer) = (; c = c.c)</code></p>
<p dir="auto">And you should mark your original layer as "convertable" (to a prunable layer):</p>

<p dir="auto">These allow for automatic conversion to the prunable wrapper via the <code>@prunable</code> macro.</p>
<p dir="auto">Then, you should implement:</p>
<ul dir="auto">
<li><code>PrunableCustomLayer(l::CustomLayer)</code>: construct a <code>PrunableCustomLayer</code> from a <code>CustomLayer</code>, which should copy all the original weights into <code>orig_w1, ..., orig_wn</code> and construct the appropriate sized masks.</li>
</ul>
<p dir="auto">You should also implement all the same construction signatures for <code>PrunableCustomLayer</code> as for <code>CustomLayer</code>, but usually this is as simple as defining:</p>
<p dir="auto"><code>PrunableCustomLayer(&lt;args&gt;) = PrunableCustomLayer(CustomLayer(&lt;args&gt;))</code></p>

<p dir="auto">For each caller method for <code>CustomLayer</code>, you should implement an analogous method for the <code>PrunableCustomLayer</code> type.</p>
<p dir="auto">This is usually as easy as <code>(c::PrunableCustomLayer)(x) = c.c(x)</code>. You may worry that the mask is not applied properly in this call, but the remaining API will properly mask out the weights when pruning is applied so that you should not have to worry about it during inference.</p>

<p dir="auto">The most complicated part is correctly defining the gradient masking for a new layer. In short, we want to capture the pullback of the wrapped type (the <code>CustomLayer</code> instance), mask its gradient, then pass that along as the gradient for the <code>PrunableCustomLayer</code>. For each call signature, you should implement a custom <code>Zygote.@adjoint</code>. In it, you want to compute the forward pass of the wrapped <code>CustomLayer</code>, but make a new pullback function that captures the <code>CustomLayer</code> gradient and applies the mask. Assume <code>CustomLayer</code> has a single-input call signature. Then you would define:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="Zygote.@adjoint function (c::PrunableCustomLayer)(x)

<p dir="auto">A few other methods are required, but are easy to implement:</p>
<ul dir="auto">
<li><code>prunableweights</code> - return the weights that can be pruned from the <em>wrapped</em> layer (e.g., <code>w1</code>, <code>w2</code>, ... from the wrapped <code>CustomLayer</code>)</li>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Pruners</h2><a id="user-content-pruners" class="anchor" aria-label="Permalink: Pruners" href="#pruners"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Prunable layers enable pruning, but <code>LotteryTickets.jl</code> implements the actual pruning procedures through <code>PruneGroups</code>. Roughly, a prune group is a collection of layers (and their prunable weights) as well as a pruning strategy. Layers in a pruning group are pruned collectively via the specified strategy.</p>
<p dir="auto">The basic pruner type is <em>magnitude pruning</em>, implemented by <code>MagnitudePruneGroup</code>, which takes a percentage <code>p</code> and prunes the bottom <code>p%</code> of parameters from the group by magnitude.</p>
<p dir="auto">Given a prunable model, a <code>MagnitudePruneGroup</code> can be specified by selecting the layers from the model to prune together and the pruning percentage.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="

<p dir="auto">Pruning groups are controlled by a <code>Pruner</code>, which activates all of the pruning groups' execution at the same time.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="

<p dir="auto">The layers within the prune group can be pruned, reset (to their original weights), or both.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Interface</h3><a id="user-content-interface-1" class="anchor" aria-label="Permalink: Interface" href="#interface-1"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">A prune group should implement the following interface:</p>
<ul dir="auto">
<li><code>prune!(g::AbstractPruneGroup)</code>: prune the layers in <code>g</code> by modifying the masks of each layer, and return <code>g</code></li>
</ul>
<p dir="auto">The remaining API is:</p>
<ul dir="auto">
<li><code>rewind!(g::AbstractPruneGroup)</code>: rewind all layers to their original weights (default behavior just calls <code>rewind!</code> on each layer)</li>
<li><code>pruneandrewind!(g::AbstractPruneGroup)</code>: prune then rewind all layers to their original weights (default behavior just calls <code>prune!(g)</code> then <code>rewind!(g)</code>)</li>
</ul>
<p dir="auto">These are defined for the <code>AbstractPruneGroup</code> type, but can be specified for your specific type if different functionality is desired.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Rough Edges</h2><a id="user-content-rough-edges" class="anchor" aria-label="Permalink: Rough Edges" href="#rough-edges"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">A small rough edge is with convolutional and bilinear layers. <code>Conv</code> and <code>Bilinear</code> are implemented as dense <em>tensors</em>, but <code>SparseArrays</code> only supports vectors and arrays. Thus, when calling <code>sparsify</code> on a <code>PrunableConv</code> or <code>PrunableBilinear</code> layer it will just result in a regular (dense) <code>Conv</code>/<code>Bilinear</code> layer, but with the pruned weights masked out.</p>
<p dir="auto">A major rough edge is the handling of layers that you don't want to prune. When resetting the network between pruning rounds, one may still want to reset these layers as well. The ideal way to do this is to wrap it in a prunable layer, but not prune it. To handle this, we have an <code>IdentityPruner</code> type that implements the same interface as other pruners, but simply doesn't prune any weights. This means it can still rewind the weights of its prunable layers.</p>
<p dir="auto">In our example above, you may want to replace the model definition with:</p>

<p dir="auto">and add another group <code>g3 = IdentityPruneGroup([m[4]])</code> to the <code>Pruner</code>.</p>
<p dir="auto">The second rough edge is also related to this issue. When calling <code>sparsify</code>, layers are converted to a sparse representation regardless of the level of sparsity of the underlying weights. In the pessimal case, layers that were not pruned at all (e.g., those that are in an <code>IdentityPruner</code> group) would be converted to a sparse representation despite being fully dense. As of right now, this library does not have a built-in way to handle this case, so it must be handled specially by the user. However, this should only happen at the very end of training and pruning, so it can be handled in a one-off fashion as a postprocessing step.</p>
<p dir="auto">Finally, there is currently no check that a layer exists only in one pruning group. The burden is on the caller to ensure that layers appear only in the desired groups.</p>

<p dir="auto">One may ask why we use dense matrices with weight masks to simulate pruned weights, rather than a sparse matrix representation. The main reason is that, until a matrix is <em>very</em> sparse, masking + dense matrix-matrix multiply is substantially faster than sparse matrix multiplication.</p>
<p dir="auto">The second reason is that, if gradient updates are not handled correctly, it is easy to accidently make a sparse matrix very dense (for example, by doing an element-wise addition). Using dense matrices + masking removes this issue at the cost of slightly more complex code.</p>
