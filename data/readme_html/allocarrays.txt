<p dir="auto">Prototype that attempts to allow usage of <a href="https://github.com/MasonProtter/Bumper.jl">Bumper.jl</a> (or potentially other allocation strategies) through code that doesn't know about Bumper.</p>
<p dir="auto">This is accomplished by creating a wrapper type <code>AllocArray</code> which dispatches <code>similar</code> dynamically to an allocator depending on the contextual scope (using <a href="https://github.com/vchuravy/ScopedValues.jl">ScopedValues.jl</a>).</p>
<p dir="auto">This package also provides a much safer <code>CheckedAllocArray</code> which keeps track of the validity
of each allocated array, to provide an error in case of access to an invalid array. This
can be used to test and develop code, before switching to <code>AllocArray</code> in case the overhead
of these checks is prohibitive.</p>
<p dir="auto">Demo:</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Design notes</h2><a id="user-content-design-notes" class="anchor" aria-label="Permalink: Design notes" href="#design-notes"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The user is responsible for constructing buffers (via <code>AllocBuffer</code> or the constructors <code>BumperAllocator</code> and <code>UncheckedBumperAllocator</code>) and for resetting them (<code>reset!</code>).
No implicit buffers are used, and <code>reset!</code> is never called in the package. These choices are deliberate: the caller must construct the buffer, pass it to AllocArrays.jl to be used when appropriate, and reset it when they are done.</p>
<p dir="auto">In particular, the caller must:</p>
<ul dir="auto">
<li>...not reset a buffer in active use. E.g., do not call <code>reset!</code> on a buffer that may be used by another task</li>
<li>...not allow memory allocated with a buffer to be live after the underlying buffer has been reset</li>
<li>...reset their buffers before it runs out of memory</li>
</ul>

<p dir="auto">Before using a bump allocator (<code>BumperAllocator</code>, or <code>UncheckedBumperAllocator</code>) it is recommended the user read the <a href="https://github.com/MasonProtter/Bumper.jl#bumperjl">Bumper.jl README</a> to understand how it works and what the limitations are.</p>
<p dir="auto">It is also recommended to start with <code>CheckedAllocArray</code> (with <code>BumperAllocator</code>)
and move to using <code>AllocArray</code> only when necessary on well-tested code.</p>
<p dir="auto">Note also:</p>
<ul dir="auto">
<li>Just as with all usage of Bumper.jl, the user is responsible for only using <code>reset!</code> when newly allocated arrays truly will not escape
<ul dir="auto">
<li>with AllocArrays this can be slightly more subtle, because within a <code>with_allocator</code> with a bump allocator  block, <code>similar</code> calls on <code>AllocArray</code> or <code>CheckedAllocArray</code>s will allocate using the bump allocator. Thus, one must be sure that none of those allocations leak past a <code>reset!</code>. The simplest way to do so is to be sure no allocations of any kind escape from a <code>reset!</code> block. You can pass in pre-allocated memory and fill that.</li>
</ul>
</li>
<li>Using an <code>UncheckedBumpAllocator</code> is not safe if allocations may occur concurrently. Since you may not know all the <code>similar</code> calls present in the code, this is a-priori dangerous to use.</li>
<li>Using <code>BumpAllocator</code> provides a semi-safe alternative simply by using a lock to control access to <code>buf</code>. In this way, the single buffer <code>buf</code> will be used to allocate for all <code>similar</code> calls (even across threads/tasks).
<ul dir="auto">
<li>However, <code>reset!</code> must be called outside of the threaded region, since deallocation in the bump allocator (via <code>reset!</code>) on one task will interfere with allocations on others.</li>
</ul>
</li>
</ul>
