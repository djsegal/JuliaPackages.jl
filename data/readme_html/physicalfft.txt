<p dir="auto">The main disadvantage of <code>PhysicalFDM.jl</code> is that the computational complexity (the matrix size) scales with <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$M^{d^d}$</math-renderer>,
where <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$M$</math-renderer> is the mesh size in each direction and <code>d</code> is the dimension of the problem.
Consequently, for meshes <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$\ge 16^3$</math-renderer>, the memory usage (<math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$\ge$</math-renderer> 64GB) and computation time (<math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$\ge$</math-renderer> 10 hrs) are not affordable.</p>
<p dir="auto"><code>PhysicalFFT.jl</code> supports resolution of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$512^3$</math-renderer> with minimum effort: 10 sec on both GPU (shared GPU memory is used) and CPU.
For meshes smaller than <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="b84cc4a75be6eae4f8bab1160113f63d">$256^3$</math-renderer>, the computation time on GPU is 1~4 orders of magnitude shorter than on CPU.
However, the vacuum boundary conditions, which are necessary for isolated gravitational systems,
are not yet supported in <code>PhysicalFFT.jl</code>.
Nevertheless, the errors from periodic boundary conditions are tolerable if the simulation box is sufficiently large compared to the system's length scale.</p>

<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using PhysicalFFT
using PhysicalFFT.PhysicalMeshes
using PhysicalMeshes.PhysicalParticles

sol(p::PVector) =  sin(2*pi*p.x) * sin(2*pi*p.y) * sin(2*pi*p.z) + sin(32*pi*p.x) * sin(32*pi*p.y) * sin(2*pi*p.z) / 256
init_rho(p::PVector) = -12 * pi * pi * sin(2*pi*p.x) * sin(2*pi*p.y) * sin(2*pi*p.z) - 12 * pi * pi * sin(32*pi*p.x) * sin(32*pi*p.y) * sin(32*pi*p.z)

function test_fft3D(Nx, boundary=Periodic())
    m = MeshCartesianStatic(;
        xMin = 0.0,
        yMin = 0.0,
        zMin = 0.0,
        xMax = 1.0,
        yMax = 1.0,
        zMax = 1.0,
        Nx = Nx - 1,
        Ny = Nx - 1,
        Nz = Nx - 1,
        NG = 0,
        dim = 3,
        boundary,
    )
    m.rho .= init_rho.(m.pos)
    fft_poisson!(m, m.rho, m.config.boundary)
    s = sol.(m.pos)
    r = m.phi .- s

    return L2norm(r)
end
