<p dir="auto"><strong>FinanceModels.jl</strong> provides a set of composable contracts, models, and functions that allow for modeling of both simple and complex financial instruments. The resulting models, such as discount rates or term structures, can then be used across the JuliaActuary ecosystem to perform actuarial and financial analysis.</p>
<p dir="auto">Additionally, the models can be used to project contracts through time: most basically as a series of cashflows but more complex output can be defined for contracts.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Overview of FinanceModels</h2><a id="user-content-overview-of-financemodels" class="anchor" aria-label="Permalink: Overview of FinanceModels" href="#overview-of-financemodels"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><a target="_blank" rel="noopener noreferrer" href="/docs/src/assets/relations.png"><img src="/docs/src/assets/relations.png" alt="A conceptual sketch of FinanceModels.jl" style="max-width: 100%;"></a></p>
<p dir="auto">Often we start with observed or assumed values for existing contracts. We want to then use those assumed values to extend the valuation logic to new contracts. For example, we may have a set of bond yields which we then want to discount a series of insurance obligations.</p>
<p dir="auto">In the language of FinanceModels, we would have a set of <code>Quote</code>s which are used to fit a <code>Model</code>. That model is then used to <code>discount</code> a new series of cashflows.</p>
<p dir="auto">That's just an example, and we can use the various components in different ways depending on the objective of the analysis.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Contracts and Quotes</h3><a id="user-content-contracts-and-quotes" class="anchor" aria-label="Permalink: Contracts and Quotes" href="#contracts-and-quotes"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Contracts are a way to represent financial obligations. These can be valued using a model, projected into a future steam of values, or combined with assumed prices as a <code>Quote</code>.</p>
<p dir="auto">Included are a number of primitives and convenience methods for contracts:</p>
<p dir="auto">Existing <code>struct</code>s:</p>
<ul dir="auto">
<li><code>Cashflow</code></li>
<li><code>Bond.Fixed</code></li>
<li><code>Bond.Floating</code></li>
<li><code>Forward</code> (an obligation with a forward start time)</li>
<li><code>Composite</code> (combine two other contracts, e.g. into a swap)</li>
<li><code>EuroCall</code></li>
<li><code>CommonEquity</code></li>
</ul>
<p dir="auto">Commonly, we deal with conventions that imply a contract and an observed price. For example, we may talk about a treasury yield of <code>0.03</code>. This is a description that implies a <code>Quote</code>ed price for an underling fixed bond. In FinanceModels, we could use <code>CMTYield(rate,tenor)</code> which would create a <code>Quote(price,Bond.Fixed(...))</code>. In this way, we can conveniently create a number of <code>Quote</code>s which can be used to fit models. Such convenience methods include:</p>
<ul dir="auto">
<li><code>ZCBYield</code></li>
<li><code>ZCBPrice</code></li>
<li><code>CMTYield</code></li>
<li><code>ParYield</code></li>
<li><code>ParSwapYield</code></li>
<li><code>ForwardYield</code></li>
</ul>
<p dir="auto">FinanceModels offers a way to define new contracts as well.</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Cashflows</h4><a id="user-content-cashflows" class="anchor" aria-label="Permalink: Cashflows" href="#cashflows"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">A <code>Cashflow</code>s obligation are themselves a contract, but other contracts can be considered as essentially anything that can be combined with assumptions (a <strong>model</strong>) to derive a collection of cashflows.</p>
<p dir="auto">For example, a obligation that pays 1.75 at time 2 could be represented as: <code>Cashflow(1.75,2)</code>.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Models</h3><a id="user-content-models" class="anchor" aria-label="Permalink: Models" href="#models"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Models are objects that can be fit to observed prices and then subsequently used to make valuations of other cashflows/contracts.</p>
<p dir="auto">Yield models include:</p>
<ul dir="auto">
<li><code>Yield.Constant</code></li>
<li>Bootstrapped <code>Spline</code>s</li>
<li><code>Yield.SmithWilson</code></li>
<li><code>Yield.NelsonSiegel</code></li>
<li><code>Yield.NelsonSiegelSvensson</code></li>
</ul>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Yield-related functions</h4><a id="user-content-yield-related-functions" class="anchor" aria-label="Permalink: Yield-related functions" href="#yield-related-functions"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The models can be used to compute various rates of interest:</p>
<ul dir="auto">
<li><code>discount(curve,from,to)</code> or <code>discount(curve,to)</code> gives the discount factor</li>
<li><code>accumulation(curve,from,to)</code> or <code>accumulation(curve,to)</code> gives the accumulation factor</li>
<li><code>zero(curve,time)</code> or <code>zero(curve,time,Frequency)</code> gives the zero-coupon spot rate for the given time.</li>
<li><code>forward(curve,from,to)</code> gives the zero rate between the two given times</li>
<li><code>par(curve,time;frequency=2)</code> gives the coupon-paying par equivalent rate for the given time.</li>
</ul>
<p dir="auto">Other models include:</p>
<ul dir="auto">
<li><code>BlackScholesMerton</code> derivative valuation</li>

<p dir="auto">However, <code>Projection</code>s allow one to combine three elements which can be extended to define any desired output (such as amortization schedules, financial statement projections, or account value rollforwards). The three elements are:</p>
<ul dir="auto">
<li>the underlying <strong>contract</strong> of interest</li>
<li>the <strong>model</strong> which includes assumptions of how the contract will behave</li>
<li>a <code>ProjectionKind</code> which indicates the kind of output desired (cashflow stream, amortization schedule, etc...)</li>
</ul>

<p dir="auto">Rates are types that wrap scalar values to provide information about how to determine <code>discount</code> and <code>accumulation</code> factors.</p>
<p dir="auto">There are two <code>Frequency</code> types:</p>
<ul dir="auto">
<li><code>Periodic(m)</code> for rates that compound <code>m</code> times per period (e.g. <code>m</code> times per year if working with annual rates).</li>
<li><code>Continuous()</code> for continuously compounding rates.</li>
</ul>

<p dir="auto">Generally, CamelCase methods which construct a datatype are exported as they are unlikely to conflict with other parts of code that may be written, but other components must either be qualified by the inner module (e.g. <code>Bond.Fixed</code>) or the package module, e.g. <code>FinanceModels.cashflow_timepoints</code> to use un-exported names.</p>
<p dir="auto">Consider using <code>import FinanceModels</code> which would require qualifying all methods, but alleviates any namespace conflicts and has the benefit of being explicit about the calls (internally we prefer this in the package design to keep dependencies and their usage clear).</p>
