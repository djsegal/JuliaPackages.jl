<p dir="auto"><em><code>Revise</code>-compatible hot-reloading middleware for web development in Julia</em></p>
<p dir="auto">Development utilities for improving your workflow when building web
applications in pure-Julia. This package integrates with <code>Revise</code> and <code>HTTP</code> to
allow for automatic hot-reloading pages with "in-place" DOM-swapping rather
than full-page refreshes.</p>

<p dir="auto">Calling <code>hot.refresh()</code> will cause any clients connected to the server to
reload their page. The reload is done "in-place" by swapping out the DOM
content with the new content for a page rather than doing a full page refresh.</p>
<p dir="auto">This does not perform any file-watching or other automatic reloading. It is
intended to be used in conjunction with separate file-watching utilities such
as the <code>FileWatching</code> module.</p>

<p dir="auto">This type can be used to automatically create an <code>HTTP.Router</code> based on the functions
defined in a given module, or modules. The router automatically updates itself when
changes are detected by <code>Revise</code> if a <code>HotReloader</code> is present in the router stack.</p>
<p dir="auto">You can define functions within a module that should act as endpoints for the
router with the <code>@route</code> and <code>@req</code> macros. Some examples follow which describe
the general form of the <code>@req</code> macro and what it supports. <code>@route</code> simply marks the
function as a route handler.</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">The <code>/api</code> route and "API Explorer" UI</h2><a id="user-content-the-api-route-and-api-explorer-ui" class="anchor" aria-label="Permalink: The /api route and &quot;API Explorer&quot; UI" href="#the-api-route-and-api-explorer-ui"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">During development it can be useful to have a way to explore the API that your
server exposes. To this end, the <code>ModuleRouter</code> automatically adds a <code>/api</code>
route to the router which can be used to explore the API via a web interface.
In production (when <code>Revise</code> is loaded) this route does not exist. If the
default <code>/api</code> route conflicts with your application then you can change the
route by passing the <code>api_route</code> keyword argument to the <code>ModuleRouter</code>
constructor.</p>
<p dir="auto">Each endpoint that your application exposes is displayed as a separate page
which includes all <code>param</code>, <code>query</code>, and <code>form</code> fields that are defined for
that endpoint. In addition, any docstrings attached to endpoints are included
in the page for easy reference.</p>
<p dir="auto">When the <code>HotReloader</code> middleware is present in the router stack then the <code>/api</code>
route will automatically update itself when changes are made to any routes, such
as docstring changes, or changes to the <code>@req</code> macros that define the routes.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>@req</code> syntax</h3><a id="user-content-req-syntax" class="anchor" aria-label="Permalink: @req syntax" href="#req-syntax"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@req(method, path, [query], [form])"><pre><span class="pl-c1">@req</span>(method, path, [query], [form])</pre></div>
<p dir="auto">where <code>method</code> can be any of</p>
<ul dir="auto">
<li><code>GET</code></li>
<li><code>POST</code></li>
<li><code>PUT</code></li>
<li><code>DELETE</code></li>
<li><code>PATCH</code></li>
<li><code>"*"</code> (due to Julia's macro syntax this must be a string literal)</li>
</ul>
<p dir="auto"><code>path</code> is either a plain <code>String</code> literal representing the path, or a string
literal with interpolated values. Interpolated values are parsed as follows:</p>
<ul dir="auto">
<li><code>$(x)</code> is parsed as a <code>String</code> value for the field named <code>x</code>.</li>
<li><code>$(x::T)</code> is parsed as a value of type <code>T</code> where <code>T</code> is any type that can be
parsed from a <code>String</code> via <code>Base.parse</code> for the field named <code>x</code>.</li>
</ul>
<p dir="auto">These values are then available as fields in the <code>params</code> field of the <code>Req</code> object
passed to the function. For example, the following function:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="@route function get_post(req::@req GET &quot;/blog/$(id::Base.UUID)&quot;)
    req.params.id # This is a `Base.UUID` value.
end"><pre><span class="pl-c1">@route</span> <span class="pl-k">function</span> <span class="pl-en">get_post</span>(req<span class="pl-k">:</span>:<span class="pl-c1">@req</span> GET <span class="pl-s"><span class="pl-pds">"</span>/blog/<span class="pl-v">$(id<span class="pl-k">::</span><span class="pl-c1">Base.UUID</span>)</span><span class="pl-pds">"</span></span>)
    req<span class="pl-k">.</span>params<span class="pl-k">.</span>id <span class="pl-c"><span class="pl-c">#</span> This is a `Base.UUID` value.</span>
<span class="pl-k">end</span></pre></div>
<p dir="auto">The optional <code>query</code> and <code>form</code> fields are used to parse query parameters and
form data respectively. These fields are parsed as follows:</p>
<ul dir="auto">
<li><code>query = {x}</code> or <code>form = {x}</code> is parsed as a query parameter named <code>x</code> which
is parsed as a <code>String</code> value.</li>
<li><code>query = {x::T}</code> or <code>form = {x::T}</code> is parsed as a query parameter named <code>x</code>
which is parsed as a value of type <code>T</code> where <code>T</code> is any type that can be
parsed from a <code>String</code> via <code>Base.parse</code>, the same as for <code>params</code> above.
If the parameter needs to contain multiple values, e.g. <code>a=1&amp;a=2</code> then <code>T</code> can
be a <code>Vector</code> of the type of the individual values in which case the value of
<code>a</code> will be <code>["1", "2"]</code> when <code>Vector{String}</code> is specified.</li>
<li>any number of fields can be specified in the <code>{...}</code> syntax, separated by
commas.</li>
<li>default values can be specified by using <code>x = default</code> instead of <code>x</code> in the
above syntax. Or <code>x::T = default</code> for a typed default value. These values are
created on-demand when the parameter is not present in the request and are not
created until needed.</li>
</ul>
<p dir="auto"><code>form</code> data by default assumes that the request body syntax is
<code>application/x-www-form-urlencoded</code> and that that the <code>Content-Type</code> header is
set to <code>application/x-www-form-urlencoded</code>. Parsing of this text is done using
<code>URIs.parseparams(s::AbstractString)</code>.</p>

<p dir="auto">JSON data parsing can be enabled by setting the <code>Content-Type</code> header to
<code>application/json</code> in the request. This will cause the <code>form</code> fields to be
parsed as JSON instead of as form data. The <code>{...}</code> syntax is still used, so
each field in the <code>NamedTuple</code> to is parsed is a JSON-parsed value. <code>JSON3.jl</code>
is used for the parsing, and as such we support using custom Julia types for
the resulting values so long as suitable <code>StructType</code> definitions are provided.
Please see the <code>JSON3.jl</code> documentation for more information on this topic.</p>

<p dir="auto">Multi-part form data can be parsed by setting the <code>Content-Type</code> header to
<code>multipart/form-data</code> in the request. This will cause the <code>form</code> fields to be
parsed as multi-part form data instead of url encoded, or JSON data. The <code>{...}</code>
syntax is still used, and each field in the <code>NamedTuple</code> is a single value from
the submitted form data that is deserialized into the declared type separately.</p>
