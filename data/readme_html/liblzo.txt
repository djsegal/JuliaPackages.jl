<p dir="auto">This package exports the following methods for interfacing with liblzo2:</p>
<ul dir="auto">
<li><code>compress(algo, src::AbstractVector{UInt8})</code>: compress data in <code>src</code> using algorithm <code>algo</code> and return the result.</li>
<li><code>unsafe_compress!(algo, dest::AbstractVector{UInt8}, src::AbstractVector{UInt8})</code>: compress data from <code>src</code> to <code>dest</code> using algorithm <code>algo</code> with no overflow checking and return the number of bytes overwritten at the front of <code>dest</code>.</li>
<li><code>decompress(algo, src::AbstractVector{UInt8})</code>: decompress data in <code>src</code> using algorithm <code>algo</code> and return the result.</li>
<li><code>decompress!(algo, dest::AbstractVector{UInt8}, src::AbstractVector{UInt8})</code>: decompress data in <code>src</code> to <code>dest</code> in-place using algorithm <code>algo</code> and return the number of bytes written, or throw an exception if <code>dest</code> is not large enough to hold the decompressed version of <code>src</code>.</li>
<li><code>unsafe_decompress!(algo, dest::AbstractVector{UInt8}, src::AbstractVector{UInt8})</code>: decompress data from <code>scr</code> to <code>dest</code> using algorithm <code>algo</code> with no overflow checking and return the number of bytes overwritten at the front of <code>dest</code>.</li>
<li><code>optimize!(algo, src::AbstractVector{UInt8})</code>: attempt to reduce the size of data in <code>src</code> that was compressed using algorithm <code>algo</code>, operating on <code>src</code> in-place.</li>
<li><code>unsafe_optimze!(algo, dest::AbstractVector{UInt8}, src::AbstractVector{UInt8})</code>: attempt to reduce the size of data in <code>src</code> that was compressed using algorithm <code>algo</code> by decompressing it into <code>dest</code> with no overflow checking, operating on <code>src</code> in-place.</li>
</ul>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">"Unsafe" means UNSAFE!</h3><a id="user-content-unsafe-means-unsafe" class="anchor" aria-label="Permalink: &quot;Unsafe&quot; means UNSAFE!" href="#unsafe-means-unsafe"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The <code>unsafe_*</code> methods are truly unsafe: if the user-supplied destination vector is not large enough to hold the output, the <a href="https://en.cppreference.com/w/c/language/behavior" rel="nofollow">behavior is undefined</a> and <a href="https://devblogs.microsoft.com/oldnewthing/20140627-00/?p=633" rel="nofollow">very bad things could happen</a>. Unless you are absolutely sure about what you are doing and are in complete control of the source data, use the <code>compress</code>, <code>decompress</code>/<code>decompress!</code>, and <code>optimize!</code> methods instead.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Always use the same algorithm family that was used to compress data to decompress that data</h3><a id="user-content-always-use-the-same-algorithm-family-that-was-used-to-compress-data-to-decompress-that-data" class="anchor" aria-label="Permalink: Always use the same algorithm family that was used to compress data to decompress that data" href="#always-use-the-same-algorithm-family-that-was-used-to-compress-data-to-decompress-that-data"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This should go without saying, but if you attempt to decompress data with a different algorithm than was used to compress the data, undefined behavior will occur. This will typically result in an exception being thrown by the safe <code>decompress</code>/<code>decompress!</code> methods, but not always: for instance, data compressed by the LZO1X family can usually be decompressed using the LZO1Y family without throwing an exception, but the output will be gibberish. There is no good way for the <code>decompress</code>/<code>decompress!</code> methods to detect the algorithm used to compress the data, so it is up to the user to keep the compression and decompression algorithms aligned.</p>
<p dir="auto">That being said, all algorithms in the same algorithm <em>family</em> use the same underlying decompression function. You can, for instance, compress data using <code>LZO1X_1</code> and decompress it using <code>LZO1X_999</code> without any issues.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Safe decompression may mean multiple attempts to decompress</h3><a id="user-content-safe-decompression-may-mean-multiple-attempts-to-decompress" class="anchor" aria-label="Permalink: Safe decompression may mean multiple attempts to decompress" href="#safe-decompression-may-mean-multiple-attempts-to-decompress"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The safe decompression method <code>decompress</code> works by attempting to decompress the source into a destination vector, catching the overrun exception returned by the liblzo2 library, then increasing the size of the destination and trying again until the decompression succeeds. This means the method may take several times longer and make more allocations than expected to successfully decompress data. If decompression speed or memory efficiency is paramount, use the in-place <code>decompress!</code> or <code>unsafe_decompress!</code> methods, but <strong>be warned that "unsafe" means UNSAFE</strong> (see above).</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Optimization doesn't do much, if anything at all</h3><a id="user-content-optimization-doesnt-do-much-if-anything-at-all" class="anchor" aria-label="Permalink: Optimization doesn't do much, if anything at all" href="#optimization-doesnt-do-much-if-anything-at-all"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The optimization feature of the LZO1X and LZO1Y family of algorithms attempts to shuffle around literal copy commands to save on storage and potentially improve decompression speed. Because of the rarity of the special circumstances required to shuffle the literal copy commands around, optimization is expected to reduce the number of bytes necessary to store the compressed data by at most 0.01%, and benchmarks I have performed on modern processors show no difference in decompression speeds between optimized and unoptimized data. The methods are included for completeness' sake, but I do not recommend their use.</p>
<p dir="auto">Because the compressed data have to be completely decompressed into memory during the optimization process, the safe <code>optimize!</code> method has to allocate enough memory to guarantee the decompressed data will fit, and that is typically 100 times more memory than necessary. If you insist on optimizing your data, I recommend running <code>unsafe_optimize!</code> immediately after <code>compress</code>, using the original source data as the destination for <code>unsafe_optimize!</code>. This guarantees that there will be just enough memory available to perform the optimization:</p>
