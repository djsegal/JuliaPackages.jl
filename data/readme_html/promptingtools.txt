<p dir="auto">Streamline your life using PromptingTools.jl, the Julia package that simplifies interacting with large language models.</p>
<p dir="auto">PromptingTools.jl is not meant for building large-scale systems. It's meant to be the go-to tool in your global environment that will save you 20 minutes every day!</p>

<p dir="auto">Getting started with PromptingTools.jl is as easy as importing the package and using the <code>@ai_str</code> macro for your questions.</p>
<p dir="auto">Note: You will need to set your OpenAI API key as an environment variable before using PromptingTools.jl (see the <a href="#creating-openai-api-key">Creating OpenAI API Key</a> section below).</p>
<p dir="auto">Following the introduction of <a href="https://help.openai.com/en/articles/8264644-what-is-prepaid-billing" rel="nofollow">Prepaid Billing</a>, you'll need to buy some credits to get started ($5 minimum).
For a quick start, simply set it via <code>ENV["OPENAI_API_KEY"] = "your-api-key"</code></p>
<p dir="auto">Install PromptingTools:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using Pkg
Pkg.add(&quot;PromptingTools&quot;)"><pre><span class="pl-k">using</span> Pkg
Pkg<span class="pl-k">.</span><span class="pl-c1">add</span>(<span class="pl-s"><span class="pl-pds">"</span>PromptingTools<span class="pl-pds">"</span></span>)</pre></div>
<p dir="auto">And we're ready to go!</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Why PromptingTools.jl</h2><a id="user-content-why-promptingtoolsjl" class="anchor" aria-label="Permalink: Why PromptingTools.jl" href="#why-promptingtoolsjl"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Prompt engineering is neither fast nor easy. Moreover, different models and their fine-tunes might require different prompt formats and tricks, or perhaps the information you work with requires special models to be used. PromptingTools.jl is meant to unify the prompts for different backends and make the common tasks (like templated prompts) as simple as possible.</p>
<p dir="auto">Some features:</p>
<ul dir="auto">
<li><strong><code>aigenerate</code> Function</strong>: Simplify prompt templates with handlebars (eg, <code>{{variable}}</code>) and keyword arguments</li>
<li><strong><code>@ai_str</code> String Macro</strong>: Save keystrokes with a string macro for simple prompts</li>
<li><strong>Easy to Remember</strong>: All exported functions start with <code>ai...</code> for better discoverability</li>
<li><strong>Light Wrapper Types</strong>: Benefit from Julia's multiple dispatch by having AI outputs wrapped in specific types</li>
<li><strong>Minimal Dependencies</strong>: Enjoy an easy addition to your global environment with very light dependencies</li>
<li><strong>No Context Switching</strong>: Access cutting-edge LLMs with no context switching and minimum extra keystrokes directly in your REPL</li>
</ul>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>ai*</code> Functions Overview</h3><a id="user-content-ai-functions-overview" class="anchor" aria-label="Permalink: ai* Functions Overview" href="#ai-functions-overview"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Noteworthy functions: <code>aigenerate</code>, <code>aiembed</code>, <code>aiclassify</code>, <code>aiextract</code>, <code>aiscan</code>, <code>aiimage</code>, <code>aitemplates</code></p>
<p dir="auto">All <code>ai*</code> functions have the same basic structure:</p>
<p dir="auto"><code>ai*(&lt;optional schema&gt;,&lt;prompt or conversation&gt;; &lt;optional keyword arguments&gt;)</code>,</p>
<p dir="auto">but they differ in purpose:</p>
<ul dir="auto">
<li><code>aigenerate</code> is the general-purpose function to generate any text response with LLMs, ie, it returns <code>AIMessage</code> with field <code>:content</code> containing the generated text (eg, <code>ans.content isa AbstractString</code>)</li>
<li><code>aiembed</code> is designed to extract embeddings from the AI model's response, ie, it returns <code>DataMessage</code> with field <code>:content</code> containing the embeddings (eg, <code>ans.content isa AbstractArray</code>)</li>
<li><code>aiextract</code> is designed to extract structured data from the AI model's response and return them as a Julia struct (eg, if we provide <code>return_type=Food</code>, we get <code>ans.content isa Food</code>). You need to define the return type first and then provide it as a keyword argument.</li>
<li><code>aiclassify</code> is designed to classify the input text into (or simply respond within) a set of discrete <code>choices</code> provided by the user. It can be very useful as an LLM Judge or a router for RAG systems, as it uses the "logit bias trick" and generates exactly 1 token. It returns <code>AIMessage</code> with field <code>:content</code>, but the <code>:content</code> can be only one of the provided <code>choices</code> (eg, <code>ans.content in choices</code>)</li>
<li><code>aiscan</code> is for working with images and vision-enabled models (as an input), but it returns <code>AIMessage</code> with field <code>:content</code> containing the generated text (eg, <code>ans.content isa AbstractString</code>) similar to <code>aigenerate</code>.</li>
<li><code>aiimage</code> is for generating images (eg, with OpenAI DALL-E 3). It returns a <code>DataMessage</code>, where the field <code>:content</code> might contain either the URL to download the image from or the Base64-encoded image depending on the user-provided kwarg <code>api_kwargs.response_format</code>.</li>
<li><code>aitemplates</code> is a helper function to discover available templates and see their details (eg, <code>aitemplates("some keyword")</code> or <code>aitemplates(:AssistantAsk)</code>)</li>
</ul>
<p dir="auto">If you're using a known <code>model</code>, you do NOT need to provide a <code>schema</code> (the first argument).</p>
<p dir="auto">Optional keyword arguments in <code>ai*</code> tend to be:</p>
<ul dir="auto">
<li><code>model::String</code> - Which model you want to use</li>
<li><code>verbose::Bool</code> - Whether you went to see INFO logs around AI costs</li>
<li><code>return_all::Bool</code> - Whether you want the WHOLE conversation or just the AI answer (ie, whether you want to include your inputs/prompt in the output)</li>
<li><code>api_kwargs::NamedTuple</code> - Specific parameters for the model, eg, <code>temperature=0.0</code> to be NOT creative (and have more similar output in each run)</li>
<li><code>http_kwargs::NamedTuple</code> - Parameters for the HTTP.jl package, eg, <code>readtimeout = 120</code> to time out in 120 seconds if no response was received.</li>
</ul>
<p dir="auto"><strong>Experimental: AgentTools</strong></p>
<p dir="auto">In addition to the above list of <code>ai*</code> functions, you can also use the <strong>"lazy" counterparts</strong> of these functions from the experimental AgentTools module.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using PromptingTools.Experimental.AgentTools"><pre><span class="pl-k">using</span> PromptingTools<span class="pl-k">.</span>Experimental<span class="pl-k">.</span>AgentTools</pre></div>
<p dir="auto">For example, <code>AIGenerate()</code> will create a lazy instance of <code>aigenerate</code>. It is an instance of <code>AICall</code> with <code>aigenerate</code> as its ai function.
It uses exactly the same arguments and keyword arguments as <code>aigenerate</code> (see <code>?aigenerate</code> for details).</p>
<p dir="auto">"lazy" refers to the fact that it does NOT generate any output when instantiated (only when <code>run!</code> is called).</p>
<p dir="auto">Or said differently, the <code>AICall</code> struct and all its flavors (<code>AIGenerate</code>, ...) are designed to facilitate a deferred execution model (lazy evaluation) for AI functions that interact with a Language Learning Model (LLM). It stores the necessary information for an AI call and executes the underlying AI function only when supplied with a <code>UserMessage</code> or when the <code>run!</code> method is applied. This allows us to remember user inputs and trigger the LLM call repeatedly if needed, which enables automatic fixing (see <code>?airetry!</code>).</p>
<p dir="auto"><strong>Experimental: RAGTools</strong></p>
<p dir="auto">Lastly, we provide a set of tools to build RAG applications (Retrieve, Answer, Generate).</p>
<p dir="auto">It can be as simple as two calls: <code>build_index</code> and <code>airag</code> (Retrieve, Answer, Generate).</p>
<p dir="auto">If you then use pretty-printing with <code>PromptingTools.pprint</code>, we highlight the generated text vs text likely sourced from the context and we score how strongly is the generated answer supported by the context.
In addition, we annotate each generated chunk with a reference to which source document it likely came from (including the confidence score between 0 and 1).</p>

<p dir="auto">Google search is great, but it's a context switch. You often have to open a few pages and read through the discussion to find the answer you need. Same with the ChatGPT website.</p>
<p dir="auto">Imagine you are in VSCode, editing your <code>.gitignore</code> file. How do I ignore a file in all subfolders again?</p>
<p dir="auto">All you need to do is to type:
<code>aai"What to write in .gitignore to ignore file XYZ in any folder or subfolder?"</code></p>
<p dir="auto">With <code>aai""</code> (as opposed to <code>ai""</code>), we make a non-blocking call to the LLM to not prevent you from continuing your work. When the answer is ready, we log it from the background:</p>
<blockquote>
<p dir="auto">[ Info: Tokens: 102 @ Cost: $0.0002 in 2.7 seconds
┌ Info: AIMessage&gt; To ignore a file called "XYZ" in any folder or subfolder, you can add the following line to your .gitignore file:
│
│ <code>│ **/XYZ │</code>
│
└ This pattern uses the double asterisk (<code>**</code>) to match any folder or subfolder, and then specifies the name of the file you want to ignore.</p>
</blockquote>
<p dir="auto">You probably saved 3-5 minutes on this task and probably another 5-10 minutes, because of the context switch/distraction you avoided. It's a small win, but it adds up quickly.</p>

<p dir="auto">Certain tasks require more powerful models. All user-facing functions have a keyword argument <code>model</code> that can be used to specify the model to be used. <p dir="auto">Each <code>ai...</code> call first looks up the provided model name in the dictionary <code>PromptingTools.MODEL_ALIASES</code>, so you can easily extend with your own aliases!</p>

<p dir="auto">Are you tired of extracting data with regex? You can use LLMs to extract structured data from text!</p>
<p dir="auto">All you have to do is to define the structure of the data you want to extract and the LLM will do the rest.</p>

<p dir="auto">This is an experimental feature, so you have to import it explicitly:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using PromptingTools.Experimental.AgentTools"><pre><span class="pl-k">using</span> PromptingTools<span class="pl-k">.</span>Experimental<span class="pl-k">.</span>AgentTools</pre></div>
<p dir="auto">This module offers "lazy" counterparts to the <code>ai...</code> functions, so you can use them in a more controlled way, eg, <code>aigenerate</code> -&gt; <code>AIGenerate</code> (notice the CamelCase), which has exactly the same arguments except it generates only when <code>run!</code> is called.</p>
<p dir="auto">For example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="out = AIGenerate(&quot;Say hi!&quot;; model=&quot;gpt4t&quot;)
run!(out)"><pre>out <span class="pl-k">=</span> <span class="pl-c1">AIGenerate</span>(<span class="pl-s"><span class="pl-pds">"</span>Say hi!<span class="pl-pds">"</span></span>; model<span class="pl-k">=</span><span class="pl-s"><span class="pl-pds">"</span>gpt4t<span class="pl-pds">"</span></span>)
<span class="pl-c1">run!</span>(out)</pre></div>
<p dir="auto">How is it useful? We can use the same "inputs" for repeated calls, eg, when we want to validate
or regenerate some outputs. We have a function <code>airetry</code> to help us with that.</p>
<p dir="auto">The signature of <code>airetry!</code> is <code>airetry!(condition_function, aicall::AICall, feedback_function)</code>.
It evaluates the condition <code>condition_function</code> on the <code>aicall</code> object (eg, we evaluate <code>f_cond(aicall) -&gt; Bool</code>). If it fails, we call <code>feedback_function</code> on the <code>aicall</code> object to provide feedback for the AI model (eg, <code>f_feedback(aicall) -&gt; String</code>) and repeat the process until it passes or until <code>max_retries</code> value is exceeded.</p>
<p dir="auto">We can catch API failures (no feedback needed, so none is provided)</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="# API failure because of a non-existent model

    model = &quot;NOTEXIST&quot;)
run!(out) # fails

# we ask to wait 2s between retries and retry 2 times (can be set in `config` in aicall as well)
airetry!(isvalid, out; retry_delay = 2, max_retries = 2)"><pre><span class="pl-c"><span class="pl-c">#</span> API failure because of a non-existent model</span>
<span class="pl-c"><span class="pl-c">#</span> RetryConfig allows us to change the "retry" behaviour of any lazy call</span>
out <span class="pl-k">=</span> <span class="pl-c1">AIGenerate</span>(<span class="pl-s"><span class="pl-pds">"</span>say hi!<span class="pl-pds">"</span></span>; config <span class="pl-k">=</span> <span class="pl-c1">RetryConfig</span>(; catch_errors <span class="pl-k">=</span> <span class="pl-c1">true</span>),
    model <span class="pl-k">=</span> <span class="pl-s"><span class="pl-pds">"</span>NOTEXIST<span class="pl-pds">"</span></span>)

<p dir="auto">Or we can validate some outputs (eg, its format, its content, etc.)</p>
<p dir="auto">We'll play a color guessing game (I'm thinking "yellow"):</p>

<p dir="auto">You can place multiple <code>airetry!</code> calls in a sequence. They will keep retrying until they run out of maximum AI calls allowed (<code>max_calls</code>) or maximum retries (<code>max_retries</code>).</p>
<p dir="auto">See the docs for more complex examples and usage tips (<code>?airetry</code>).
We leverage Monte Carlo Tree Search (MCTS) to optimize the sequence of retries, so it's a very powerful tool for building robust AI workflows (inspired by <a href="https://arxiv.org/abs/2310.04406" rel="nofollow">Language Agent Tree Search paper</a> and by <a href="https://arxiv.org/abs/2312.13382" rel="nofollow">DSPy Assertions paper</a>).</p>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Package Interface</h2><a id="user-content-package-interface" class="anchor" aria-label="Permalink: Package Interface" href="#package-interface"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The package is built around three key elements:</p>
<ul dir="auto">
<li>Prompt Schemas: Define the structure of the prompt, how to separate it, combine it, how to "render" it</li>
<li>Messages: Hold the user inputs (=prompts) and AI outputs (=responses). Prompts are effectively "conversations to be completed"</li>
<li>Task-oriented functions: Provide the user-facing functionality (eg, <code>aigenerate</code>, <code>aiembed</code>, <code>aiclassify</code>)</li>
</ul>
<p dir="auto">Why this design? Different APIs require different prompt formats. For example, OpenAI's API requires an array of dictionaries with <code>role</code> and <code>content</code> fields, while Ollama's API for Zephyr-7B model requires a ChatML schema with one big string and separators like <code>&lt;|im_start|&gt;user\nABC...&lt;|im_end|&gt;user</code>. For separating sections in your prompt, OpenAI prefers markdown headers (<code>##Response</code>) vs Anthropic performs better with HTML tags (<code>&lt;text&gt;{{TEXT}}&lt;/text&gt;</code>).</p>
<p dir="auto">This package is heavily inspired by <a href="https://github.com/jxnl/instructor">Instructor</a> and it's clever use of function calling API.</p>
<p dir="auto"><strong>Prompt Schemas</strong></p>
<p dir="auto">The key type used for customization of logic of preparing inputs for LLMs and calling them (via multiple dispatch).</p>
<p dir="auto">All are subtypes of <code>AbstractPromptSchema</code> and each task function has a generic signature with schema in the first position <code>foo(schema::AbstractPromptSchema,...)</code></p>
<p dir="auto">The dispatch is defined both for "rendering" of prompts (<code>render</code>) and for calling the APIs (<code>aigenerate</code>).</p>
<p dir="auto">Ideally, each new interface would be defined in a separate <code>llm_&lt;interface&gt;.jl</code> file (eg, <code>llm_openai.jl</code>).</p>
<p dir="auto"><strong>Messages</strong></p>
<p dir="auto">Prompts are effectively a conversation to be completed.</p>
<p dir="auto">Conversations tend to have three key actors: system (for overall instructions), user (for inputs/data), and AI assistant (for outputs). We provide <code>SystemMessage</code>, <code>UserMessage</code>, and <code>AIMessage</code> types for each of them.</p>
<p dir="auto">Given a prompt schema and one or more message, you can <code>render</code> the resulting object to be fed into the model API.
Eg, for OpenAI</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using PromptingTools: render, SystemMessage, UserMessage

<p dir="auto">This object can be provided directly to the OpenAI API.</p>
<p dir="auto"><strong>Task-oriented functions</strong></p>
<p dir="auto">The aspiration is to provide a set of easy-to-remember functions for common tasks, hence, all start with <code>ai...</code>. All functions should return a light wrapper with resulting responses. At the moment, it can be only <code>AIMessage</code> (for any text-based response) or a generic <code>DataMessage</code> (for structured data like embeddings).</p>
<p dir="auto">Given the differences in model APIs and their parameters (eg, OpenAI API vs Ollama), task functions are dispatched on <code>schema::AbstractPromptSchema</code> as their first argument.</p>
<p dir="auto">See <code>src/llm_openai.jl</code> for an example implementation.
Each new interface would be defined in a separate <code>llm_&lt;interface&gt;.jl</code> file.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Configuring the Environment Variable for API Key</h3><a id="user-content-configuring-the-environment-variable-for-api-key" class="anchor" aria-label="Permalink: Configuring the Environment Variable for API Key" href="#configuring-the-environment-variable-for-api-key"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This is a guide for OpenAI's API key, but it works for any other API key you might need (eg, <code>MISTRALAI_API_KEY</code> for MistralAI API).</p>
<p dir="auto">To use the OpenAI API with PromptingTools.jl, set your API key as an environment variable:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="ENV[&quot;OPENAI_API_KEY&quot;] = &quot;your-api-key&quot;"><pre><span class="pl-c1">ENV</span>[<span class="pl-s"><span class="pl-pds">"</span>OPENAI_API_KEY<span class="pl-pds">"</span></span>] <span class="pl-k">=</span> <span class="pl-s"><span class="pl-pds">"</span>your-api-key<span class="pl-pds">"</span></span></pre></div>
<p dir="auto">As a one-off, you can:</p>
<ul dir="auto">
<li>set it in the terminal before launching Julia: <code>export OPENAI_API_KEY = &lt;your key&gt;</code></li>
<li>set it in your <code>setup.jl</code> (make sure not to commit it to GitHub!)</li>
</ul>
<p dir="auto">Make sure to start Julia from the same terminal window where you set the variable.
Easy check in Julia, run <code>ENV["OPENAI_API_KEY"]</code> and you should see your key!</p>
<p dir="auto">A better way:</p>
<ul dir="auto">
<li>On a Mac, add the configuration line to your terminal's configuration file (eg, <code>~/.zshrc</code>). It will get automatically loaded every time you launch the terminal</li>
<li>On Windows, set it as a system variable in "Environment Variables" settings (see the Resources)</li>
</ul>
<p dir="auto">We also support Preferences.jl, so you can simply run: <code>PromptingTools.set_preferences!("OPENAI_API_KEY"=&gt;"your-api-key")</code> and it will be persisted across sessions.
To see the current preferences, run <code>PromptingTools.get_preferences("OPENAI_API_KEY")</code>.</p>
<p dir="auto">Be careful NOT TO COMMIT <code>LocalPreferences.toml</code> to GitHub, as it would show your API Key to the world!</p>

<p dir="auto">Ollama runs a background service hosting LLMs that you can access via a simple API. It's especially useful when you're working with some sensitive data that should not be sent anywhere.</p>

<p dir="auto">Fine-tuning is a powerful technique to adapt a model to your specific use case (mostly the format/syntax/task). It requires a dataset of examples, which you can now easily generate with PromptingTools.jl!</p>
<ol dir="auto">
<li>
<p dir="auto">You can save any conversation (vector of messages) to a file with <code>PT.save_conversation("filename.json", conversation)</code>.</p>
</li>
<li>
<p dir="auto">Once the finetuning time comes, create a bundle of ShareGPT-formatted conversations (common finetuning format) in a single <code>.jsonl</code> file. Use <code>PT.save_conversations("dataset.jsonl", [conversation1, conversation2, ...])</code> (notice that plural "conversationS" in the function name).</p>
</li>
</ol>
<p dir="auto">For an example of an end-to-end finetuning process, check out our sister project <a href="https://github.com/svilupp/Julia-LLM-Leaderboard/blob/main/experiments/cheater-7b-finetune/README.md">JuliaLLMLeaderboard Finetuning experiment</a>.
