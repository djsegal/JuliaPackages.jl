<p dir="auto">This small package contains:</p>
<ul dir="auto">
<li>
<p dir="auto"><code>cavity!</code> and <code>cavity</code>: Functions to compute the <code>N</code> all-but-one operations between <code>N</code> elements in time <code>O(N)</code>. The operation is arbitrary and needs only to be associative. This is equivalent to computing <code>[reduce(op, (src[j] for j in eachindex(src) if i != j); init) for i in eachindex(src)]</code> which however would need <code>N*(N-1)</code> evaluations of <code>op</code>.
If <code>op</code> is commutative with exact inverse <code>invop</code>, you could obtain the same result of <code>cavity(src, op, init)</code>, also in time <code>O(N)</code>, with <code>invop.(reduce(op, src; init), src)</code>.</p>
</li>
<li>
<p dir="auto"><code>Accumulator</code>: An <code>a = Accumulator(v::AbstractVector)</code> works as a replacement for <code>v</code> with extra tracking computations.</p>
<ul dir="auto">
<li>Construction of <code>a</code> requires time <code>O(N)</code> where <code>N == length(v)</code>.</li>
<li><code>sum(a)</code> requires time <code>O(1)</code>.</li>
<li><code>cumsum(a)</code>, <code>cavity(a)</code> require time <code>O(1)</code> and return respectively a <code>CumSum</code> and <code>Cavity</code> objects that are linked to <code>a</code>.</li>
</ul>
</li>
<li>
<p dir="auto"><code>c::CumSum(a::Accumulator)</code>: keeps a live-updated <code>cumsum</code> of <code>a</code>.</p>
<ul dir="auto">
<li>Create it with <code>c = cumsum(a::Accumulator)</code></li>
<li>Retrieval <code>c[i]</code> takes time <code>O(log N)</code>.</li>
<li><code>collect(c)</code> takes time <code>O(N)</code></li>
<li><code>searchsortedfirst(r, c)</code> takes time <code>O(log N)</code></li>
</ul>
</li>
<li>
<p dir="auto"><code>c::Cavity(a::Accumulator)</code>: keeps a live-updated <code>cavity</code> of <code>a</code>.</p>
<ul dir="auto">
<li>Create it with <code>c = cavity(a::Accumulator)</code>.</li>
<li>Retrieval <code>c[i]</code> takes time <code>O(log N)</code>.</li>
<li><code>collect(c)</code> takes time <code>O(N)</code> (but is slower than <code>cavity(v::Vector)</code>).</li>
</ul>
</li>
<li>
<p dir="auto"><code>Q::ExponentialQueueDict{K}()</code>: <code>Dict</code>-like interface to a collection of events with associated independent probability rates, intended for sampling on a Gillespie-like scheme.</p>
<ul dir="auto">
<li>Events are of type <code>K</code>.</li>
<li>Dict-like contruction <code>Q = ExponentialQueueDict([:a =&gt; 0.1, :b =&gt; 0.2, :c =&gt; 0.3])</code> is allowed</li>
<li>Rates can be queried by <code>getindex</code> (i.e. <code>r = Q[k]</code>) and updated via <code>setindex!</code> (i.e. <code>Q[k] = r</code>), both in time <code>O(log N)</code> where <code>N</code> is the number of stored events.</li>
<li>Next event type and time can extracted from the queue by <code>k,t = pop!(Q)</code> or <code>k,t = peek(Q)</code>. On <code>pop!</code>, event <code>k</code> is then removed from the collection. <code>pop!</code> and <code>peek</code> take time <code>O(log N)</code>.</li>
<li>If event time is unneeded, next event alone can be extracted with <code>k = peekevent(Q)</code> (taking also time <code>O(log N)</code>).</li>
</ul>
</li>
<li>
<p dir="auto"><code>Q::ExponentialQueue()</code>: Like <code>ExponentialQueue{Int}</code> but events are stored on a vector instead of a <code>Dict</code>, so it may be slightly more efficient. Event indices are positive integers (note that the memory space needed scales with the maximum index, so use ExponentialQueueDIct{Int} if you need very large indices).</p>
</li>
</ul>
