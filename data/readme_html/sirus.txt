<p dir="auto">This package is a pure Julia implementation of the <strong>S</strong>table and <strong>I</strong>nterpretable <strong>RU</strong>le <strong>S</strong>ets (SIRUS) algorithm.
The algorithm was originally created by Clément Bénard, Gérard Biau, Sébastien Da Veiga, and Erwan Scornet (Bénard et al., <a href="http://proceedings.mlr.press/v130/benard21a.html" rel="nofollow">2021</a>).
<code>SIRUS.jl</code> has implemented both classification and regression, but we found that performance is generally best on classification tasks.</p>
<p dir="auto">The main benefit of this algorithm is that it is <strong>fully explainable</strong>.
This differs from model-agnostic explainability techniques such as SHAP, which convert the model to a simplified representation.
However, <strong>the complex model is still used for predictions</strong>, which can lead to hidden biases or reliability issues.
The SIRUS algorithm fixes this by using a simplified model for <strong>both</strong> for prediction and explanation.</p>

<p dir="auto">This package defines two rule-based models that satisfy the Machine Learning Julia <a href="https://github.com/alan-turing-institute/MLJ.jl"><code>MLJ.jl</code></a> interface.
The models are <code>StableRulesClassifier</code> and <code>StableRulesRegressor</code>:</p>

<p dir="auto">This is a basic example, in most cases you want to tune the <code>max_depth</code>, <code>max_rules</code>, and <code>lambda</code> hyperparameters.
See <code>?StableRulesClassifier</code>, <code>?StableRulesRegressor</code>, or the <a href="https://sirus.jl.huijzer.xyz/dev/api/" rel="nofollow">API documentation</a> for more information about the models and their hyperparameters.
A full guide through binary classification can be found in the <a href="https://sirus.jl.huijzer.xyz/dev/binary-classification/" rel="nofollow">Simple Binary Classification</a> example.</p>

<p dir="auto">To submit patches, use pull requests (PRs) here on GitHub.
In general:</p>
<ul dir="auto">
<li>Try to keep PRs limited to one feature or bug; otherwise they become hard to review/verify.</li>
<li>Try to use the code style that is used in the rest of the codebase.
See also the <a href="https://github.com/invenia/BlueStyle">Code Style Blue</a>.</li>
<li>Try to update documentation when updating code, but feel free to leave documentation updates for a separate PR.</li>
<li>When possible, make PRs as easily reversible as possible.
Any change that would be easily reversible later provides little risk and can, therefore, more easily be merged.</li>
</ul>
<p dir="auto">As long as the PR moves the codebase forward, merging will likely happen.</p>
