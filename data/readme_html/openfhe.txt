<p dir="auto">OpenFHE.jl is a Julia wrapper package for
<a href="https://github.com/openfheorg/openfhe-development">OpenFHE</a>, a C++ library for fully
homomorphic encryption. The C++ functionality is exposed in native Julia via the
<a href="https://github.com/JuliaInterop/CxxWrap.jl">CxxWrap.jl</a> package, using
<a href="https://github.com/hpsc-lab/openfhe-julia">OpenFHE-julia</a> as its backend.</p>
<p dir="auto"><em>Note: This package is work in progress and not all capabilities of OpenFHE have been
translated to Julia yet. Community contributions are very welcome!</em></p>

<p dir="auto">If you have not yet installed Julia, please <a href="https://julialang.org/downloads/platform/" rel="nofollow">follow the instructions for your

<a href="https://github.com/hpsc-lab/OpenFHE.jl">OpenFHE.jl</a> works with Julia v1.8

following commands in the Julia REPL:</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Memory issues</h3><a id="user-content-memory-issues" class="anchor" aria-label="Permalink: Memory issues" href="#memory-issues"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">OpenFHE is a memory-optimized C++ library, but these optimizations can cause
memory issues when transitioning to Julia.</p>
<p dir="auto">In OpenFHE, large objects like <code>Ciphertext</code>, <code>Plaintext</code>, and <code>CryptoContext</code> are managed
using <code>std::shared_ptr</code>. These objects are not freed until all associated <code>std::shared_ptr</code>s
are destroyed. Since the Julia objects that hold a reference to these shared pointers are relatively small, Julia's garbage collector
does not always free them automatically, as they are not considered a high priority for garbage collection. This is because Julia's garbage collector primarily
focuses on "young" objects during its incremental collections, leaving some <code>std::shared_ptr</code>s
in memory even when they are no longer in use. This may result in a significant increase in memory consumption over time,
as a single <code>Ciphertext</code> object can occupy over 60 MB. Consequently, complex operations may lead
to gigabytes of memory being occupied without being freed until the Julia session is terminated.
One possible solution is to manually trigger Julia's garbage collector
to perform a full collection, which will also clean up these "small" objects:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="GC.gc()"><pre>GC<span class="pl-k">.</span><span class="pl-c1">gc</span>()</pre></div>
<p dir="auto">Additionally, OpenFHE optimizes memory usage in C++ by storing evaluation keys and <code>CryptoContext</code>s
in static objects. These objects, being quite large, remain in memory until the Julia REPL is
closed. To release them while the REPL is still running, you can execute the following functions:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="ClearEvalMultKeys()
ClearEvalSumKeys()
ClearEvalAutomorphismKeys()
ReleaseAllContexts()"><pre><span class="pl-c1">ClearEvalMultKeys</span>()
<span class="pl-c1">ClearEvalSumKeys</span>()
<span class="pl-c1">ClearEvalAutomorphismKeys</span>()
<span class="pl-c1">ReleaseAllContexts</span>()</pre></div>
<p dir="auto">Note that this will invalidate all currently existing contexts, even those which are
still in use. Thus you should only call these functions once you are done with a given
FHE setup and want to start a new one.
For more details, please refer to the documentation for <a href="@ref"><code>ClearEvalMultKeys</code></a>,
<a href="@ref"><code>ClearEvalSumKeys</code></a>, <a href="@ref"><code>ClearEvalAutomorphismKeys</code></a>, and <a href="@ref"><code>ReleaseAllContexts</code></a>.</p>
<p dir="auto">Therefore, for a full cleanup of all OpenFHE-occupied memory, first ensure that all variables holding references to OpenFHE objects are out of scope and then execute</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="ClearEvalMultKeys()
ClearEvalSumKeys()
ClearEvalAutomorphismKeys()
ReleaseAllContexts()
GC.gc()"><pre><span class="pl-c1">ClearEvalMultKeys</span>()
<span class="pl-c1">ClearEvalSumKeys</span>()
<span class="pl-c1">ClearEvalAutomorphismKeys</span>()
<span class="pl-c1">ReleaseAllContexts</span>()
GC<span class="pl-k">.</span><span class="pl-c1">gc</span>()</pre></div>
<p dir="auto">By running these commands at appropriate points in your code, you can prevent excessive memory
usage and ensure efficient memory management when using OpenFHE.jl.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Using a custom OpenFHE-julia library</h3><a id="user-content-using-a-custom-openfhe-julia-library" class="anchor" aria-label="Permalink: Using a custom OpenFHE-julia library" href="#using-a-custom-openfhe-julia-library"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">By default, OpenFHE.jl uses the <a href="https://github.com/hpsc-lab/openfhe-julia">OpenFHE-julia</a>
library provided by the openfhe_julia_jll.jl package, which is automatically obtained when
installing OpenFHE.jl. Someimtes, however, it might be beneficial to instead use a
system-provided OpenFHE-julia library, e.g., for development or performance purposes. You
can change the default by providing a different library with the <code>OpenFHE.set_library!</code>
function, i.e., by running</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Transitioning between OpenFHE and OpenFHE.jl</h3><a id="user-content-transitioning-between-openfhe-and-openfhejl" class="anchor" aria-label="Permalink: Transitioning between OpenFHE and OpenFHE.jl" href="#transitioning-between-openfhe-and-openfhejl"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">OpenFHE.jl using CxxWrap.jl to wrap the C++ library OpenFHE for use in Julia. In general, we
try to stick as close to the original library's names and conentions as possible. Since some
concepts of C++ do not directly translate to Julia, however, some differences are
unavoidable. The most notable one is likely that Julia does not know the concept of class
member functions. CxxWrap.jl (and OpenFHE.jl) translates this to Julia functions that expect
the object as its first argument. Thus, a C++ member function call</p>
<div class="highlight highlight-source-c++ notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="my_object.member_function(arg1, arg2);"><pre>my_object.member_function(arg1, arg2);</pre></div>
<p dir="auto">will look like</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="member_function(my_object, arg1, arg2)"><pre><span class="pl-c1">member_function</span>(my_object, arg1, arg2)</pre></div>
<p dir="auto">in Julia.</p>
<p dir="auto">To simplify switching back and forth between OpenFHE.jl and the C++ library OpenFHE,
OpenFHE.jl tries to use the same type and function names as OpenFHE. Since <code>PascalCase</code> is
used for types and functions in OpenFHE, the same style is used in OpenFHE.jl, even though
this is contrary to typical Julia best practices (where <code>PascalCase</code> is only used for types
and <code>snake_case</code> is used for functions).</p>
<p dir="auto">Furthermore, all OpenFHE types are wrapped by corresponding CxxWrap.jl types, which can
sometimes be very verbose. To reduce clutter in the Julia REPL, OpenFHE.jl thus often uses a
simpler canonical output when printing an object. For example, the output of
<code>GenCryptoContext(parameters)</code> is an object of type
<code>CxxWrap.StdLib.SharedPtrAllocated{CryptoContextImpl{DCRTPoly}}</code>, but when <code>show</code>ing the
object we just print <code>SharedPtr{CryptoContext{DCRTPoly}}()</code>. To find out the actual
underlying type, use <code>typeof</code>.</p>
