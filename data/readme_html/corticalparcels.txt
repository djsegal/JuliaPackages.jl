<p dir="auto">This Julia package supplies a set of tools for conveniently and efficiently working with parcels, or regions of interest, in the context of the surface-space representation of the cerebral cortex. It builds upon the <code>Hemisphere</code> and <code>CorticalSurface</code> types (with supertype <code>SurfaceSpace</code>) from <a href="https://github.com/myersm0/CorticalSurfaces.jl">CorticalSurfaces.jl</a> and provides the foundation for my implementation of an important parcel-generation and -evaluation method in <a href="https://github.com/myersm0/WatershedParcellation.jl">WatershedParcellation.jl</a>. The functions supplied are based on MATLAB code developed at Washington University by Tim Laumann and Evan Gordon from their 2016 paper <a href="https://pubmed.ncbi.nlm.nih.gov/25316338/" rel="nofollow">"Generation and Evaluation of a Cortical Area Parcellation from Resting-State Correlations."</a>.</p>
<p dir="auto">A <code>Parcel</code> is a discrete region of interest on the cortical surface, and in this implementation is stored internally as a <code>BitVector</code> of vertices where each element denotes membership (<code>true</code> or <code>false</code>). The total length of that vector constitutes the surface-space representation in which the parcel is defined. The size of a parcel <code>size(p::Parcel)</code> is given as the number of non-zero elements of that vector, i.e. the number of vertices belonging to that parcel. This implementation was chosen to enable very fast performance of common operations such as getting the size, computing overlap with other parcels, dilating and eroding, etc, by reducing them internally to simple bitwise operations.</p>
<p dir="auto">A parcellation is a collection of <code>Parcel</code>s that all share the same space. It's typically the case that the parcels within it are non-overlapping, but nothing in this implementation enforces that.</p>
<p dir="auto">As of version 0.7, the former Parcellation type has been replaced by <code>HemisphericParcellation</code>, which is functionally equivalent. It's been reanmed to distinguish it from the new <code>BilateralParcellation</code> struct, which provides the capability of dealing with both hemispheres at the same time. Currently <code>BilateralParcellation</code> is available only as a convenient container and constructor for its left and right component <code>HemisphericParcellation</code>s; it has little functionality beyond that <em>yet</em>, so for the moment you can use it to store the hemispheres and then you'll have to manage iteration over the hemispheres yourself in order to do some work on each of them individually.</p>
<p dir="auto">The <code>HemisphericParcellation</code> struct contains two fields:</p>
<ul dir="auto">
<li><code>surface</code>: a <code>Hemisphere</code> supplying details of the geometry (particularly, the size of the space) that all its component <code>Parcel</code>s must conform to
<ul dir="auto">
<li>(if however the geometry is not of interest in your application, then a dummy surface can be created by, for example, <code>Hemisphere(32492)</code> where the only piece of information that's strictly required is the number of vertices, 32492 in this case)</li>
</ul>
</li>
<li><code>parcels</code>: a <code>Dict{T, Parcel}</code> mapping keys of type <code>T</code> to parcels, where <code>T</code> can be any type (preferably one for which a <code>zero(::T)</code> method is defined) that you want to use as keys for accessing and labeling individual parcels</li>
</ul>
<p dir="auto">Rather than having to create the parcel dictionaries yourself, I anticipate that a parcellation will most often be initialized via its <code>BilateralParcellation(surface::SurfaceSpace, x::Vector{T})</code> constructor, since the <code>Vector{T}</code> representation is probably the way you read in an existing parcellation from disk, e.g. from a <a href="https://github.com/myersm0/CIFTI.jl%22">CIFTI</a> file. See the Usage section below.</p>
<p dir="auto">A parcellation (either hemispheric or bilateral) can be mapped back to a vanilla <code>Vector{T}</code> representation if desired via <code>vec(px::AbstractParcellation)</code>.</p>
<p dir="auto">Some notation notes: in the following documentation and in demos, <code>p</code>, <code>p1</code>, <code>p2</code> will refer to individual parcels; and <code>px</code> will refer to a whole parcellation.</p>

<p dir="auto">The performance is going to depend on several factors. The benchmarks below are based on using a single-hemisphere parcellation of 185 parcels, in a space of 32492 vertices, and compares the current <code>BitVector</code>-based implementation to an alternative using <code>SparseVector</code>s as well as to a naive <code>Vector{Int}</code> representation (simply a list of vertex index numbers).</p>
<ul dir="auto">
<li><em>Adding or removing vertices to/from a <code>Parcel</code></em>. This is where the current implementation shines most, via operations like <code>union!(p1::Parcel, p2::Parcel)</code> and analogous calls to <code>setdiff!</code> and <code>intersect!</code>.</li>
<li><em>Computing the amount of overlap of two <code>Parcel</code>s</em>. This is fast because it reduces to just taking the dot product of their respective membership vectors.</li>
<li><em>Checking the size of a <code>Parcel</code>.</em> This is the only case where the current implementation lags behind alternatives.</li>
<li><em>Checking a <code>Parcellation</code> for unassigned values</em>. This is relatively "slow" compared to <code>Parcel</code>-level operations supplied. But it should be infrequent enough that it doesn't matter much; and the present <code>BitVector</code> is still faster than alternatives.</li>
</ul>

<p dir="auto">While the need to compute the size of a parcel is indeed a common operation and we'd like it to be as fast as possible, this implementation's considerable advantage in the other basic operations should still make it the clear frontrunner in most use cases.</p>
<p dir="auto">If we assume for simplicity that the above operations occur equally often, the <code>SparseVector</code> implementation (used in this package version 0.1.0 only) achieves a 25x speedup relative to the naive case, and the present <code>BitVector</code> implementation (package version 0.2+) achieves a 48x speedup relative to the same. If we ignore the <code>unassigned(px)</code> call, the current implementation improves to a 191x speedup over baseline.</p>

<p dir="auto">A full demo of the basic functionality can be found in <code>examples/demo.jl</code>.</p>
<p dir="auto">The package <a href="https://github.com/myersm0/CorticalSurfaces.jl">CorticalSurfaces.jl</a> provides the definitions of <code>Hemisphere</code> and <code>CorticalSurface</code> types (and their supertype <code>SurfaceSpace</code>), on which many of the operations in this package depend. So first of all, load both packages and create a <code>Hemisphere</code> struct that will define the vertex space. At a minimum, you need to specify the number of vertices in that space, for example 32492; but see <a href="https://github.com/myersm0/CorticalSurfaces.jl">CorticalSurfaces.jl</a> for further details.</p>

<p dir="auto">The above examples use <code>Int</code> as the initialization parameter, and this defines the type of key that will be assigned to each parcel. Any type should be usable, however, provided that its <code>typemax</code> can represent the largest value you anticipate needing to store. You could use <code>String</code> keys, for example, if you want to provide descriptive labels for your parcels and index them in that way.</p>

<p dir="auto"><code>unassigned(px::HemisphericParcellation)</code> may be used to dynamically determine the elements in the vector space that are not assigned to any parcel.</p>
<p dir="auto"><code>vec(px::AbstractParcellation)</code> will reduce the parcellation to a single <code>Vector{T}</code>. If you constructed <code>px</code> from a <code>Vector{T}</code> (and have not changed any of its elements), this operation should return that same vector.</p>
