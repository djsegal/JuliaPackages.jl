<p dir="auto">This package provides data structures and solvers for several variants of iterative refinement (IR). It will become much more useful when half precision (aka <code>Float16</code>) is fully supported in LAPACK/BLAS. For now, its only general-purpose
application is classical iterative refinement with double precision equations and single precision factorizations.</p>
<p dir="auto">The half precision stuff is good for those of us doing research in this field. Half precision performance has progressed to the point where you can actually get things done. On an Apple M2-Pro, a half precision LU only costs 3--8 times
what a double precision LU costs. This may be as good as it gets unless someone wants to duplicate the LAPACK implementation and get the benefits from blocking, recursion, and clever cache management.</p>
<p dir="auto"><strong>The half precision LU for Float16 in this package is much faster (more than 10x on my M2 Pro) than the default in Julia. Look at <a href="src/Factorizations/hlu!.jl">src/Factorizations/hlu!.jl</a> to see the hack job I did to <a href="https://github.com/JuliaLang/julia/blob/master/stdlib/LinearAlgebra/src/lu.jl">generic_lu</a>.</strong></p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">What is iterative refinement?</h3><a id="user-content-what-is-iterative-refinement" class="anchor" aria-label="Permalink: What is iterative refinement?" href="#what-is-iterative-refinement"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This package will make solving dense systems of linear equations faster by using the LU factorization and IR. It is limited to LU for now. A very generic description of this for solving a linear system <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A x = b$</math-renderer> is</p>
<p dir="auto"><strong>IR(A, b)</strong></p>
<ul dir="auto">
<li><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$x = 0$</math-renderer></li>
<li><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$r = b$</math-renderer></li>
<li>Factor <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A = LU$</math-renderer> in a lower precision</li>
<li>While <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$|| r ||$</math-renderer> is too large
<ul dir="auto">
<li><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$d = (LU)^{-1} r$</math-renderer></li>
<li><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$x = x + d$</math-renderer></li>
<li><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$r = b - Ax$</math-renderer></li>
</ul>
</li>
<li>end</li>
</ul>
<p dir="auto">In Julia, a code to do this would solve the linear system <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A x = b$</math-renderer> in double precision by using a
factorization in a lower precision, say single, within a residual correction iteration. This means that one would need
to allocate storage for a copy of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A$</math-renderer> in the lower precision and factor that copy. Then one has to determine what the line
<math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$d = (LU)^{-1} r$</math-renderer> means. Do you cast <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$r$</math-renderer> into the lower precision before the solve or not? <strong>MultiPrecisionArrays.jl</strong> provides
data structures and solvers to manage this. The <strong>MPArray</strong> structure lets you preallocate <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A$</math-renderer>, the low precision copy, and the residual <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$r$</math-renderer>.
The factorizations factor the low-precision copy and the solvers use that factorization and the original high-precision matrix to run
the while loop in the algorithm. We encode all this is functions like <code>mplu</code>, which builds a factorization object that does IR
when you use the backslash operator <code>\</code>.</p>
<p dir="auto">IR is a perfect example of a storage/time tradeoff.
To solve a linear system <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A x = b$</math-renderer> in <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$R^N$</math-renderer> with IR,
one incurs the storage penalty of making a low
precision copy of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A$</math-renderer> and reaps the benefit of only having to
factor the low precision copy.</p>
<p dir="auto">While you might think this is a good idea for all problems, it is not so good for smaller problems. The reason is that IR swaps the factoriation cost for
a matrix-vector multiply and the two triangular solves for LU <strong>in each IR iteration</strong>. Triangular solves do not thread as well as factorizations or matrix-vector
multiplies and that can affect the performance in a significant way, even though it is only <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$N^2$</math-renderer> work. The details are <a href="https://ctkelley.github.io/MultiPrecisionArrays.jl/dev/Details/N2Work" rel="nofollow">in the docs</a>.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">An example to get started</h3><a id="user-content-an-example-to-get-started" class="anchor" aria-label="Permalink: An example to get started" href="#an-example-to-get-started"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Herewith, the world's most simple example to show how iterative refinement works. We will follow that with some benchmarking on the cost of factorizations.</p>
<p dir="auto">The results in this README use Julia 1.10.4 and openBLAS. You should consider trying MKL (Intel machines) or <a href="https://github.com/JuliaLinearAlgebra/AppleAccelerate.jl">AppleAccelerate</a>. I have switched to AppleAccelerate myself. It gets faster with every new OS release, but the triangular solvers are still slower than openBLAS. The performance (iteration counts and timings) of IR depend on versions of OS/Julia/MultiPrecsionArrays and hour choice of BLAS. I have used several different versions in the docs and the ArXiV paper and you should try the
examples in your own environment.</p>
<p dir="auto">The functions we use are <strong>MPArray</strong> to create the structure and <strong>mplu!</strong> to factor the low precision copy. In this example high precision is <code>Float64</code> and low
precision is <code>Float32</code>. The matrix is the sum of the identity and a constant multiple of the trapezoid rule discretization of the Greens operator for <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$-d^2/dx^2$</math-renderer> on <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$[0,1]$</math-renderer></p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$$
G u(x) = \int_0^1 g(x,y) u(y) , dy
$$</math-renderer></p>
<p dir="auto">where</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$$
g(x,y) = \left\{ \begin{array}{l}
y (1 - x) \ \mbox{if x &gt; y} \\
x (1 -y ) \ \mbox{otherwise}
\end{array}
\right.
$$</math-renderer></p>
<p dir="auto">The code for this is in the <strong>/src/Examples</strong> directory. The file is <strong>Gmat.jl</strong>. You need to do</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="using MultiPrecisionArrays.Examples"><pre class="notranslate"><code>using MultiPrecisionArrays.Examples
</code></pre></div>
<p dir="auto">to get to it.</p>
<p dir="auto">The example below compares the cost of a double precision factorization to a MPArray factorization. The <code>MPArray</code> structure has a working
precision (<code>TW</code>) and a factorization (low)  precision (<code>TF</code>) matrix. The structure we will start with
is</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="struct MPArray{TW&lt;:AbstractFloat,TF&lt;:AbstractFloat,TR&lt;:AbstractFloat}

<p dir="auto">The structure also stores the residual and the solution in the residual precision <code>TR</code>. Most of the time <code>TR = TW</code>.
The <code>onthefly</code> Boolean tells the solver how to do the interprecision transfers. The easy way to get started is to use the <code>mplu</code>
command directly on the matrix. That will build the MPArray, follow that with the factorization of <code>AL</code>, and put in all in a structure
that you can use as a factorization object with <code>\</code>. I do not export the constructor for this or any other multiprecision array structure. You should use functions like <code>mplu</code> to build
multiprecision factorization objects.</p>
<p dir="auto">Now we will see how the results look. In this example we compare the result with iterative refinement with <code>A\b</code>, which is LAPACK's LU.
As you can see the results are equally good. Note that the factorization object <code>MPF</code> is the
output of <code>mplu</code>. This is analogous to <code>AF=lu(A)</code> in LAPACK.</p>
<p dir="auto">You may not get exactly the same results for this example on
different hardware, BLAS, number of cores, versions of Julia/OS/MulitPrecisionArrays.
I am still playing with the termination criteria and the iteration
count could grow or shrink as I do that as could the residual for the converged result.</p>

<p dir="auto">The compute time for <code>mplu</code> should be a bit more than half that of <code>lu!</code>. The reason is
that <code>mplu</code> factors a low precision array, so the factorization cost is cut in half. Memory
is a different story because. The reason
is that both <code>mplu</code> and <code>lu!</code> do not allocate storage for a new high precision array,</p>
<p dir="auto">but <code>mplu</code> allocates for a low precision copy, so the memory and allocation cost for <code>mplu</code>
is 50% more than <code>lu</code>.</p>
<p dir="auto">One issue with smaller problems is that the triangular solve
does not parallelize as well as the factorization, so does not exploit
multi-core processor as well. We can see this in the IR solver times because
each iteration of IR needs a matrix-vector multiply and a triangular solve.</p>

example of a time/storage tradeoff. You have to store a low precision copy of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$A$</math-renderer>, so the storage burden increases by 50% and the factorization time is cut in half.

<p dir="auto">You can get some iteration statistics by using the
<strong>reporting</strong> keyword argument to the solvers. The easiest way
to do this is with the backslash command. When you use this option you
get a data structure with the solution and the residual history.</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="julia&gt; using MultiPrecisionArrays

<p dir="auto">As you can see, IR does well for this problem. The package uses an initial
iterate of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$x = 0$</math-renderer> and so the initial residual is simply <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$r = b$</math-renderer>
and the first entry in the residual history is <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="3d4d61a2729d2a2a33795c287ee2c790">$|| b ||_\infty$</math-renderer>. The
iteration terminates successfully after five matrix-vector products.</p>
<p dir="auto">You may wonder why the residual after the first iteration was so much
larger than single precision roundoff. The reason is that the default
when the low precision is single is to scale and downcast the residual
for the triangular solves. This is faster for medium sized problems.</p>
