<p dir="auto">DBMigrations.jl tries to be simple, transparent, and flexible. It relies on minimal required structure to work, while allowing for more complex setups.</p>
<p dir="auto">It aims to be compatible with all database packages that support the interfaces in <a href="https://github.com/JuliaDatabases/DBInterface.jl">DBInterface.jl</a>.
Currently that includes SQLite, MySQL, LibPQ.jl, and ODBC.jl.</p>
<p dir="auto">The primary interface is calling <code>DBMigrations.runmigrations(conn::DBInterface.Connection, dir::String)</code>.</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="DBMigrations.runmigrations(conn::DBInterface.Connection, dir::String)"><pre class="notranslate"><code>DBMigrations.runmigrations(conn::DBInterface.Connection, dir::String)
</code></pre></div>
<p dir="auto">Using an established database connection <code>conn</code> (which should have the appropriate schema already
selected), search the directory <code>dir</code> for migration files and apply them to the database. Migration
files should be named like <code>V1__baseline.sql</code>, <code>V2__latlong.sql</code>, etc. where they <em>must</em> start with
a capital <code>V</code> followed by a number, followed by two underscores, followed by a description of the
migration. The number must be unique across all migrations. The description can be anything, but
should be descriptive of the migration. The file extension currently must be <code>.sql</code>.</p>
<p dir="auto">Migration files found in <code>dir</code> will be checked against a special <code>__migrations__</code> table that
the DBMigrations.jl package manages in the database connection for tracking which migrations have
already been applied. If a migration file is found in <code>dir</code> that has not been applied, it will be
applied to the database. If a migration file is found in <code>dir</code> that has already been applied, it
will be skipped. If a migration file is found in <code>dir</code> that has been applied but has changed since
it was applied, an error will be thrown (migrations should be immutable once applied).</p>
<p dir="auto">Migration files may contain multiple SQL statements, separated by semicolons. Each statement will
be executed in order. If any statement fails, the entire migration will be rolled back and an error
will be thrown. If a migration file contains a syntax error, the migration will be rolled back and
an error will be thrown.</p>
