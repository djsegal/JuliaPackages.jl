<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Package Motivation</h2><a id="user-content-package-motivation" class="anchor" aria-label="Permalink: Package Motivation" href="#package-motivation"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The goal for this package is to provide a relatively simple <em>Julian</em> API for simulating thermodynamical quantities in statistical mechanics with Monte Carlo methods. As the title implies, the methods of interest focus on <em>replica-exchange</em>, or massively-parallel simulation of systems that occasionally swap information for mutually faster convergence.</p>
<p dir="auto">With this said, a helpful user interface is important for usability and ultimately reproducibility of scientific results. We therefore place some constraints on how one can actually access the high-performance code. Luckily, the Julia type system with multiple-dispatch can do this for us.</p>

<p dir="auto">In our view, any Monte Carlo simulation can be disected into a set of interacting black boxes. These include</p>
<ol dir="auto">
<li><a href="src/Parameters/"><code>Parameters</code></a>: the data structures that act as experimental knobs with which one tunes a simulation.</li>
<li><a href="src/Models"><code>Models</code></a>: the data structure that contains all relevant information for the system being simulated. The <code>model</code>s encapsulate the following data structures:
<ol dir="auto">
<li><a href="src/Models/Lattices/"><code>Lattices</code></a>: the underlying geometry in which a system evolves during a simulation.</li>
<li><a href="src/Models/Hamiltonians/"><code>Hamiltonians</code></a>: the data structure that contains all of a system's degrees of freedom and how they interact amongst themselves. (In many ways this <em>defines</em> the system itself.)</li>
<li><a href="src/Models/Observables"><code>Observables</code></a>: the thermodynamic quantities to be sampled during the Monte Carlo simulation.</li>
</ol>
</li>
<li><a href="src/Algorithms/"><code>Algorithms</code></a>: the Monte Carlo methods used to define individual time-steps in the simulation. These also update the system itself.</li>
<li><a href="src/Simulations/"><code>Simulations</code></a>: the set of <code>main</code> functions that actually perform a simulation.</li>
</ol>
<p dir="auto">Each of these pieces are defined through a series of methods and types whose implementations are independent. Because of this, each of these pieces are separated as submodules (in the Julian sense). We also deliberately choose to trap the exported names from these submodules within <code>TRExMC</code>. This reduces the amount of clutter in the namespace, even though I admit that needing to write things, like <code>Hamiltonians.BasicIsing</code> may get annoying at times. 🙃</p>
