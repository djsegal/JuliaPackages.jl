<p dir="auto">VectorPrisms.jl exposes the ability to view a (potentially nested) <code>struct</code> as a <code>AbstractVector</code>.
It exposes this both through composition with the <code>VectorPrism</code> wrapper type, and through inheritance with the <code>AbstractRecordVector</code> type.
These conceptually work by recursively (depth first) searching all fields looking for elements that subtype the declared eltype (which may be concrete, abstract, or a union).</p>
<p dir="auto">Throughout these documentation we will refer to the example of:</p>

<p dir="auto">By and large the operations on our types are characterized by the <code>AbstractVector</code> API -- that is the whole point.
But we do provide a couple of operations that only make sense for these types/</p>

It takes an optional first argument that specifies if it should return <code>String</code>s (default), or <code>Expr</code>s.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Should I use <code>AbstractRecordVector</code> or <code>VectorPrism</code>?</h3><a id="user-content-should-i-use-abstractrecordvector-or-vectorprism" class="anchor" aria-label="Permalink: Should I use AbstractRecordVector or VectorPrism?" href="#should-i-use-abstractrecordvector-or-vectorprism"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">In general it is a bit nicer to use <code>AbstractRecordVector</code> if you can slot it nicely into your existing type hierarchy,
since this means your type is always exposed as itself to methods.
However, this is not always possible since Julia does not have multiple inheritance.</p>
<p dir="auto">This is where <code>VectorPrism</code> enters.
You can wrap your type in it to get the <code>AbstractVector</code> view.
However, now you do not get your methods anymore.
Some things like <code>getproperty</code> and function invocation are delegated to the original object, but by no means all possible operations.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Limitations: no dynamically sized memory</h3><a id="user-content-limitations-no-dynamically-sized-memory" class="anchor" aria-label="Permalink: Limitations: no dynamically sized memory" href="#limitations-no-dynamically-sized-memory"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The size of types with the structs must be compile-time known.
They can be <code>struct</code>s or<code>Tuples</code>, they can not be <code>Vector</code>s.
This also means it can not contain types like <code>Dict</code>s which are built on type of <code>Vector</code>s.
However, if you know the size of your <code>Array</code>s, wrapping them in <code>StaticArrays.SizedArray</code>
allows them to be used inside a <code>VectorPrism</code>/<code>AbstractRecordVector</code>.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">How does it work under the hood and is it fast?</h3><a id="user-content-how-does-it-work-under-the-hood-and-is-it-fast" class="anchor" aria-label="Permalink: How does it work under the hood and is it fast?" href="#how-does-it-work-under-the-hood-and-is-it-fast"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The core functionality is that <code>getindex</code> is an <code>@generated</code> function which basically generates a chain of <code>if</code>-<code>else</code>s for all the fields of the eltype.
So for our example it would rounghly look like:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="function getindex(bar::Bar, ii::Int)
    if ii==1
        return bar.x
    elseif ii==2
        return bar.foo.a
    elseif ii==3
        return bar.y
    else
        throw(BoundsError(bar, ii))
    end
end"><pre><span class="pl-k">function</span> <span class="pl-en">getindex</span>(bar<span class="pl-k">::</span><span class="pl-c1">Bar</span>, ii<span class="pl-k">::</span><span class="pl-c1">Int</span>)
    <span class="pl-k">if</span> ii<span class="pl-k">==</span><span class="pl-c1">1</span>
        <span class="pl-k">return</span> bar<span class="pl-k">.</span>x
    <span class="pl-k">elseif</span> ii<span class="pl-k">==</span><span class="pl-c1">2</span>
        <span class="pl-k">return</span> bar<span class="pl-k">.</span>foo<span class="pl-k">.</span>a
    <span class="pl-k">elseif</span> ii<span class="pl-k">==</span><span class="pl-c1">3</span>
        <span class="pl-k">return</span> bar<span class="pl-k">.</span>y
    <span class="pl-k">else</span>
        <span class="pl-c1">throw</span>(<span class="pl-c1">BoundsError</span>(bar, ii))
    <span class="pl-k">end</span>
<span class="pl-k">end</span></pre></div>
<p dir="auto">This is indeed fast.
If the index is compile-time known (like a literal) then all the branches are eliminated and <code>bar[2]</code> directly compiles into <code>bar.foo.a</code>.
If not, this gets analysed this as a switch statement for which it has many options for how to compile including to a jump statement or a series of conditionals depending which is faster. You can check it isn't actually running the series of conditions for large structs because the timing remands constant not changing with index.
<code>getindex</code> on a <code>AbstractRecordVector</code>/<code>VectorPrism</code> of any size remains on the order of a couple of CPU instructions, similar to <code>getindex</code> on <code>Vector</code>.</p>
<p dir="auto">Wrapping things in <code>VectorPrism</code> is also very cheap since it does not allocate.
Further more, it will often be removed entirely the compiler during SROA optimiation (Scalar Replacement of Aggregates).</p>

<p dir="auto"><code>AbstractRecordVector</code> is conceptually very similar to <a href="https://juliaarrays.github.io/StaticArrays.jl/stable/pages/api/#FieldVector" rel="nofollow">StaticArrays.FieldVector</a>.
The primary difference is that <code>AbstractRecordVector</code> works recursively on all structs contained within your struct.
So for</p>
<p dir="auto">we would have that <code>bar[2]</code> would return <code>bar.foo.a</code> (which was 2). (as well as <code>bar[1]</code> returning (which was <code>10</code>)).
In contrast had <code>Bar&lt;:FieldVector{2, Int}</code> when <code>bar[2]</code> would have returned <code>Bar.foo</code> (and violated the declared element type).</p>
<p dir="auto">A second (related) difference is that leaf types that do not subtype the declared <code>eltype</code> are simply ignored.
So, continuing our previous example <code>bar[3]</code> would return <code>bar.y</code> (which was <code>30</code>).</p>

<p dir="auto">A prism is a type of optic, like a lens.
This concept is relatively well established in Closure and Haskell.
Julia programmers may be familar with <a href="https://github.com/JuliaObjects/Accessors.jl">Accessors.jl</a> uses lenses.</p>
<p dir="auto">A lens is about fields, it encodes a <em>has-a</em> relationship.
A prism on the other-hand encodes a <em>is-a</em> relationship.
So the <code>VectorPrism</code> allows us to view a struct as if it was an <code>AbstractVector</code>.</p>
<p dir="auto">We do not do this though a standard optic construction of a forward-function which returns both the new object and a back-function (closure) that returns the object to the original, but rather though exposing that API fully and without new memory allocation, thus no need for a back function.</p>
<p dir="auto">We do note that there are many implementation of the standard vector prism construction in julia, with various tweaks to meet various needs, for example <a href="https://github.com/JuliaDiff/FiniteDifferences.jl/blob/0766bbc7b81381b134835d31145ad4822fd7e65f/src/to_vec.jl"><code>FiniteDifferences.to_vec</code></a>, <a href="https://docs.sciml.ai/Flux/stable/destructure/#Optimisers.destructure" rel="nofollow"><code>Optimizers.destructure</code></a> and others.``</p>
