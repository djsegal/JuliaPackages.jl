<p dir="auto">Sometimes, when writing automated tests, rather than specifying the value to compare against you want to compare against a "snapshot". This package provides the <code>@snapshot_test</code> macro, which compares the result of an expression against a snapshot. Snapshot testing is often discouraged, because you're not really testing that the code produces the expected output, only that the output doesn't change. But in cases with complex outputs, it may be most useful to manually inspect the output of the function once, and then simply assert that it does not change.</p>

<p dir="auto">To create a snapshot test, add to your test file:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="@snapshot_test &quot;test_name&quot; expression"><pre lang="{julia}" class="notranslate"><code>@snapshot_test "test_name" expression
</code></pre></div>
<p dir="auto">This will compute <code>expression</code>, and compare the result against a serialized value (the snapshot). By default, snapshots will be found in <code>$JULIA_PROJECT/snapshots</code>. Within that folder, there will be one snapshot for each snapshot test, serialized using the built-in Julia <code>Serialization</code> module and gzipped.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Creating snapshots</h3><a id="user-content-creating-snapshots" class="anchor" aria-label="Permalink: Creating snapshots" href="#creating-snapshots"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The first time you run the code above, you'll get an error:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="ERROR: Snapshot file .../snapshots/test_name.gz does not exist! Re-run with environment variable CREATE_NONEXISTENT_SNAPSHOTS=yes to create."><pre class="notranslate"><code>ERROR: Snapshot file .../snapshots/test_name.gz does not exist! Re-run with environment variable CREATE_NONEXISTENT_SNAPSHOTS=yes to create.
</code></pre></div>
<p dir="auto">This is expected—when you first create the test, there's nothing to compare the value against. As the error message indicates, if you re-run with the environment variable <code>CREATE_NONEXISTENT_SNAPSHOTS=yes</code>, the snapshot file will be created. You should investigate that the snapshotted value is correct before committing the snapshot file to version control.</p>
<p dir="auto"><code>SnapshotTests</code> will only ever create a snapshot file that does not exist; it will <em>never</em> overwrite an existing snapshot file. This is to avoid inadvertently updating old snapshot to include unwanted results when creating new snapshots. To update a snapshot, just delete the serialized file from the <code>snapshots/</code> directory, and update the snapshots again.</p>
<p dir="auto"><code>Base.isequal(result, expected)</code> must be <code>true</code> for a snapshot test to pass. Structs are <a href="https://discourse.julialang.org/t/surprising-struct-equality-test/4890" rel="nofollow">only equal if their fields are identity-equal (not value-equal)</a>. The <a href="https://github.com/jolin-io/StructEquality.jl">StructEquality.jl</a> library is often helpful for creating value based <code>isequal</code> functions.</p>
<p dir="auto">You can also specify a custom comparator at the end of the <code>@snapshot_test</code> macro. For instance, to use <code>isapprox</code>:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="@snapshot_test &quot;test_name&quot; expression (isapprox)"><pre lang="{julia}" class="notranslate"><code>@snapshot_test "test_name" expression (isapprox)
</code></pre></div>
<p dir="auto">Parentheses are optional but improve readability IMHO.</p>

<p dir="auto">Normally, failed snapshot tests result in test failures (as one would expect). However, debugging failed snapshot tests can be difficult, as there is just a yes/no indication of equality with what is almost certainly a complex object. If you start the tests from the REPL (not by running <code>]test</code>, but by running <code>include("runtests.jl")</code>), and have the environment variable <code>START_REPL_ON_SNAPSHOT_FAILURE=yes</code>, <a href="https://github.com/JuliaDebug/Infiltrator.jl">Infiltrator.jl</a> will be used to start a REPL with the variables <code>observed</code> (what the test code produced) and <code>expected</code> (what was read in from the snapshot) to evaluate the differences interactively.</p>
<p dir="auto">If you determine that the changes are as expected, you can delete the snapshot files and recreate them (see above). However, my preference is to instead write a custom comparator function that returns true if all of the differences are as expected, ensure the test passes with the custom comparator, commit the custom comparator to the repository to document the expected changes, and then delete and recreate the snapshots and restore the original comparator. This avoids testing being based on results in an interactive session, which is a bad practice—though certainly useful to debug as a precursor to writing the custom comparator.</p>
<p dir="auto">Actually starting the tests interactively is a challenge because the test environment is created on the fly by combining the project environment with the test environment. <a href="https://github.com/JuliaTesting/TestEnv.jl">TestEnv.jl</a> can solve this problem, as it allows activating the test environment of the active project. To avoid installing it as a dependency in my main project, I prefer to install it in the global environment and load it before activating my package. So a full interactive testing run would look something like this:</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="my-project $ START_REPL_ON_SNAPSHOT_FAILURE=yes julia

</code></pre></div>
