<p dir="auto"><a id="user-content-grouppresentations" href="#GroupPresentations">#</a>
<strong><code>GroupPresentations</code></strong> — <em>Module</em>.</p>
<p dir="auto">This  is a  port of  some GAP3/VkCurve  functionality on <em>presentations</em> of <em>finitely presented groups</em>.</p>
<p dir="auto">We  have defined just enough functionality  on finitely presented groups so that  presentations  can  be  translated  to  finitely presented groups and vice-versa. The focus is on presentations, the goal being to simplify them.</p>
<p dir="auto">The  elements of finitely presented groups are <code>AbsWord</code> or abstract words, representing elements of a free group.</p>

<p dir="auto">The  functions <code>Presentation</code>  and <code>FpGroup</code>  create a  presentation from a finitely presented group and vice versa.</p>
<p dir="auto">In order to speed up the algorithms, the relators in a presentation are not represented  internally by <code>AbsWord</code>s, but by lists of positive or negative generator  numbers which  we call  <em>Tietze words</em>.  Here is another example with a few functions to explore presentations.</p>

<strong><code>GroupPresentations.Presentation</code></strong> — <em>Method</em>.</p>
<p dir="auto"><code>Presentation( G::FpGroup[, debug=1])</code></p>
<p dir="auto">returns  the  presentation  corresponding  to  the given finitely presented group <code>G</code>.</p>
<p dir="auto">The  optional <code>debug</code> parameter  can be used  to restrict or  to extend the amount  of output  provided by  Tietze transformation  functions when being applied  to the created  presentation. The default  value 1 is designed for interactive  use and implies  explicit messages to  be displayed by most of these functions. A <code>debug</code> value of 0 will suppress these messages, whereas a <code>debug</code> value of 2 will enforce some additional output.</p>

<p dir="auto"><code>simplify(p [,tries])</code></p>
<p dir="auto">simplify  the  presentation  <code>p</code>.  We  have  found heuristics which make it somewhat  efficient, but the algorithm depends  on random numbers so is not reproducible.  The main  idea is  to rotate  relators between  calls to the basic  <code>GroupPresentations.Go</code> function. By default 100 such rotations are tried (unless  the  presentation  is  so  small  that  less rotations exhaust all possible  ones), but the actual number tried  can be controlled by giving a second  parameter <code>tries</code> to the function. Another useful tool to deal with presentations is <code>tryconjugate</code>.</p>

<strong><code>GroupPresentations.conjugate</code></strong> — <em>Function</em>.</p>
<p dir="auto"><code>conjugate(p,conjugation)</code></p>
<p dir="auto">This program modifies a presentation by conjugating a generator by another. The  conjugation to  apply is  described by  a length-3  string of the same style  as  the  result  of  <code>display_balanced</code>,  that is <code>"abA"</code> means replace  the second generator by its  conjugate by the first, and  <code>"Aba"</code> means replace it by its conjugate by the inverse of the first.</p>

<p dir="auto"><a id="user-content-grouppresentations.tryconjugate" href="#GroupPresentations.tryconjugate">#</a>
<strong><code>GroupPresentations.tryconjugate</code></strong> — <em>Function</em>.</p>
<p dir="auto"><code>tryconjugate(p[,goal[,printlevel]])</code></p>
<p dir="auto">This program tries to simplify group presentations by applying conjugations to  the  generators.  The  algorithm  depends  on  random  numbers,  and on tree-searching,  so is  not reproducible.  By default  the program stops as soon  as a shorter presentation is found.  Sometimes this does not give the desired  presentation.  One  can  give  a  second argument <code>goal</code>, then the program  will only stop when  a presentation of length  less than <code>goal</code> is found.  Finally, a third  argument can be  given and then all presentations the  programs runs  over which  are of  length less  than or  equal to this argument are displayed. Due to the non-deterministic nature of the program, it  may be useful to  run it several times  on the same input. Upon failure (to improve the presentation), the program returns <code>p</code>.</p>
