<p dir="auto">Do you miss playing hide and seek with memory leaks? Do you find GC overhead problematic?
PtrArrays.jl can take you back to the good old days of manual memory management.
See also <a href="https://github.com/MasonProtter/Bumper.jl">Bumper.jl</a> if you want to avoid GC
overhead and don't like hide and seek.</p>
<p dir="auto">This package provides <code>malloc(T, dims...)</code> which allocates an <code>AbstractArray{T}</code> with the
provided <code>dims</code>. If you want, you can call <code>free</code> on the array once you're done using it
but it can be more fun to see what happens if you don't.</p>

<p dir="auto"><a href="https://github.com/MasonProtter/Bumper.jl">Bumper.jl</a> provides bump allocators which allow
you to manage your own allocation stack, bypassing the Julia GC.</p>
<p dir="auto"><a href="https://github.com/brenhinkeller/">StaticTools.jl</a> is a much larger package which provides,
among other things, a
<a href="https://brenhinkeller.github.io/StaticTools.jl/dev/#StaticTools.MallocArray" rel="nofollow">MallocArray</a>
type that behaves similarly to PtrArray. As StaticTools.jl is meant to run without the Julia
runtime, it does not make use of features such as exceptions. Consequently, all usages of
<code>StaticTools.MallocArray</code> are implicitly annotated with <code>@inbounds</code> and out of bounds
accesses are UB instead of errors, StaticTools.MallocArray with invalid indices will return
a null pointer with size zero while PtrArrays will throw, etc. In general, StaticTools.jl's
<code>MallocArray</code> can be thought of as "unsafe" while <code>PtrArray</code> is "safe" (though memory leaks
will still occur if you call <code>malloc</code> and fail to call <code>free</code>)</p>
<p dir="auto"><a href="https://github.com/LilithHafner/PtrArrays.jl/tree/0b6dbdc012e1058b2b64d0f94863eff4120def85">MallocArrays.jl</a>
is the original name of this package. It is obsolete.</p>
