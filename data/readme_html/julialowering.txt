<p dir="auto">JuliaLowering.jl is an experimental port of Julia's code lowering compiler
passes, written in Julia itself. "Code lowering" is the set of compiler passes
which <em>symbolically</em> transform and simplify Julia's syntax prior to type
inference.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Goals</h2><a id="user-content-goals" class="anchor" aria-label="Permalink: Goals" href="#goals"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This work is intended to</p>
<ul dir="auto">
<li>Bring precise code provenance to Julia's lowered form (and eventually
downstream in type inference, stack traces, etc). This has many benefits
<ul dir="auto">
<li>Talk to users precisely about their code via character-precise error and
diagnostic messages from lowering</li>
<li>Greatly simplify the implementation of critical tools like Revise.jl
which rely on analyzing how the user's source maps to the compiler's data
structures</li>
<li>Allow tools like JuliaInterpreter to use type-inferred and optimized
code, with the potential for huge speed improvements.</li>
</ul>
</li>
<li>Bring improvements for macro authors
<ul dir="auto">
<li>Prototype "automatic hygiene" (no more need for <code>esc()</code>!)</li>
<li>Precise author-defined error reporting from macros</li>
<li>Sketch better interfaces for syntax trees (hopefully!)</li>
</ul>
</li>
</ul>

<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">Design Notes</h1><a id="user-content-design-notes" class="anchor" aria-label="Permalink: Design Notes" href="#design-notes"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Lowering has five symbolic simplification passes:</p>
<ol dir="auto">
<li>Macro expansion - expanding user-defined syntactic constructs by running the
user's macros. This pass also includes a small amount of other symbolic
simplification.</li>
<li>Syntax desugaring - simplifying Julia's rich surface syntax down to a small
number of syntactic forms.</li>
<li>Scope analysis - analyzing identifier names used in the code to discover
local variables, closure captures, and associate global variables to the
appropriate module. Transform all names (kind <code>K"Identifier"</code>) into binding
IDs (kind <code>K"BindingId"</code>) which can be looked up in a table of bindings.</li>
<li>Closure conversion - convert closures to types and deal with captured
variables efficiently where possible.</li>
<li>Flattening to linear IR - convert code in hierarchical tree form to a
flat array of statements; convert control flow into gotos.</li>
</ol>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Syntax trees</h2><a id="user-content-syntax-trees" class="anchor" aria-label="Permalink: Syntax trees" href="#syntax-trees"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Want something something better than <code>JuliaSyntax.SyntaxNode</code>! <code>SyntaxTree</code> and
<code>SyntaxGraph</code> provide this. Some future version of these should end up in
<code>JuliaSyntax</code>.</p>
<p dir="auto">We want to allow arbitrary attributes to be attached to tree nodes by analysis
passes. This separates the analysis pass implementation from the data
structure, allowing passes which don't know about each other to act on a shared
data structure.</p>
<p dir="auto">Design and implementation inspiration comes in several analogies:</p>
<p dir="auto">Analogy 1: the ECS (Entity-Component-System) pattern for computer game design.
This pattern is highly successful because it separates game logic (systems)
from game objects (entities) by providing flexible storage</p>
<ul dir="auto">
<li>Compiler passes are "systems"</li>
<li>AST tree nodes are "entities"</li>
<li>Node attributes are "components"</li>
</ul>
<p dir="auto">Analogy 2: The AoS to SoA transformation. But here we've got a kind of
tree-of-structs-with-optional-attributes to struct-of-Dicts transformation.
The data alignment / packing efficiency and concrete type safe storage benefits
are similar.</p>
<p dir="auto">Analogy 3: Graph algorithms which represent graphs as a compact array of node
ids and edges with integer indices, rather than using a linked data structure.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Problems with Hygiene in Julia's exiting macro system</h3><a id="user-content-problems-with-hygiene-in-julias-exiting-macro-system" class="anchor" aria-label="Permalink: Problems with Hygiene in Julia's exiting macro system" href="#problems-with-hygiene-in-julias-exiting-macro-system"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">To write correct hygienic macros in Julia (as of 2024), macro authors must use
<code>esc()</code> on any any syntax passed to the macro so that passed identifiers escape
to the macro caller scope. However</p>
<ul dir="auto">
<li>This is not automatic and the correct use of <code>esc()</code> is one of the things
that new macro authors find most confusing. (My impression, based on various
people complaining about how confusing <code>esc()</code> is.)</li>
<li><code>esc()</code> wraps expressions in <code>Expr(:escape)</code>, but this doesn't work well when
macros pass such escaped syntax to an inner macro call. As discussed in
<a href="https://github.com/JuliaLang/julia/issues/37691" data-hovercard-type="issue" data-hovercard-url="/JuliaLang/julia/issues/37691/hovercard">Julia issue #37691</a>, macros
in Julia's existing system are not composable by default. Writing
composable macros in the existing system would require preserving the escape
nesting depth when recursing into any macro argument nested expressions.
Almost no macro author knows how to do this and is prepared to pay for the
complexity of getting it right.</li>
</ul>
<p dir="auto">The requirement to use <code>esc()</code> stems from Julia's pervasive use of the simple
<code>Expr</code> data structure which represents a unadorned AST in which names are plain
symbols. For example, a macro call <code>@foo x</code> gets passed the  symbol <code>:x</code>
which is just a name without any information attached to indicate that it came
from the scope where <code>@foo</code> was called.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Hygiene in JuliaLowering</h3><a id="user-content-hygiene-in-julialowering" class="anchor" aria-label="Permalink: Hygiene in JuliaLowering" href="#hygiene-in-julialowering"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">In JuliaLowering we make hygiene automatic and remove <code>esc()</code> by combining names
with scope information. In the language of the paper <a href="https://michaeldadams.org/papers/hygiene/hygiene-2015-popl-authors-copy.pdf" rel="nofollow"><em>Towards the Essence of
Hygiene</em></a>
by Michael Adams, this combination is called a "syntax object". In
JuliaLowering our representation is the tuple <code>(name,scope_layer)</code>, also called
<code>VarId</code> in the scope resolution pass.</p>
<p dir="auto">JuliaLowering's macro expander attaches a unique <em>scope layer</em> to each
identifier in a piece of syntax. A "scope layer" is an integer identifer
combined with the module in which the syntax was created.</p>
<p dir="auto">When expanding macros,</p>
<ul dir="auto">
<li>Any identifiers passed to the macro are tagged with the scope layer they were
defined within.</li>
<li>A new unique scope layer is generated for the macro invocation, and any names
in the syntax produced by the macro are tagged with this layer.</li>
</ul>
<p dir="auto">Subsequently, the <code>(name,scope_layer)</code> pairs are used when resolving bindings.
This ensures that, by default, we satisfy the basic rules for hygenic macros
discussed in Adams' paper:</p>
<ol dir="auto">
<li>A macro can't insert a binding that can capture references other than those
inserted by the macro.</li>
<li>A macro can't insert a reference that can be captured by bindings other than
those inserted by the macro.</li>
</ol>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Lowering of exception handlers</h2><a id="user-content-lowering-of-exception-handlers" class="anchor" aria-label="Permalink: Lowering of exception handlers" href="#lowering-of-exception-handlers"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Exception handling involves a careful interplay between lowering and the Julia
runtime. The forms <code>enter</code>, <code>leave</code> and <code>pop_exception</code> dynamically modify the
exception-related state on the <code>Task</code>; lowering and the runtime work together
to maintain correct invariants for this state.</p>
<p dir="auto">Lowering of exception handling must ensure that</p>
<ul dir="auto">
<li>Each <code>enter</code> is matched with a <code>leave</code> on every possible non-exceptional
program path (including implicit returns generated in tail position).</li>
<li>Each <code>catch</code> block which is entered and handles the exception - by exiting
via a non-exceptional program path - is matched with a <code>pop_exception</code></li>
<li>Each <code>finally</code> block runs, regardless of the way it's entered - either by
normal program flow, an exception, early <code>return</code> or a jump out of an inner
context via <code>break</code>/<code>continue</code>/<code>goto</code> etc.</li>
</ul>
<p dir="auto">The following special forms are emitted into the IR:</p>
<ul dir="auto">
<li><code>(= tok (enter catch_label dynscope))</code> -
push exception handler with catch block at <code>catch_label</code> and dynamic
scope <code>dynscope</code>, yielding a token which is used by <code>leave</code> and
<code>pop_exception</code>. <code>dynscope</code> is only used in the special <code>tryfinally</code> form
without associated source level syntax (see the <code>@with</code> macro)</li>
<li><code>(leave tok)</code> -
pop exception handler back to the state of the <code>tok</code> from the associated
<code>enter</code>. Multiple tokens can be supplied to pop multiple handlers using
<code>(leave tok1 tok2 ...)</code>.</li>
<li><code>(pop_exception tok)</code> - pop exception stack back to state of associated enter</li>
</ul>
<p dir="auto">When an <code>enter</code> is encountered, the runtime pushes a new handler onto the
<code>Task</code>'s exception handler stack which will jump to <code>catch_label</code> when an
exception occurs.</p>
<p dir="auto">There are two ways that the exception-related task state can be restored</p>
<ol dir="auto">
<li>By encountering a <code>leave</code> which will restore the handler state with <code>tok</code>.</li>
<li>By throwing an exception. In this case the runtime will pop one handler
automatically and jump to the catch label with the new exception pushed
onto the exception stack. On this path the exception stack state must be
restored back to the associated <code>enter</code> by encountering <code>pop_exception</code>.</li>
</ol>
<p dir="auto">Note that the handler and exception stack represent two distinct types of
exception-related state restoration which need to happen. Note also that the
"handler state restoration" actually includes several pieces of runtime state
including GC flags - see <code>jl_eh_restore_state</code> in the runtime for that.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Lowering finally code paths</h3><a id="user-content-lowering-finally-code-paths" class="anchor" aria-label="Permalink: Lowering finally code paths" href="#lowering-finally-code-paths"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>

multiple code paths may traverse the finally block. For example, consider the
code</p>

<p dir="auto">In this situation there's four distinct code paths through the finally block:</p>
<ol dir="auto">
<li><code>return f(x)</code> needs to call <code>val = f(x)</code>, leave the <code>try</code> block, run <code>h()</code> then
return <code>val</code>.</li>
<li><code>continue</code> needs to call <code>h()</code> then jump to the start of the while loop</li>
<li><code>break</code> needs to call <code>h()</code> then jump to the exit of the while loop</li>
<li>If an exception occurs in <code>f(x)</code> or <code>g(x)</code>, we need to call <code>h()</code> before
falling back into the while loop.</li>
</ol>
<p dir="auto">To deal with these we create a <code>finally_tag</code> variable to dynamically track
which action to take after the finally block exits. Before jumping to the block
we set this variable to a unique integer tag identifying the incoming code
path. At the exit of the user's code (<code>h()</code> in this case) we perform the jump
appropriate to the <code>break</code>, <code>continue</code> or <code>return</code> as necessary based on the tag.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">How does macro expansion work?</h3><a id="user-content-how-does-macro-expansion-work" class="anchor" aria-label="Permalink: How does macro expansion work?" href="#how-does-macro-expansion-work"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>

<p dir="auto">First we copy the AST here. This is mostly a trivial deep copy of <code>Expr</code>s and
shallow copy of their non-<code>Expr</code> children, except for when they contain
embedded <code>CodeInfo/phi/phic</code> nodes which are also deep copied.</p>
<p dir="auto">Second we expand macros recursively by calling</p>
<p dir="auto"><code>jl_expand_macros(expr, inmodule, macroctx, onelevel, world, throw_load_error)</code></p>
<p dir="auto">This relies on state indexed by <code>inmodule</code> and <code>world</code>, which gives it some
funny properties:</p>
<ul dir="auto">
<li><code>module</code> expressions can't be expanded: macro expansion depends on macro
lookup within the module, but we can't do that without <code>eval</code>.</li>
</ul>
<p dir="auto">Expansion proceeds from the outermost to innermost macros. So macros see any
macro calls or quasiquote (<code>quote/$</code>) in their children as unexpanded forms.</p>
<p dir="auto">Things which are expanded:</p>
<ul dir="auto">
<li><code>quote</code> is expanded using flisp code in <code>julia-bq-macro</code>
<ul dir="auto">
<li>symbol / ssavalue -&gt; <code>QuoteNode</code> (inert)</li>
<li>atom -&gt; itself</li>
<li>at depth zero, <code>$</code> expands to its content</li>
<li>Expressions <code>x</code> without <code>$</code> expand to <code>(copyast (inert x))</code></li>
<li>Other expressions containing a <code>$</code> expand to a call to <code>_expr</code> with all the
args mapped through <code>julia-bq-expand-</code>. Roughly!</li>
<li>Special handling exists for multi-splatting arguments as in <code>quote quote $$(x...) end end</code></li>
</ul>
</li>
<li><code>macrocall</code> proceeds with
<ul dir="auto">
<li>Expand with <code>jl_invoke_julia_macro</code>
<ul dir="auto">
<li>Call <code>eval</code> on the macro name (!!) to get the macro function. Look up
the method.</li>
<li>Set up arguments for the macro calling convention</li>
<li>Wraps errors in macro invocation in <code>LoadError</code></li>
<li>Returns the expression, as well as the module at
which that method of that macro was defined and <code>LineNumberNode</code> where
the macro was invoked in the source.</li>
</ul>
</li>
<li>Deep copy the AST</li>
<li>Recursively expand child macros in the context of the module where the
macrocall method was defined</li>
<li>Wrap the result in <code>(hygienic-scope ,result ,newctx.m ,lineinfo)</code> (except
for special case optimizations)</li>
</ul>
</li>
<li><code>hygenic-scope</code> expands <code>args[1]</code> with <code>jl_expand_macros</code>, with the module
of expansion set to <code>args[2]</code>.  Ie, it's the <code>Expr</code> representation of the
module and expression arguments to <code>macroexpand</code>. The way this returns
either <code>hygenic-scope</code> or unwraps is a bit confusing.</li>
<li>"<code>do</code> macrocalls" have their own special handling because the macrocall is
the child of the <code>do</code>. This seems like a mess!!</li>
</ul>

<ul dir="auto">

<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">How does scope resolution work?</h4><a id="user-content-how-does-scope-resolution-work" class="anchor" aria-label="Permalink: How does scope resolution work?" href="#how-does-scope-resolution-work"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">We traverse the AST starting at the root paying attention to certian nodes:</p>
<ul dir="auto">
<li>Nodes representing identifiers (Identifier, operators, var)
<ul dir="auto">
<li>If a variable exists in the table, it's <em>replaced</em> with the value in the table.</li>
<li>If it doesn't exist, it becomes an <code>outerref</code></li>
</ul>
</li>
<li>Variable scoping constructs: <code>local</code>, <code>local-def</code>
<ul dir="auto">
<li>collected by scope-block</li>
<li>removed during traversal</li>
</ul>
</li>
<li>Scope metadata <code>softscope</code>, <code>hardscope</code> - just removed</li>
<li>New scopes
<ul dir="auto">
<li><code>lambda</code> creates a new scope containing itself and its arguments,
otherwise copying the parent scope. It resolves the body with that new scope.</li>
<li><code>scope-block</code> is really complicated - see below</li>
</ul>
</li>
<li>Scope queries <code>islocal</code>, <code>locals</code>
<ul dir="auto">
<li><code>islocal</code> - statically expand to true/false based on whether var name is a local var</li>
<li><code>locals</code> - return list of locals - see <code>@locals</code></li>
<li><code>require-existing-local</code> - somewhat like <code>islocal</code>, but allows globals
too (whaa?! naming) and produces a lowering error immediately if variable
is not known.  Should be called <code>require-in-scope</code> ??</li>
</ul>
</li>
<li><code>break-block</code>, <code>symbolicgoto</code>, <code>symboliclabel</code> need special handling because
one of their arguments is a non-quoted symbol.</li>
<li>Add static parameters for generated functions <code>with-static-parameters</code></li>
<li><code>method</code> - special handling for static params</li>
</ul>
<p dir="auto"><code>scope-block</code> is the complicated bit. It's processed by</p>
<ul dir="auto">
<li>Searching the expressions within the block for any <code>local</code>, <code>local-def</code>,
<code>global</code> and assigned vars. Searching doesn't recurse into <code>lambda</code>,
<code>scope-block</code>, <code>module</code> and <code>toplevel</code></li>
<li>Building lists of implicit locals or globals (depending on whether we're in a
top level thunk)</li>
<li>Figuring out which local variables need to be renamed. This is any local variable
with a name which has already occurred in processing one of the previous scope blocks</li>
<li>Check any conflicting local/global decls and soft/hard scope</li>
<li>Build new scope with table of renames</li>
<li>Resolve the body with the new scope, applying the renames</li>
</ul>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Notes on toplevel-only forms and eval-related functions</h3><a id="user-content-notes-on-toplevel-only-forms-and-eval-related-functions" class="anchor" aria-label="Permalink: Notes on toplevel-only forms and eval-related functions" href="#notes-on-toplevel-only-forms-and-eval-related-functions"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">In the current Julia runtime,</p>
<p dir="auto"><code>Base.eval()</code></p>
<ul dir="auto">
<li>Uses <code>jl_toplevel_eval_in</code> which calls <code>jl_toplevel_eval_flex</code></li>
</ul>
<p dir="auto"><code>jl_toplevel_eval_flex(mod, ex)</code></p>
<ul dir="auto">
<li>Lowers if necessay</li>
<li>Evaluates certain blessed top level forms
<ul dir="auto">
<li><code>:.</code></li>
<li><code>:module</code></li>
<li><code>:using</code></li>
<li><code>:import</code></li>
<li><code>:public</code></li>
<li><code>:export</code></li>
<li><code>:global</code></li>
<li><code>:const</code></li>
<li><code>:toplevel</code></li>
<li><code>:error</code></li>
<li><code>:incomplete</code></li>
<li>Identifier and literals</li>
</ul>
</li>
<li>Otherwise expects <code>Expr(:thunk)</code>
<ul dir="auto">
<li>Use codegen "where necessary/profitable" (eg ccall, has_loops etc)</li>
<li>Otherwise interpret via <code>jl_interpret_toplevel_thunk</code></li>
</ul>
</li>
</ul>
<p dir="auto">Should we lower the above blessed top level forms to julia runtime calls?
Pros:</p>
<ul dir="auto">
<li>Semantically sound. Lowering should do syntax checking in things like
<code>Expr(:using)</code> rather than doing this in the runtime support functions.</li>
<li>Precise lowering error messages</li>
<li>Replaces more Expr usage</li>
<li>Replaces a whole pile of C code with significantly less Julia code</li>
<li>Lowering output becomes more consistently imperative
Cons:</li>
<li>Lots more code to write</li>
<li>May need to invent intermediate data structures to replace <code>Expr</code></li>
<li>Bootstrap?</li>
<li>Some forms require creating toplevel thunks</li>
</ul>
<p dir="auto">In general, we'd be replacing current <em>declarative</em> lowering targets like
<code>Expr(:using)</code> with an <em>imperative</em> call to a <code>Core</code> API instead. The call and
the setup of its arguments would need to go in a thunk. We've currently got an
odd mixture of imperative and declarative lowered code.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Notes on Racket's hygiene</h2><a id="user-content-notes-on-rackets-hygiene" class="anchor" aria-label="Permalink: Notes on Racket's hygiene" href="#notes-on-rackets-hygiene"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">People look at <a href="https://racket-lang.org/" rel="nofollow">Racket</a> as an example of a very
complete system of hygienic macros. We should learn from them, but keeping in
mind that Racket's macro system is inherently more complicated. Racket's
current approach to hygiene is described in an <a href="https://www.youtube.com/watch?v=Or_yKiI3Ha4" rel="nofollow">accessible talk</a>
and in more depth in <a href="https://www-old.cs.utah.edu/plt/publications/popl16-f.pdf" rel="nofollow">a paper</a>.</p>
<p dir="auto">Some differences which makes Racket's macro expander different from Julia:</p>
<ul dir="auto">
<li>Racket allows <em>local</em> definitions of macros. Macro code can be embedded in an
inner lexical scope and capture locals from that scope, but still needs to be
executed at compile time. Julia supports macros at top level scope only.</li>
<li>Racket goes to great lengths to execute the minimal package code necessary to
expand macros; the "pass system". Julia just executes all top level
statements in order when precompiling a package.</li>
<li>As a lisp, Racket's surface syntax is dramatically simpler and more uniform</li>
</ul>
</article></div>
