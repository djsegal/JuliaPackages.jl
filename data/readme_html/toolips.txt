<p dir="auto"><code>Toolips</code> is an extensible web and server-development framework for the Julia programming language.</p>
<ul dir="auto">
<li><strong>HTTPS capable</strong> Can be deployed with SSL.</li>
<li><strong>Extensible</strong> server platform.</li>
<li><strong>Declarative</strong> and <strong>composable</strong> files, html, Javascript, <em>and</em> CSS templating syntax provided by <a href="https://github.com/ChifiSource/ToolipsServables.jl">ToolipsServables</a>.</li>
<li><strong>Modular</strong> servers -- toolips applications are <strong>regular Julia Modules</strong>.</li>
<li><strong>Versatilility</strong> -- toolips can be used for <em>all</em> use-cases, from full-stack web-development to simple endpoints.</li>
<li><strong>Parallel Computing</strong> -- <em>Declarative</em> process management provided by <a href="https://github.com/ChifiSource/ParametricProcesses.jl">parametric processes</a>.</li>
</ul>
<p dir="auto">Toolips is able to create ...</p>
<ul dir="auto">
<li>Endpoints</li>
<li>File servers</li>
<li>Fullstack web applications</li>
<li>Other HTTP/HTTPS servers (e.g. Proxy server)</li>
<li>UDP servers and services (e.g. Data-base cursors, DNS servers)</li>
</ul>

<p dir="auto"><code>Toolips</code> is available in <em>three</em> different version flavors:</p>
<ul dir="auto">
<li>Latest (main) -- The main working version of toolips.</li>
<li>stable (#stable) -- Faster, more frequent updates than main; stable... but some new features are not fully implemented.</li>
<li>and Unstable (#Unstable) -- Latest updates, packages could be temporarily broken in different ways from time to time.</li>
</ul>

<p dir="auto">In <code>Toolips</code>, projects are modules which <strong>export</strong> <code>Toolips</code> types. These special types are</p>
<ul dir="auto">
<li>Any sub-type of <code>AbstractRoute</code>.</li>
<li>Any sub-type of <code>Extension</code>.</li>
<li>or a <code>Vector{&lt;:AbstractRoute}</code></li>
</ul>
<p dir="auto">Here is a simple " hello world" project.</p>

<p dir="auto">To create a <code>Route</code>, we provide the <code>route</code> <code>Function</code> with a <strong>target</strong>, a <code>String</code> path starting at <code>/</code> to mount the website's base URL and a <code>Function</code> passed through <strong>do</strong>. The general <code>Toolips</code> process on a route is creating data and then writing it to the <code>Connection</code> with <code>write!</code>. The <code>Function</code> we provide will take a <code>&lt;:</code> of an <code>AbstractConnection</code>. We are able to annotate this argument in our <code>route</code> call to change our route's functionality based on the dispatch. This creates what is effectively <em>multiple dispatch routing</em>, consider the example below:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="module HelloWorld

    write!(c, &quot;hello world&quot;)
end

mobile_home = route(&quot;/&quot;) do c::MobileConnection
    write!(c, &quot;hello world&quot;)
end

# multi-routing our home
home = route(mobile_home, desktop_home)
export start!, home
end"><pre><span class="pl-k">module</span> HelloWorld

<p dir="auto">In the case above, mobile clients will be redirected to the latter <code>Function</code>, as their <code>Connection</code> will convert into a <code>MobileConnection</code>.</p>
<p dir="auto">Routes are stored in the <code>Connection</code> under <code>Connection.routes</code>. We can dynamically change our <code>routes</code> by mutating this <code>Vector{&lt;:AbstractRoute}</code>.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="module ToolipsServer

<p dir="auto">Extensions appear in <code>Toolips</code> in four main forms:</p>
<ul dir="auto">
<li><code>Connection</code> extensions,</li>
<li>routing extensions,</li>
<li>server extensions,</li>
<li>and <code>Component</code> extensions.</li>
</ul>
<p dir="auto"><code>Connection</code> extensions allow us to utilize <code>MultiRoute</code> with new multiple dispatch <code>Connection</code> configurations. Routing extensions allow us to change the functionality of the <code>Toolips</code> router in different instances. Server extensions allow us to add autoloaded data, or perform actions alongside before our routes whenever a <code>Connection</code> is served. Finally, <code>Component</code> extensions give us more composable <code>Component</code> types to work with, and more high-level web-development capabilities.</p>
<p dir="auto"><code>Connection</code> extensions are typically used through <code>MultiRoute</code>. This is done by providing multiple routes to <code>route</code>, which will call different routes depending on the incoming client <code>Connection</code>. For example, the <code>MobileConnection</code> is the quintessential <code>Connection</code> extension provided by <code>Toolips</code>.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="module Sample

<p dir="auto">Another type of extension that can be created for toolips is the routing extension. Routing extensions are created by extending the <code>route!</code> function. This function may be extended by adding new methods for <code>Route</code> types (<code>&lt;:AbstractRoute</code>), <code>Connection</code> types (<code>&lt;:AbstractConnection</code>), a <code>Vector</code> with <code>&lt;:AbstractRoute</code> as its type parameter, or extension types (<code>&lt;:AbstractExtension</code>).</p>
<ul dir="auto">
<li>on an incoming <code>Connection</code>, <code>route!</code> is initially called on each extension using <code>route!(c, ::AbstractExtension)</code> (only if the binding exists) before the main routing process begins -- giving extensions the first oppurtunity to <code>write!</code> to the <code>Connection</code>.</li>
<li><code>route!</code> is called twice during the routing process, first on the <code>Connection</code> and the <code>Vector{&lt;:AbstractRoute}</code> that holds the routes. This is where the startup printout of <code>Toolips</code> comes to relevance:</li>
</ul>

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">multi-threading</h2><a id="user-content-multi-threading" class="anchor" aria-label="Permalink: multi-threading" href="#multi-threading"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>Toolips</code> includes a distributed computing implementation built atop <a href="https://github.com/ChifiSource/ParametricProcesses.jl">ParametricProcesses</a>. This implementation of multi-threading allows us to serve each incoming connection on a different thread simply by providing the number of threads to utilize.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content=""><pre></pre></div>
<p dir="auto">For the most part, this is straightforward -- but there are some things to be aware of...</p>
<ul dir="auto">
<li>When a server is multi-threaded, its routes will be passed an <code>IOConnection</code> -- not a regular <code>Connection</code>. Routes will need to be annotated as an <code>AbstractConnection</code> (to work with single or multiple threads,) an <code>IOConnection</code> (to work with multi-threaded servers only,) or an <code>AbstractConnection</code> to work with multi-threaded servers.</li>
<li>A multi-threaded server <strong>must be a project</strong>. The <code>Module</code> cannot be defined below <code>Main</code>, it must have its own <code>Project.toml</code> file. This is because your <code>Module</code> needs to be used across multiple threads from the same environment; <code>ParametricProcesses</code> will not be able to serialize your entire server and send it over to all of your threads. Instead, it is used via the environment. An environment compatible with this is of course set up for you when <code>new_app</code> is used.</li>
<li>Finally, only certain objects will be serialized across threads. This means that we must be weary of what is in our <code>IOConnection.data</code>, or we might run into problems serializing across threads. This will primarily happen with functions. For example, consider the following <code>Session</code> callback:</li>
</ul>

<p dir="auto">Because <code>Tooips</code> was built primarily to drive other <a href="https://github.com/ChifiSource">chifi</a> software, <code>ChifiSource</code> has created a number of projects with <code>Toolips</code>. Here is a list of large projects we have created based on <code>Toolips</code>, along with their repository links.</p>
<ul dir="auto">
<li><a href="https://github.com/ChifiSource/Olive.jl">Olive</a> <code>Olive</code> is <em>the</em> reason that <code>Toolips</code> was created in the first place. <code>Olive</code> is a parametric extensible notebook editor for Julia. This is a great example to demonstrate a full-scale project.
<ul dir="auto">
<li>Using: <code>Toolips</code>, <a href="https://github.com/ChifiSource/ToolipsServables.jl">ToolipsServables</a>, <a href="https://github.com/ChifiSource/ToolipsSession.jl">ToolipsSession</a></li>
</ul>
</li>
<li><a href="https://github.com/ChifiSource/Gattino.jl">Gattino</a> <code>Gattino</code> is <code>Toolips</code>-based, or rather <code>ToolipsServables</code>-based SVG data visualizations for Julia. A look into this project may give insight on how <code>ToolipsServables</code> and <code>Toolips</code> might be used without a <code>WebServer</code>.
<ul dir="auto">
<li>Using: <a href="https://github.com/ChifiSource/ToolipsServables.jl">ToolipsServables</a></li>
</ul>
</li>
<li><a href="https://github.com/emmaccode/JLChat.jl">JLChat</a> <code>JLChat</code> is emma's <code>Toolips</code>-built chatroom demonstration. This example is great for demonstrating how to create a small application in <code>Toolips</code>, along with using <a href="https://github.com/ChifiSource/ToolipsSession.jl">ToolipsSession</a> and its RPC feature.
<ul dir="auto">
<li>Using: <code>Toolips</code>, <a href="https://github.com/ChifiSource/ToolipsServables.jl">ToolipsServables</a>, <a href="https://github.com/ChifiSource/ToolipsSession.jl">ToolipsSession</a></li>
</ul>
</li>
<li><a href="https://github.com/ChifiSource/ChiProxy.jl">ChiProxy</a> <code>ChiProxy</code> is a <code>Toolips</code>-bound proxy server for Julia. This proxy server demonstrates replacing the <code>Toolips</code> router by extending functions, allowing for routes to be routed by host rather than just <code>target</code> -- as well as a plethora of other special capabilities.
<ul dir="auto">
<li>Using: <code>Toolips</code></li>
</ul>
</li>
<li>ChiNS <code>ChiNS</code> is a Domain Name Server built with <code>Toolips</code>. This project provides a running example of <code>ToolipsUDP</code>, as well as a pretty nice demonstration of how to create a DNS server.
<ul dir="auto">
<li>Using: <a href="https://github.com/ChifiSource/ToolipsUDP.jl">ToolipsUDP</a></li>

</li>

<p dir="auto">When submitting issues or pull-requests for Olive, it is important to make sure of a few things. We are not super strict, but making sure of these few things will be helpful for maintainers!</p>
<ol dir="auto">
<li>You have replicated the issue on <strong>Unstable</strong></li>
<li>The issue does not currently exist... or does not have a planned implementation different to your own. In these cases, please collaborate on the issue, express your idea and we will select the best choice.</li>
<li><strong>Pull Request TO UNSTABLE</strong></li>
<li>Be <strong>specific</strong> about your issue -- if you are experiencing multiple issues, open multiple issues. It is better to have a high quantity of issues that specifically describe things than a low quantity of issues that describe multiple things.</li>
<li>If you have a new issue, <strong>open a new issue</strong>. It is not best to comment your issue under an unrelated issue; even a case where you are experiencing that issue, if you want to mention <strong>another issue</strong>, open a <strong>new issue</strong>.</li>
<li>Questions are fine, but <strong>not</strong> questions answered inside of this <code>README</code>.</li>
</ol>
