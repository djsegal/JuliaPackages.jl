<p dir="auto">RustyObjectStore.jl is a Julia package for getting and putting data in cloud object stores, such as Azure Blob Storage and AWS S3.
It is built on top of the Rust <a href="https://docs.rs/object_store/" rel="nofollow">object_store crate</a>.
It provides a minimal API and focusses on high throughput.</p>
<p dir="auto"><em>The package is under active development.</em></p>

<p dir="auto">Requests are sent via calling <code>put_object</code> or <code>get_object!</code>, providing the location of the object to put/get, either the data to send or a buffer that will receive data, and credentials.
For <code>put_object</code> the data must be a vector of bytes (<code>UInt8</code>).
For <code>get_object!</code> the buffer must be a vector into which bytes (<code>UInt8</code>) can be written.</p>

<p dir="auto">n_threads is the number of rust executor threads to use. The default 0 means to use threads equal
to the number of cores.</p>
<p dir="auto">cache_capacity is the size of the LRU cache rust uses to cache connection objects. Here a connection
means a unique combination of destination URL, credentials, and per-connection configuration such as
timeouts; it does not mean an HTTP connection.</p>
<p dir="auto">cache_ttl_secs is the time-to-live in seconds for the rust connection cache. Using 0 will disable
ttl eviction.</p>
<p dir="auto">cache_tti_secs is the time in seconds that a connection can be idle before it is removed from the
rust cache. Using 0 will disable tti eviction.</p>
<p dir="auto">multipart_put_threshold is the size in bytes for which any put request over this size will use a
multipart upload. The put part size is determined by the rust object_store implementation, which
uses 10MB.</p>
<p dir="auto">multipart_get_threshold and multipart_get_part_size configure automatic multipart gets. The part
size can be greater than the threshold without breaking anything, but it may not make sense to do so.
The default 8MB for these values was borrowed from CloudStore.jl.</p>
<p dir="auto">concurrency_limit is the max number of concurrent Rust tasks that will be allowed for requests.</p>

<p dir="auto">The Rust <a href="https://github.com/apache/arrow-rs/tree/master/object_store">object_store</a> crate does not provide a C API, so we have defined a C API in <a href="https://github.com/relationalAI/object_store_ffi">object_store_ffi</a>.
RustyObjectStore.jl depends on <a href="https://github.com/JuliaBinaryWrappers/object_store_ffi_jll.jl">object_store_ffi_jll.jl</a> to provides a pre-built object_store_ffi library, and calls into the native library via <code>@ccall</code>.</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Rust/Julia Interaction</h4><a id="user-content-rustjulia-interaction" class="anchor" aria-label="Permalink: Rust/Julia Interaction" href="#rustjulia-interaction"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Julia calls into the native library providing a libuv condition variable and then waits on that variable.
In the native code, the request from Julia is passed into a queue that is processed by a Rust spawned task.
Once the request to cloud storage is complete, Rust signals the condition variable.
In this way, the requests are asynchronous all the way up to Julia and the network processing is handled in the context of native thread pool.</p>
<p dir="auto">For a GET request, Julia provides a buffer for the native library to write into.
This requires Julia to know a suitable size before-hand and requires the native library to do an extra memory copy, but the upside is that Julia controls the lifetime of the memory.</p>
<p dir="auto">The library provides a way for Julia code to be notifed about a panic on a Rust thread through the <code>on_rust_panic</code> argument of <code>init_object_store</code>.
The default behavior is to log the stack trace (if enabled through RUST_BACKTRACE) and exit the process.
The general recommendation is to treat Rust panics as fatal because Julia tasks may hang due to not being notified.</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Threading Model</h4><a id="user-content-threading-model" class="anchor" aria-label="Permalink: Threading Model" href="#threading-model"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Rust object_store uses the <a href="https://docs.rs/tokio" rel="nofollow">tokio</a> async runtime. By default tokio sets up a worker thread pool with a number of threads equal to the number of cores.
This is configurable using the StaticConfig n_threads option described above.</p>
<p dir="auto">The unit of scheduling for tokio is a task, and tasks are created by spawn calls. Tasks must be non-blocking and use async/await for I/O operations,
which also serve as yield points for the cooperative concurrency between tasks. There is work stealing of tasks among the worker thread pools.</p>
<p dir="auto">In object_store_ffi we use buffer_unordered to create a task for each request from Julia (up to a configurable concurrency limit) and allow them to be processed in any order.
The concurrency limit is configurable using the StaticConfig concurrency_limit option described above.</p>
<p dir="auto">Julia will call into object_store_ffi providing a libuv condition variable and then wait on that variable.
In the Rust code, the request from Julia is passed into a queue that is processed by a Rust spawned task. Once the request to cloud storage is complete,
Rust signals the condition variable. In this way, the requests are asynchronous all the way up to Julia and the network processing is handled in the context of Rust thread pool.</p>

<p dir="auto">When working on RustyObjectStore.jl you can either use <a href="https://github.com/JuliaBinaryWrappers/object_store_ffi_jll.jl">object_store_ffi_jll.jl</a> or use a local build of <a href="https://github.com/relationalAI/object_store_ffi">object_store_ffi</a>.
Using object_store_ffi_jll.jl is just like using any other Julia package.
For example, you can change object_store_ffi_jll.jl version by updating the Project.toml <code>compat</code> entry and running <code>Pkg.update</code> to get the latest compatible release,
or <code>Pkg.develop</code> to use an unreleased version.</p>
<p dir="auto">Alternatively, you can use a local build of object_store_ffi library by setting the <code>OBJECT_STORE_LIB</code> environment variable to the location of the build.
For example, if you have the object_store_ffi repository at <code>~/repos/object_store_ffi</code> and build the library by running <code>cargo build --release</code> from the base of that repository,
then you could use that local build by setting <code>OBJECT_STORE_LIB="~/repos/object_store_ffi/target/release"</code>.</p>
<p dir="auto">The <code>OBJECT_STORE_LIB</code> environment variable is intended to be used only for local development.
The library path is set at package precompile time, so if the environment variable is changed RustyObjectStore.jl must recompile for the change to take effect.
You can check the location of the library in use by inspecting <code>RustyObjectStore.rust_lib</code>.</p>
<p dir="auto">Since RustyObjectStore.jl is the primary user of object_store_ffi, the packages should usually be developed alongside one another.
For example, updating object_store_ffi and then testing out the changes in RustyObjectStore.jl.
A new release of object_store_ffi should usually be followed by a new release of object_store_ffi_jll.jl, and then a new release RustyObjectStore.jl.</p>

<p dir="auto">New releases of RustyObjectStore.jl can be made by incrementing the version number in the Project.toml file following <a href="semver.org">Semantic Versioning</a>,
and then commenting on the commit that should be released with <code>@JuliaRegistrator register</code>
(see <a href="https://github.com/RelationalAI/RustyObjectStore.jl/commit/1b1ba5a198e76afe37f75a1d07e701deb818869c#comments">example</a>).
The <a href="https://github.com/JuliaRegistries/Registrator.jl">JuliaRegistrator</a> bot will reply to the comment and automatically open a PR to the <a href="https://github.com/JuliaRegistries/General/">General</a> package registry, that should then automatically be merged within a few minutes.
Once that PR to General is merged the new version of RustyObjectStore.jl is available, and the TagBot Github Action will make add a Git tag and a GitHub release for the new version.</p>
<p dir="auto">RustyObjectStore.jl uses the object_store_ffi library via depending on object_store_ffi_jll.jl which installs pre-built binaries.
So when a new release of object_store_ffi is made, we need there to be a new release of object_store_ffi_jll.jl before we can make a release of RustyObjectStore.jl that uses the latest object_store_ffi.</p>
