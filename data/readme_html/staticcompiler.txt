<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Standalone compilation</h3><a id="user-content-standalone-compilation" class="anchor" aria-label="Permalink: Standalone compilation" href="#standalone-compilation"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">StaticCompiler.jl provides the functions <code>compile_executable</code> and <code>compile_shlib</code> for compiling a Julia function to a native executable or shared library for use from outside of Julia:</p>

<p dir="auto">This approach comes with substantial limitations compared to regular julia code, as you cannot rely on julia's runtime, <code>libjulia</code> (see, e.g., <a href="https://github.com/brenhinkeller/StaticTools.jl">StaticTools.jl</a> for some ways to work around these limitations).</p>
<p dir="auto">The low-level function <code>StaticCompiler.generate_obj</code> (not exported) generates object files. This can be used for more control of compilation. This can be used for example, to cross-compile to other targets.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Method overlays</h3><a id="user-content-method-overlays" class="anchor" aria-label="Permalink: Method overlays" href="#method-overlays"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Sometimes, a julia function you want to statically compile will do things (such as throwing errors) that aren't supported natively by StaticCompiler. One tool provided for working around this is the <code>@device_override</code> macro which lets you swap out a method, but only inside of a StaticCompiler.jl compilation context. For example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia&gt; using Libdl, StaticCompiler

julia&gt; f(x) = g(x) + 1;

julia&gt; g(x) = 2x

julia&gt; @device_override g(x::Int) = x - 10

julia&gt; f(1) # Gives the expected answer in regular julia

<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Limitations</h2><a id="user-content-limitations" class="anchor" aria-label="Permalink: Limitations" href="#limitations"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li>GC-tracked allocations and global variables do <em>not</em> work with <code>compile_executable</code> or <code>compile_shlib</code>. This has some interesting consequences, including that all functions <em>within</em> the function you want to compile must either be inlined or return only native types (otherwise Julia would have to allocate a place to put the results, which will fail).</li>
<li>Since error handling relies on libjulia, you can only throw errors from standalone-compiled (<code>compile_executable</code> / <code>compile_shlib</code>) code if an explicit overload has been defined for that particular error with <code>@device_override</code> (see <a href="src/quirks.jl">quirks.jl</a>).</li>
<li>Type instability. Type unstable code cannot currently be statically compiled via this package.</li>
<li>Doesn't work on Windows (but works in WSL on Windows 10+). PRs welcome.</li>
</ul>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Guide for Package Authors</h2><a id="user-content-guide-for-package-authors" class="anchor" aria-label="Permalink: Guide for Package Authors" href="#guide-for-package-authors"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">To enable code to be statically compiled, consider the following:</p>
<ul dir="auto">
<li>
<p dir="auto">Use type-stable code.</p>
</li>
<li>
<p dir="auto">Use Tuples, NamedTuples, StaticArrays, and other types where appropriate. These allocate on the stack and don't use Julia's heap allocation.</p>
</li>
<li>
<p dir="auto">Avoid Julia's internal allocations. That means don't bake in use of Arrays or Strings or Dicts. Types from StaticTools can help, like StaticStrings and MallocArrays.</p>
</li>
<li>
<p dir="auto">If need be, manage memory manually, using <code>malloc</code> and <code>free</code> from StaticTools.jl. This works with <code>StaticTools.MallocString</code> and <code>StaticTools.MallocArray</code>, or use <a href="https://github.com/MasonProtter/Bumper.jl">Bumper.jl</a>.</p>
</li>
<li>
<p dir="auto">Don't use global variables that need to be allocated and initialized. Instead of global variables, use context structures that have an initialization function. It is okay to use global Tuples or NamedTuples as the use of these should be baked into compiled code.</p>
</li>
<li>
<p dir="auto">Use context variables to store program state, inputs, and outputs. Parameterize these typese as needed, so your code can handle normal types (Arrays) and static-friendly types (StaticArrays, MallocArrays, or StrideArrays). The SciML ecosystem does this well (<a href="https://github.com/SciML/OrdinaryDiffEq.jl/blob/e7f045950615352ddfcb126d13d92afd2bad05e4/src/integrators/type.jl#L82">example</a>). Use of these context variables also enables allocations and initialization to be centralized, so these could be managed by the calling routines in Julia, Python, JavaScript, or other language.</p>
</li>
<li>
<p dir="auto">Arguments and returned values from <code>compile_shlib</code> must be native objects such as <code>Int</code>, <code>Float64</code>, or <code>Ptr</code>. They cannot be things like <code>Tuple{Int, Int}</code> because that is not natively sized. Such objects need to be passed by reference instead of by value.</p>
</li>
<li>
<p dir="auto">If your code needs an array as a workspace, instead of directly creating it, create it as a function argument (where it could default to a standard array creation). That code could be statically compiled if that function argument is changed to a MallocArray or another static-friendly alternative.</p>
</li>
</ul>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Guide for Statically Compiling Code</h2><a id="user-content-guide-for-statically-compiling-code" class="anchor" aria-label="Permalink: Guide for Statically Compiling Code" href="#guide-for-statically-compiling-code"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">If you're trying to statically compile generic code, you may run into issues if that code uses features not supported by StaticCompiler. One option is to change the code you're calling using the tips above. If that is not easy, you may by able to compile it anyway. One option is to use method overlays to change what methods are called.</p>
<p dir="auto"><a href="https://github.com/JuliaDebug/Cthulhu.jl">Cthulhu</a> is a great help in digging into code, finding type instabilities, and finding other sources of code that may break static compilation.</p>
