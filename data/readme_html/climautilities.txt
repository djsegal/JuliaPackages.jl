<p dir="auto"><code>ClimaUtilities</code> is collection of general-purpose tools for CliMA packages.</p>
<p dir="auto"><code>ClimaUtilities.jl</code> contains:</p>
<ul dir="auto">
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/climaartifacts/" rel="nofollow"><code>ClimaArtifacts</code></a>,
a module that provides an MPI-safe way to lazily download artifacts and to tag
artifacts that are being accessed in a given simulation.</li>
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/inputs/" rel="nofollow"><code>SpaceVaryingInputs</code> and
<code>TimeVaryingInputs</code></a> to
work with external input data.</li>
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/datastrctures/" rel="nofollow"><code>DataStructures</code></a>
with useful general purpose data structures.</li>
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/filereaders/" rel="nofollow"><code>FileReaders</code></a>,
<a href="https://clima.github.io/ClimaUtilities.jl/dev/datahandling/" rel="nofollow"><code>DataHandling</code></a>,
and <a href="https://clima.github.io/ClimaUtilities.jl/dev/regridders/" rel="nofollow"><code>Regridders</code></a>
to process input data and remap it onto the simulation grid.</li>
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/outputpathgenerator/" rel="nofollow"><code>OutputPathGenerator</code></a>
to prepare the output directory structure of a simulation.</li>
<li><a href="https://clima.github.io/ClimaUtilities.jl/dev/timemanager/" rel="nofollow"><code>TimeManager</code></a> to
handle dates.</li>
</ul>

<p dir="auto">These guidelines aim to ensure consistent code quality, maintainability, and a
smooth collaborative workflow for <code>ClimaUtilities.jl</code>. Please, read these
guidelines even if you are familiar with other CliMA packages as there may be
some differences.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">A key design principle</h3><a id="user-content-a-key-design-principle" class="anchor" aria-label="Permalink: A key design principle" href="#a-key-design-principle"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>ClimaUtilities.jl</code> is meant to be a foundational package, so it should have
near-zero-cost for features that are not explicitly requested. This means that
it should not depend on any package outside of the standard library and should
have negligible import costs. To accomplish this, everything is implemented in
Julia extensions.</p>
<p dir="auto">Extensions are organized in the following way. The extensions defined in the
<code>Project.toml</code> are defined in terms of the packages they require to be loaded.
This avoids circular dependencies among extensions. Each of these extensions
<code>include</code>s modules that match what is defined in <code>src</code>.</p>
<p dir="auto">For example, <code>ClimaUtilitiesClimaCoreNCDatasetsExt</code> is loaded when <code>ClimaCore</code>
and <code>NCDatasets</code> are loaded. Internally, <code>ClimaUtilitiesClimaCoreNCDatasetsExt</code>
loads <code>DataHandlingExt.jl</code>, <code>SpaceVaryingInputsExt.jl</code>, and
<code>TimeVaryingInputsExt.jl</code>. Each of them implements methods defined in
<code>src/DataHandling.jl</code>, <code>src/SpaceVaryingInputs.jl</code>, and
<code>src/TimeVaryingInputs.jl</code> respectively</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Tests and environments</h3><a id="user-content-tests-and-environments" class="anchor" aria-label="Permalink: Tests and environments" href="#tests-and-environments"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">We prioritize well-tested code to guarantee <code>ClimaUtilities.jl</code> functions
reliably. Here are some principles we follow:</p>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Tests are collected in the <code>test</code> folder and are exclusively there</h4><a id="user-content-tests-are-collected-in-the-test-folder-and-are-exclusively-there" class="anchor" aria-label="Permalink: Tests are collected in the test folder and are exclusively there" href="#tests-are-collected-in-the-test-folder-and-are-exclusively-there"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This means that:</p>
<ul dir="auto">
<li>All the tests can be run with <code>Pkg.test()</code> or <code>julia --project=test tests/runtests.jl</code>;</li>
<li>There are no special tests in the Buildkite pipeline;</li>
<li>In fact, we use Buildkite only to run the tests with MPI/GPUs.</li>
</ul>
<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">There are no checked-in <code>Manifest.toml</code> files</h4><a id="user-content-there-are-no-checked-in-manifesttoml-files" class="anchor" aria-label="Permalink: There are no checked-in Manifest.toml files" href="#there-are-no-checked-in-manifesttoml-files"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">While checking in <code>Manifest.toml</code> files ensures reproducibility, it also
introduces some nuisance, including:</p>
<ul dir="auto">
<li>lot of git/repository noise just for "up deps";</li>
<li>multiple environments that have to be managed;</li>
<li>busywork to keep the manifests updated.</li>
</ul>
<p dir="auto">In this repository, we have four environments:</p>
<ul dir="auto">
<li>project,</li>
<li>documentation,</li>
<li>test,</li>
<li>buildkite.</li>
</ul>
<p dir="auto">The buildkite environment, in <code>.buildkite</code>, contains everything that is required
to test <code>ClimaUtilities.jl</code> in its most general configuration (ie, including
<code>CUDA.jl</code> and <code>MPI.jl</code>). As the name suggests, this is the (only) environment
used by our Buildkite pipeline.</p>

<p dir="auto">:note: Please, open an issue if you find workflow problems/friction with this
system.</p>
</blockquote>

<div class="markdown-heading" dir="auto"><h4 class="heading-element" dir="auto">Code Formatting with <code>JuliaFormatter.jl</code></h4><a id="user-content-code-formatting-with-juliaformatterjl" class="anchor" aria-label="Permalink: Code Formatting with JuliaFormatter.jl" href="#code-formatting-with-juliaformatterjl"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">One of the tests consists in checking that the code is uniformly formatted. We
use <a href="https://github.com/domluna/JuliaFormatter.jl">JuliaFormatter.jl</a> to achieve
consistent formatting. Here's how to use it:</p>
<p dir="auto">You can either install in your base environment with</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia -e 'using Pkg; Pkg.add(&quot;JuliaFormatter&quot;)'"><pre>julia -e <span class="pl-s"><span class="pl-pds">'</span>using Pkg; Pkg.add("JuliaFormatter")<span class="pl-pds">'</span></span></pre></div>
<p dir="auto">or use it from within the <code>TestEnv</code> or the <code>.buildkite</code> environments (see previous section).</p>
<p dir="auto">Then, you can format the package running:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="using JuliaFormatter; format(&quot;.&quot;)"><pre><span class="pl-k">using</span> JuliaFormatter; <span class="pl-c1">format</span>(<span class="pl-s"><span class="pl-pds">"</span>.<span class="pl-pds">"</span></span>)</pre></div>
<p dir="auto">or just with <code>format(".")</code> if the package is already imported.</p>
<p dir="auto">The rules for formatting are defined in the <code>.JuliaFormatter.toml</code>.</p>
<p dir="auto">If you are used to formatting from the command line instead of the REPL, you can
install <code>JuliaFormatter</code> in your base environment and call</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="julia -e 'using JuliaFormatter; format(&quot;.&quot;)'"><pre>julia -e <span class="pl-s"><span class="pl-pds">'</span>using JuliaFormatter; format(".")<span class="pl-pds">'</span></span></pre></div>
<p dir="auto">You could also define a shell alias</p>
<div class="highlight highlight-source-shell notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="alias julia_format_here=&quot;julia -e 'using JuliaFormatter; format(\&quot;.\&quot;)'&quot;"><pre><span class="pl-c1">alias</span> julia_format_here=<span class="pl-s"><span class="pl-pds">"</span>julia -e 'using JuliaFormatter; format(<span class="pl-cce">\"</span>.<span class="pl-cce">\"</span>)'<span class="pl-pds">"</span></span></pre></div>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Pull Request (PR) and commits</h3><a id="user-content-pull-request-pr-and-commits" class="anchor" aria-label="Permalink: Pull Request (PR) and commits" href="#pull-request-pr-and-commits"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Here's how to structure your contributions effectively:</p>
<ul dir="auto">
<li>Descriptive Title: Briefly summarize the changes your PR introduces. Commit
titles should preferably be under 50 characters, start with a capital latter,
and use imperative verbs (e.g., "Remove superfluous function call").</li>
<li>Detailed Description: Explain the purpose of your changes. Focus on the
intent.</li>
<li>Breaking Changes: If your PR introduces breaking changes, highlight them
clearly in the description.</li>
</ul>
<p dir="auto">Your pull request can contain one or multiple commits. In either cases, it is
