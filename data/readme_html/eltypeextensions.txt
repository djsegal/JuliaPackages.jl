<p dir="auto">EltypeExtensions.jl is a mini toolbox for eltype-related conversions. The motivation of this package comes from manipulating (nested) arrays with different eltypes. However if you have any reasonable idea that works on other instances, feel free to write an issue/pull request.</p>
<p dir="auto">We note that this package has some overlap with <a href="https://github.com/emmt/TypeUtils.jl">TypeUtils.jl</a> and <a href="https://github.com/emmt/Unitless.jl">Unitless.jl</a>.</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>elconvert</code> and <code>_to_eltype</code></h3><a id="user-content-elconvert-and-_to_eltype" class="anchor" aria-label="Permalink: elconvert and _to_eltype" href="#elconvert-and-_to_eltype"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>elconvert(T, x)</code> works like <code>convert(T, x)</code>, except that <code>T</code> refers to the eltype of the result. This can be useful for generic codes.</p>
<p dir="auto">It should be always true that <code>elconvert(T, x) isa _to_eltype(T, typeof(x))</code>. However, since <code>elconvert</code> and <code>_to_eltype</code> use different routines, it's possible that the equality doesn't hold for some types. Please submit an issue or PR if that happens.</p>
<p dir="auto">If <code>typeof(x)</code> is not in Base or stdlib, the package who owns the type should implement corresponding <code>_to_eltype</code> or <code>elconvert</code>. <code>elconvert</code> has fallbacks, in which case it could be unnecessary:</p>
<ul dir="auto">
<li>For a subtype of <code>AbstractArray</code>, <code>elconvert</code> calls the constructor <code>AbstractArray{T}</code> and <code>_to_eltype</code> returns <code>Array</code>.</li>
<li>For a subtype of <code>AbstractUnitRange</code>, <code>elconvert</code> calls the constructor <code>AbstractUnitRange{T}</code>.</li>
<li>For a subtype of <code>AbstractRange</code>, <code>elconvert</code> uses broadcast through <code>map</code>.</li>
<li>For a <code>Tuple</code>, <code>elconvert</code> uses dot broadcast.</li>
<li>For other types, <code>elconvert</code> calls <code>convert</code> and <code>_to_eltype</code>.</li>
</ul>
<p dir="auto">However, <code>_to_eltype</code> must be implemented for each type to support <code>baseconvert</code> and <code>precisionconvert</code>. The following types from Base and stdlib are explicitly supported by <code>_to_eltype</code>:</p>

<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto"><code>basetype</code> and <code>precisiontype</code></h3><a id="user-content-basetype-and-precisiontype" class="anchor" aria-label="Permalink: basetype and precisiontype" href="#basetype-and-precisiontype"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">The <code>basetype</code> is used for nested collections, where <code>eltype</code> is repeatedly applied until the bottom. <code>precisiontype</code> has a similar idea, but goes deeper when possible. <code>precisiontype</code> is used to manipulate the accuracy of (nested) collections.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Method naming convention</h3><a id="user-content-method-naming-convention" class="anchor" aria-label="Permalink: Method naming convention" href="#method-naming-convention"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<ul dir="auto">
<li><code>sometype(T)</code> gets the <code>sometype</code> of type <code>T</code>.</li>
<li><code>sometype(x) = sometype(typeof(x))</code> is also provided for convenience.</li>
<li><code>_to_sometype(T,S)</code> converts the type <code>S</code> to have the <code>sometype</code> of <code>T</code>.</li>
<li><code>someconvert(T,A)</code> converts <code>A</code> to have the <code>sometype</code> of <code>T</code>.</li>
</ul>
<p dir="auto">where <code>some</code> can be <code>el</code>, <code>base</code> and <code>precision</code>.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">On <code>precisionconvert</code></h3><a id="user-content-on-precisionconvert" class="anchor" aria-label="Permalink: On precisionconvert" href="#on-precisionconvert"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto"><code>precisionconvert</code> accepts an optional third argument <code>prec</code>.</p>
<ul dir="auto">
<li>When <code>T</code> has static precision, <code>prec</code> has no effect.</li>
<li>When <code>T</code> has dynamic precision, <code>prec</code> specifies the precision of conversion. When <code>prec</code> is not provided, the precision is decided by the external setup from <code>T</code>. The difference is significant when <code>precisionconvert</code> is called by another function. See the document for an example.</li>
<li>When <code>T</code> is an integer, the conversion will dig into <code>Rational</code> as well. In contrast, since <code>Rational</code> as a whole is more "precise" than an integer, <code>precisiontype</code> doesn't unwrap <code>Rational</code>.</li>
</ul>
