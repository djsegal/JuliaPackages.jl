<div class="markdown-heading" dir="auto"><h1 class="heading-element" dir="auto">BasicAkerRelationalScore</h1><a id="user-content-basicakerrelationalscore" class="anchor" aria-label="Permalink: BasicAkerRelationalScore" href="#basicakerrelationalscore"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">This is a dimensionality reduction algorithm which has the goal of maintaining interpretability i.e we eliminate variables directly from potential models that don't seem to add any predictive power. This is accomplished by the use of decision trees to approximate a function between two variables. This is a modified version of the <a href="#1"><em>Predictive Power Score</em></a> inspired by Florian Wetschoreck's article</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">The Problem</h2><a id="user-content-the-problem" class="anchor" aria-label="Permalink: The Problem" href="#the-problem"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">We'll start with a set of observations which can be further split into a set of features <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$F$</math-renderer> (<strong>things we want to use to predict</strong>) and targets <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$T$</math-renderer> (<strong>things we want to predict</strong>). The elements <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x\in F$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y\in T$</math-renderer> are time-series of some measurable quantity. The main goal will be to minimize the set of features and targets we want to use to build models based on how well a feature does at predicting all the targets. How can we choose a good minimal set of observables to build models with? If we can potentially identify that there is a function between <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer>, then we can say that <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> has predictive power with respect to <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer>. So, how can identify if a function potentially exists between <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer>? which basically means we can build</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Universal Function Approximators</h3><a id="user-content-universal-function-approximators" class="anchor" aria-label="Permalink: Universal Function Approximators" href="#universal-function-approximators"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">Decision Trees are universal function approximators which basically means, we can split two dimensional subset of our data into different bins which are chosen based on minimizing a cost function. In this case the boundaries of the bins are chosen so as to minimize the error of the tree model makes when making predicitons. Spliting the data into different bins is constructing a function, but we need to understand how well this function does compared to a more naive model of prediction: taking the median of the target <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer> and always guessing that any <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> will map to the median.</p>
<div class="markdown-heading" dir="auto"><h3 class="heading-element" dir="auto">Comparing Model Performance</h3><a id="user-content-comparing-model-performance" class="anchor" aria-label="Permalink: Comparing Model Performance" href="#comparing-model-performance"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">If we have two different models <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$g_1$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$g_2$</math-renderer> mapping feature <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> to  target <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer>, then we will need a way to choose which model does a better job at predicting <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer> from <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer>. One way to do this is to look at the mean absolute error of each model which is defined as</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$$\text{MAE}=\sum\limits_{i=1}^{N}|y_i-g(x_i)|$$</math-renderer></p>
<p dir="auto">We can compare the how well the "smart model" does as compared to the "naive model" by looking at the ratio of $\text{MAE}<em>{\text{smart}}$ to $\text{MAE}</em>{\text{naive}}$ which is defined as <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r$</math-renderer></p>
<p dir="auto">as the smart model does better, this ratio becomes smaller and as the smart model starts doing as good or worse than the naive model, this ratio becomes larger. Up to this point, this is pretty much just the predictive power score. If our smart model is doing better than the naive model, then we have at least established that constructing a function between <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$x$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$y$</math-renderer> is useful which means that we should include it in whatever models that we wish to build.</p>
<div class="markdown-heading" dir="auto"><h2 class="heading-element" dir="auto">Making the BARS</h2><a id="user-content-making-the-bars" class="anchor" aria-label="Permalink: Making the BARS" href="#making-the-bars"><svg class="octicon octicon-link" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="m7.775 3.275 1.25-1.25a3.5 3.5 0 1 1 4.95 4.95l-2.5 2.5a3.5 3.5 0 0 1-4.95 0 .751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018 1.998 1.998 0 0 0 2.83 0l2.5-2.5a2.002 2.002 0 0 0-2.83-2.83l-1.25 1.25a.751.751 0 0 1-1.042-.018.751.751 0 0 1-.018-1.042Zm-4.69 9.64a1.998 1.998 0 0 0 2.83 0l1.25-1.25a.751.751 0 0 1 1.042.018.751.751 0 0 1 .018 1.042l-1.25 1.25a3.5 3.5 0 1 1-4.95-4.95l2.5-2.5a3.5 3.5 0 0 1 4.95 0 .751.751 0 0 1-.018 1.042.751.751 0 0 1-1.042.018 1.998 1.998 0 0 0-2.83 0l-2.5 2.5a1.998 1.998 0 0 0 0 2.83Z"></path></svg></a></div>
<p dir="auto">There are a number of features that would be nice to have to make the process for judging how well a variable does at predicting another</p>
<p dir="auto">The main thing we can do is to use a gaussian to map <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r$</math-renderer> to <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$[0,10]$</math-renderer> so that we now have</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$$10e^{-r^2}$$</math-renderer></p>
<p dir="auto">The main advantage of doing this beside bounding our score between <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$0$</math-renderer> and <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$10$</math-renderer> is to divide the score into roughly three regions i) Low, ii) Intermediate, and iii) High. Due to the characteristic of the gaussian, the derivative</p>
<p dir="auto"><math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$$\frac{d}{dr}\Big(10e^{-r^2}\Big)=-20re^{-r^2}$$</math-renderer> will not vary that much when <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r$</math-renderer> is close to zero (in the high score region) nor far from zero (in the low score region); thus, we get good separation of of the scores for the most part. The only remaining question is where is the intermediate region?. We can bound the region of interest since the maximum change in the value of the BARS occurs when <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r\approx .71$</math-renderer> with a maximum value of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$.86$</math-renderer>: This forms the boundary of the intermediate-to-low score region. The boundary for the high-to-intermediate should occur when a small increase in <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r$</math-renderer>, say by <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$.01$</math-renderer> leads to the score dropping below the previously establish threshold of <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$.71$</math-renderer>. So, we need to solve the linearization around <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r$</math-renderer> such that</p>
<p dir="auto"><math-renderer class="js-display-math" style="display: block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$$e^{-r^2}-2re^{-r^2}(r+.01)=.71$$</math-renderer></p>
<p dir="auto">which implies that <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$r\approx.32$</math-renderer> which means <math-renderer class="js-inline-math" style="display: inline-block" data-static-url="https://github.githubassets.com/static" data-run-id="eba6b439c319a767b11da443eda98c54">$BARS(.32)\approx .90$</math-renderer>.</p>
