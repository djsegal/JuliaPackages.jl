<p dir="auto">The <em>typical</em> <code>ParametricProcesses</code> workflow involves creating a process manager with workers, then creating jobs and distributing them amongst those workers using <code>assign!</code> and <code>distribute!</code>.  To get started, we can create a <code>ProcessManager</code> by using the <code>processes</code> Function. This <code>Function</code> will take an <code>Int64</code> and optionally, a <code>Process</code> type. The default process type will be <code>Threaded</code>, so ensure you have multiple threads for the following example:</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="procs = processes(5)"><pre>procs <span class="pl-k">=</span> <span class="pl-c1">processes</span>(<span class="pl-c1">5</span>)</pre></div>
<p dir="auto">We can create a process manager with workers of any type using this same <code>Function</code>, <code>processes</code>.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="async_procs = processes(2, Async)"><pre>async_procs <span class="pl-k">=</span> <span class="pl-c1">processes</span>(<span class="pl-c1">2</span>, Async)</pre></div>

<p dir="auto">Here is a list of other functions used to manage workers.</p>
<ul dir="auto">
<li><code>close(pm::ProcessManager)</code> - closes <strong>all</strong> active <code>Workers</code> in <code>pm</code>.</li>
<li><code>delete!(pm::ProcessManager, pid::Int64)</code> - closes <code>Worker</code> by <code>pid</code></li>
<li><code>delete!(pm::ProcessManager, name::String)</code> - closes <code>Worker</code> by <code>name</code>.</li>
<li><code>worker_pids(pm::ProcessManager)</code>  - returns worker process identifiers for all <code>Workers</code> in <code>pm.workers</code></li>
<li><code>waitfor(pm::ProcessManager, pids::Any ...)</code> - waits for <code>pids</code> to finish, then returns their returns in a <code>Vector{Any}</code></li>
<li><code>put!(pm::ProcessManager, pids::Vector{Int64}, vals ...)</code> - serializes data and defines in in the <code>Main</code> of each process in <code>pids</code>.</li>
</ul>
<p dir="auto">There is also <code>@everywhere</code> used to define functions and modules across all workers, as well as <code>@distribute</code> to use all available workers for iteration.</p>

<p dir="auto">In order to use our threads to complete tasks, we will need to construct a sub-type of <code>AbstractJob</code>. The running type for this is <code>ProcessJob</code>, which may be called from the <code>new_job</code> binding. We provide this with a <code>Function</code> that takes arguments, as well as the arguments we seek to provide to that <code>Function</code> (if any).</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="new_job(f::Function, args ...; keyargs ...)"><pre><span class="pl-c1">new_job</span>(f<span class="pl-k">::</span><span class="pl-c1">Function</span>, args <span class="pl-k">...</span>; keyargs <span class="pl-k">...</span>)</pre></div>

<p dir="auto">Adding your own <code>Workers</code> is pretty straightforward. We can create new functionality by creating a new &lt;: <code>Process</code> or a new &lt;: <code>AbstractWorker</code>. A <code>Process</code> is used to change the functionality of a <code>Worker</code>, an <code>AbstractWorker</code> extension usually means we need to facilitate different types of <code>Worker</code> data or <code>ProcessManager</code> functionality. Creating a <code>Process</code> is very simple, as a <code>Process</code> is simply an <code>abstract</code> type.</p>
<div class="highlight highlight-source-julia notranslate position-relative overflow-auto" dir="auto" data-snippet-clipboard-copy-content="abstract type CUDA &lt;: Process end"><pre><span class="pl-k">abstract type</span> CUDA <span class="pl-k">&lt;:</span> <span class="pl-c1">Process</span> <span class="pl-k">end</span></pre></div>

<p dir="auto">Pretty simple; these are the main functionality that changes when we are using different hardware -- allocating jobs, creating workers to do the jobs, and closing the workers will all be different depending on what <code>Process</code> we are using. Fortunately, a <code>Worker</code> will fit entirely into the API by simply extending these three, so with these simple functions we can easily create high-level bindings to distribute our jobs over a myriad of different worker types. If we wanted to create our own <code>Worker</code>, things would get a little more complicated. It is also possible to make your own sub-type of <code>AbstractProcessManager</code> or <code>AbstractJob</code> and extend that way. All of the information needed to follow consistencies for these super-types are available in the documentation.</p>

<p dir="auto">We are not super picky on contributions, as the goal of <a href="https://github.com/ChifiSource">chifi</a> is to get more people involved in computing. However, if you want your code merged there are definitely a few things to be aware of before contributing to this package.</p>
<ul dir="auto">
<li>If there is no issue for what you want to do, <a href="https://github.com/ChifiSource/ParametricProcesses.jl">create an issue</a></li>
<li>If you have multiple issues, <strong>submit multiple issues</strong> rather than typing each issue into one issue.</li>
<li>Make sure the issue you are solving or feature you want to implement is still feasible on <code>Unstable</code> -- this is the top-level development branch which represents the latest unstable changes.</li>
<li>Please format your documentation using the technique presented in the rest of the file.</li>
<li>Make sure <code>Pkg.test("ParametricProcesses")</code> works with your version of <code>ParametricProcesses</code> before making a pull-request.</li>
</ul>
